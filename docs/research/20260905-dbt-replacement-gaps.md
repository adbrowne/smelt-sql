# Research: gaps to smelt as a production dbt replacement (post-backlog)

**Date**: 2026-09-05
**Topic**: Assuming the current outcome backlog (`.claude/outcome-backlog`, all `docs/outcomes/2026090[4-5]-*` entries) lands in full, what is still missing for smelt to be a viable production replacement for dbt? Scoped to gaps that survive that work, not a restatement of what's already queued.
**Related**: `docs/research/20260529-dbt-incremental-adapter.md` (dbt-as-adapter, planner-rules-vs-macros framing — this doc does not re-litigate that conclusion, it assumes the adapter mode is *not* built and asks what a standalone smelt project still lacks), `docs/research/20260905-ten-directions.md` (item 3 restates the adapter idea as still-unbuilt; item 4 "explain the diff" is the one already scaffolded as `docs/outcomes/20260905-property-diff`), `docs/specs/architecture.md` §"Specs not yet authored" (names `migration_from_dbt.md` as unauthored — this doc is a first pass at that content, not the spec itself).

## What "post-backlog" means here

The backlog (`docs/outcomes/20260904-programme-hygiene` through `20260905-property-diff`) is entirely **incremental-maintenance substrate work**: walk-migration residue, delta-signature front door, decision/dialect-emission residue, ratchet paydown, and the property-diff ("explain the diff") feature. None of it touches macros/extensibility, seeds/snapshots, semantic layer, docs-site generation, CI defer/state workflows, auth, orchestration integration, or adapter breadth. So "after the backlog" leaves smelt's *incremental-correctness* story much stronger and everything below **completely untouched** — this doc is the gap list for that untouched surface, which is most of what a production dbt shop actually depends on day to day.

## Executive summary (ranked most severe first)

1. **No adapter ecosystem beyond three backends (DuckDB, Spark, BigQuery)** — no Snowflake, Redshift, Postgres, Databricks-SQL-warehouse, or Athena. dbt has 20+ maintained adapters; most production dbt shops run on one of the ones smelt doesn't have. **Blocker** for the majority of prospective switchers, and structurally hard (each backend needs its own dialect emission + capability matrix, `CLAUDE.md` "Function-registry single ownership" rule).
2. **No macro/package ecosystem entry point** — smelt's typed meta-language + `smelt.define` functions are a real (arguably better) mechanism, but there is no `smelt` equivalent of `dbt-utils`/`dbt_expectations`/dbt Hub: no package manager, no published community library, no way to pull in someone else's reusable logic. A team migrating loses every `dbt_utils.*` call site with no drop-in replacement.
3. **No CI "slim CI" workflow (state comparison + `--defer`)** — dbt's `state:modified+ --defer --state ./state` is the standard PR-CI pattern (build only what changed, against a deferred prod baseline) and is heavily used operationally. smelt has `smelt diff` (schema-level) and the incoming `property_diff` outcome (property-level, git-ref baseline) but neither is a *selection* mechanism that changes what a CI run builds/tests, nor is there a `--defer`-equivalent to avoid rebuilding unselected upstream models in a sandbox target.
4. **No snapshots (SCD2) as a first-class feature** — dbt ships `dbt snapshot` with `dbt_valid_from`/`dbt_valid_to`/`dbt_scd_id` and `timestamp`/`check` strategies out of the box. smelt's own incremental-models spec *lists* SCD2 as a limitation example (`docs/specs/incremental_models.md:231`, "one further model... SCD2... appears in §Limitations") rather than a shipped materialization — the maintenance-plan framework can express it in principle but there's no packaged, one-line `snapshot` declaration.
5. **No auth/permissions/multi-tenant model at all** — `smelt ui` explicitly has "no authentication and no HTTPS" (`docs/specs/cli.md:145`); there is no RBAC, no per-project role model, no SSO story. dbt Core itself doesn't have this either (it's a dbt Cloud feature), but a serious production rollout for a team needs *some* answer, and smelt has zero surface area toward it, even at the CLI/warehouse-permissions-passthrough level.
6. **No orchestrator integration story** — no Airflow provider, no Dagster asset factory, no dbt Cloud-equivalent scheduler with a UI (the self-directed-scheduler research, `docs/research/20260905-self-directed-scheduler.md`, is same-day and unshipped). dbt has mature first- and third-party integrations (`dbt-airflow`, `dagster-dbt`) that smelt has nothing analogous to.
7. **No migration tooling from an existing dbt project** — confirmed empty by `docs/specs/architecture.md:541` ("`migration_from_dbt.md` ... No content today"). Every switch is a from-scratch rewrite; the May adapter research explicitly deferred this ("dbt manifest importer... Best pure on-ramp... deferred").
8. **Docs-site generation is Markdown/JSON only, not a hosted interactive site** — `smelt docs generate` (`docs/specs/data_catalog.md`) has no HTML output, no `smelt docs serve`, no DAG visualization, no free-text search — all named as open follow-ons in `docs/TODO.md` ("`smelt docs` follow-ons: HTML output, `smelt docs serve`, column-lineage visualization"). dbt's generated docs site (search + DAG + column lineage, hosted by dbt Cloud or any static host) is table stakes for analyst-facing teams.

## If I could only fix N things before calling this production-ready

Ranked by (severity × how many prospective adopters it blocks), assuming the incremental-substrate backlog above is already done:

1. **Ship at least one more mainstream warehouse adapter (Snowflake or Postgres first)** — without this, the addressable market is "already on DuckDB/Spark/BigQuery," which is a small slice of the dbt install base. This is the single highest-leverage, highest-cost item; start with Postgres (cheapest dialect delta, `smelt-dialect` already has strong DuckDB/Spark/BigQuery infrastructure to extend) as a proof the registry-driven emission model generalizes, then Snowflake for market reach.
2. **Build the slim-CI selection + defer mechanism** — `state:modified+` equivalent wired into `model_selection.md`'s grammar plus a defer-resolution mode in `smelt-runtime`. This is the single most-used *operational* dbt workflow and currently has zero smelt equivalent (the queued `property_diff` outcome is adjacent but explicitly not a selection mechanism).
3. **Write and ship `migration_from_dbt.md` plus a real manifest/compiled-SQL importer** — even a partial importer (import naive, non-macro-heavy models verbatim; flag the rest for manual port) turns "rewrite everything" into "port the hard 20%," which is very likely a total-cost-of-adoption blocker today.
4. **A minimal package/library mechanism for `smelt.define` functions** — does not need to be a full registry on day one; even a documented "how to vendor a shared `.sql` file of common functions across projects" convention closes the most common `dbt_utils.*` call sites (surrogate keys, date spines, pivot helpers already flagged in `docs/ROADMAP.md`'s deferred-work list).
5. **Snapshots (SCD2) as a first-class declaration** — the maintenance-plan substrate (post-backlog) is exactly the machinery to derive this correctly; turning the currently-unmet spec example into a real `smelt snapshot`-equivalent surface is comparatively cheap relative to items 1–3 and closes a very common real-world requirement (dimension history tracking).

Items not in the top 5 but worth flagging to the user directly: auth/permissions and orchestrator integration are both real blockers for *team* production use, but they're more "wrap smelt in existing infrastructure" problems (a thin Airflow/Dagster adapter, warehouse-native permissions) than deep architectural gaps — lower engineering risk, likely fine to sequence after 1–4 once there's a concrete pilot team asking for them.

# Research: Pipe SQL (`|>`) syntax for smelt

**Date**: 2026-06-27
**Topic**: Whether and how smelt should accept BigQuery/Databricks-style **pipe syntax** (`FROM t |> WHERE p |> AGGREGATE sum(x) GROUP BY y`) as an authoring surface. First pass collapses pipes back to standard SQL for every backend; the architecture should leave room to emit *native* pipe SQL on backends that support it (BigQuery, Databricks/Spark 4.0, DuckDB-via-extension) later.
**Motivating ask** (Andrew): support pipe SQL like BigQuery and Databricks (and DuckDB via extension). First pass: backends collapse it back to normal SQL. Both goals: author now, native passthrough later. Operator scope is bounded by what smelt's SQL surface already supports.
**Related**: `docs/specs/architecture.md` (compilation pipeline, single typed CST, identity printer), `docs/specs/models.md` (model-body surface), `docs/specs/meta_language.md` (the existing meta-world `|>` operator — the disambiguation question), `docs/specs/types.md` + `crates/smelt-db/src/type_inference/` (stage-by-stage column scope), `docs/specs/scoping.md`.

---

## 0. TL;DR

1. **Pipe SQL is a syntactic re-spelling of the relational algebra smelt already compiles.** Every pipe operator in scope maps onto a clause smelt's parser and type inference already support. There is no new *execution* semantics — only a new way to write the same query. That makes "collapse to standard SQL" a real and clean target.

2. **smelt is unusually well-positioned for it.** Its analysis already walks `FROM → WHERE → GROUP BY → HAVING → SELECT` as a *stage pipeline*, threading a `TypeContext` ("the columns visible at this point") from one clause to the next (`type_inference/binary.rs::walk_select_columns`). Pipe SQL's mental model — *each stage is a table→table function; the next stage sees exactly the previous stage's output columns* — is **literally that same stage model made syntactically explicit**. The semantic engine pipe SQL needs already exists.

3. **The one real design tension is the token.** `|>` (`PIPE_ARROW`) is already taken: it is the **meta-language** pipe (`x |> f(args)` ≡ `f(x, args)`, desugared at compile time, `expr.rs:136`). SQL-world pipes and meta-world pipes are different languages that would share a glyph. Disambiguation is the load-bearing decision and §4 lays out the options.

4. **Recommended shape:** a **FROM-first pipe query** is a new *query form* that parses into first-class pipe CST nodes, is analysed by reusing the existing stage-by-stage `TypeContext` machinery, and is **lowered at the dialect-printer seam** (`smelt-dialect`) — the exact place the codebase already chooses between native and rewritten SQL (it already rewrites `QUALIFY`→subquery for backends that lack it). That seam is where "collapse to standard SQL today, emit native pipes on capable backends tomorrow" becomes a single capability flag, not a rewrite. (§5, §7.)

5. **Scope (first pass):** the BigQuery operator set **intersected with smelt's surface** — `FROM`, `WHERE`, `SELECT`, `EXTEND`, `SET`, `DROP`, `RENAME`, `AS`, `AGGREGATE … GROUP BY`, `ORDER BY`, `LIMIT`, `JOIN`, `UNION/INTERSECT/EXCEPT`, `DISTINCT`. Defer `CALL` (TVFs), `WINDOW`-as-operator, `TABLESAMPLE`, `ASSERT`, and `PIVOT/UNPIVOT` (see the discrepancy flag in §3).

6. **Open the spec with one decision needed from Andrew before we write it:** the disambiguation strategy (§4) and confirmation of the PIVOT/UNPIVOT status (§3).

## 1. What pipe SQL is

Pipe syntax comes from Google's VLDB paper *"SQL Has Problems. We Can Fix Them: Pipe Syntax in SQL."* The model: a query is a **linear chain of stages**. It starts from a table (`FROM t`, a "FROM-first" query) and each `|> OPERATOR …` consumes the table the previous stage produced and emits a new table. Because evaluation order *is* lexical order, the scoping warts of standard SQL disappear: a column created by `|> EXTEND x AS y` or `|> AGGREGATE … AS y` is immediately visible to the next `|> WHERE y > 0` — no separate `HAVING`/`QUALIFY`, no "alias not visible in WHERE."

```sql
-- pipe form
FROM orders
|> WHERE status = 'paid'
|> AGGREGATE sum(amount) AS revenue GROUP BY customer_id
|> WHERE revenue > 1000
|> ORDER BY revenue DESC
|> LIMIT 10

-- standard form (the lowering target)
SELECT customer_id, sum(amount) AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING sum(amount) > 1000      -- the post-aggregate |> WHERE
ORDER BY revenue DESC
LIMIT 10
```

## 2. State across the three backends

| Engine | Support | Notes |
|---|---|---|
| **BigQuery** | **GA 2025-02-04**, on by default | Reference implementation. Richest operator set. Allows both FROM-first *and* pipes appended to a complete standard `SELECT … FROM …` query. |
| **Databricks / Spark** | **Spark 4.0 / DBR 16.2+** (DBR 18+ also accepts bare `\|`) | Backward-compatible. **Omits** `RENAME`, `CALL`, `WINDOW`, `DISTINCT`, `ASSERT` and the `GROUP AND ORDER BY` form vs BigQuery. |
| **DuckDB** | **Community extension only** (`psql` / `duckdb-psql` by ywelsch) | Thin syntactic rewrite; supports `from/where/select/group by/order by/limit/join` piped, uses `(\| … \|)` for nested sub-pipes. Does **not** implement the BigQuery verbs (`EXTEND`, `AGGREGATE`, `SET`, …). Core DuckDB has an open feature request, nothing shipped. |

**Portable native subset** = BigQuery's set minus Spark's omissions. For the *collapsed* path this doesn't matter (we emit standard SQL everywhere). For the future *native* path it defines a per-backend capability matrix: only operators a backend natively understands can be passed through; the rest must lower even on a pipe-capable backend.

Sources: [BigQuery pipe reference](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/pipe-syntax), [BigQuery pipe guide](https://docs.cloud.google.com/bigquery/docs/pipe-syntax-guide), [BigQuery GA blog](https://cloud.google.com/blog/products/data-analytics/simplify-your-sql-with-pipe-syntax-in-bigquery-and-cloud-logging), [Spark 4.0.2 pipe docs](https://spark.apache.org/docs/4.0.2/sql-pipe-syntax.html), [Databricks pipe blog](https://www.databricks.com/blog/sql-gets-easier-announcing-new-pipe-syntax), [DuckDB psql extension](https://duckdb.org/community_extensions/extensions/psql), [duckdb-psql repo](https://github.com/ywelsch/duckdb-psql).

## 3. Operator scope — pipe operators × smelt's surface

The first pass covers exactly the pipe operators that correspond to SQL smelt already parses and type-checks. From the surface audit (`parser/select.rs`, `syntax_kind.rs:154-217`, `ast.rs:891-947`):

| Pipe operator | Standard-SQL meaning | smelt support | First pass? |
|---|---|---|---|
| `FROM t` | table source (incl. `smelt.ref()`, subquery, `LATERAL`) | ✅ `FROM_CLAUSE`/`TABLE_REF` | ✅ entry point |
| `\|> WHERE p` | `WHERE` pre-agg / `HAVING` post-agg / `QUALIFY` post-window | ✅ all three clauses exist | ✅ |
| `\|> SELECT …` | projection (a stage, not "last") | ✅ `SELECT_LIST` | ✅ |
| `\|> EXTEND e AS c` | `SELECT *, e AS c` (re-projection) | ✅ via projection | ✅ |
| `\|> SET c = e` | re-project replacing `c` | ✅ via projection | ✅ |
| `\|> DROP c` | re-project dropping `c` | ✅ via projection | ✅ |
| `\|> RENAME a AS b` | re-project aliasing | ✅ via projection | ✅ |
| `\|> AS alias` | name the intermediate table | ✅ table alias | ✅ |
| `\|> AGGREGATE agg … [GROUP BY k …]` | `SELECT k, agg … GROUP BY k` | ✅ `GROUP_BY_CLAUSE` + aggregates | ✅ |
| `\|> ORDER BY …` | `ORDER BY` | ✅ `ORDER_BY_CLAUSE` | ✅ |
| `\|> LIMIT n [OFFSET m]` | `LIMIT/OFFSET` | ✅ `LIMIT_CLAUSE` | ✅ |
| `\|> JOIN [kind] t ON…/USING…` | join (pipe input = left) | ✅ `JOIN_CLAUSE` (INNER/LEFT/RIGHT/FULL/CROSS) | ✅ |
| `\|> UNION/INTERSECT/EXCEPT (q),(q)…` | set ops (N-way, comma-separated) | ✅ binary set ops; N-way needs un-nesting | ✅ (lower to nested binary) |
| `\|> DISTINCT` | `SELECT DISTINCT *` | ✅ `DISTINCT` | ✅ |
| `\|> WINDOW w AS …` | window-col stage | ⚠️ window funcs supported, operator form new | ⏸️ defer |
| `\|> CALL tvf(args)` | pipe table into TVF | ❓ TVF surface unclear | ⏸️ defer |
| `\|> TABLESAMPLE …` | sampling | ⚠️ exists on `TABLE_REF` only | ⏸️ defer |
| `\|> ASSERT cond` | row-level runtime check | ❌ no equivalent construct | ⏸️ defer |
| `\|> PIVOT/UNPIVOT` | pivot | ⚠️ **see discrepancy** | ⏸️ defer |

**✅ Discrepancy resolved.** The ask said "smelt doesn't support PIVOT/UNPIVOT"; the surface audit found `PIVOT_CLAUSE`/`UNPIVOT_CLAUSE` in the *parser*. Reconciliation (verified): pivot is **parse-only and actively rejected** — `check_types.rs:278-302::check_unsupported_constructs` emits an `Error` diagnostic, *"PIVOT is not supported — output columns depend on data values and cannot be determined at compile time"* (tests `test_pivot_rejected_with_diagnostic`/`test_unpivot_rejected_with_diagnostic`; known-gap registry `parser-compat/src/gaps.rs:152` `pivot_unpivot`, `planned_fix: false`). This is a **principled** rejection: smelt requires compile-time-determinable output schemas. Therefore the pipe `|> PIVOT`/`|> UNPIVOT` operators are deferred *for the same reason* — not an oversight, and the spec should state it that way.

## 4. The disambiguation problem (the decision that gates the spec)

`|>` already means something in smelt: the **meta-language pipe**, `x |> f(args)` ≡ `f(x, args)`, parsed in `expr.rs:136-175` into a `PIPE_EXPR` node, lowered entirely at compile time (it never reaches the database). The lexer emits one `PIPE_ARROW` token, currently only consumed in meta contexts.

SQL-world pipes (`FROM t |> WHERE …`) and meta-world pipes are **different languages sharing a glyph**. They never legally co-occur — meta pipes live in `smelt.define`/generator bodies (meta-expressions); SQL pipes live in a Data-World query body. So this is resolvable by *context*, not a hard grammar clash, but we must choose how:

- **Option A — Context-directed parse (recommended).** Reuse the same `PIPE_ARROW` token; the *parser position* decides meaning. Inside a query body the pipe-chain parser owns `|>`; inside a meta-expression the existing `PIPE_EXPR` parser owns it. This matches how smelt already disambiguates (`parse_file` dispatches by leading keyword; `=>` is a named-param only in argument position). No lexer change, no new glyph. Cost: the SELECT/query parser must learn to continue into a pipe chain, and we must be sure the two never nest ambiguously (they don't, given Data-World vs meta-World separation — but the spec must state the boundary precisely).
- **Option B — Distinct token.** Give SQL pipes their own glyph (e.g. a different arrow). Zero ambiguity, but diverges from BigQuery/Spark/DuckDB syntax — defeats the compatibility goal. **Rejected** unless A proves unworkable.
- **Option C — Mode marker.** Require a leading marker to enter pipe mode (e.g. a `FROM`-first body is implicitly pipe mode). Effectively a sub-case of A: "FROM-first body ⇒ the query parser is in pipe-accepting mode." Worth folding into A as the trigger rule.

**Recommendation:** Option A with the C trigger — *a query body that begins with `FROM` (no leading `SELECT`) is a pipe query*, and within it `|>` is the SQL pipe. This also answers "where can pipe SQL appear" (§5).

## 5. Where pipe SQL can appear, and how it lowers

**Where (recommendation).** Model a pipe query as a **query form that produces the same thing a `SELECT_STMT` produces** — a table. Then it composes anywhere a query is legal: a whole model body, a subquery `(FROM t |> …)`, a CTE body, a set-op arm. BigQuery and Spark both allow this (and allow appending pipes to a standard `SELECT` too). **First pass:** support the **model body** and **subquery/CTE body** positions; appending pipes onto a *standard* leading `SELECT` (BigQuery's other form) can be a later nicety — FROM-first is the simpler, unambiguous trigger.

**How it lowers — two architectures:**

- **(L1) Desugar at the CST level into standard `SELECT_STMT` subtree(s).** Pipe nodes are rewritten to ordinary clauses/subqueries before analysis; nothing downstream changes. *Pro:* smallest blast radius; type inference, planner, dialect printer all untouched. *Con:* the user's pipe structure is gone by analysis time (worse diagnostics that point at original syntax), and native passthrough later means re-deriving pipes or keeping the original CST alongside — awkward.
- **(L2) First-class pipe CST nodes, analysed via the existing stage machinery, lowered at the dialect printer (recommended).** A `PIPE_QUERY` node holds an ordered list of stage nodes. Analysis reuses `walk_select_columns`'s `TypeContext` threading — each stage updates the visible-column set exactly as clauses do today. Emission happens in `smelt-dialect/printer.rs`, which **already** chooses native-vs-rewritten per backend (e.g. `QUALIFY`→subquery). A `supports_pipe_syntax` capability flag (added to `BackendCapabilities`, `dialect.rs`) selects: emit native `|>` (BigQuery/Spark/DuckDB-psql) or collapse to standard SQL (everyone else, and everyone in the first pass). *Pro:* the native-vs-collapsed decision lands at the one seam built for exactly this; diagnostics keep pipe structure; "author now, native later" is a flag flip, not a rewrite. *Con:* analysis and the printer must learn pipe stages — but the `TypeContext` stage model already matches, so this is additive, not novel.

**Recommendation: L2.** It puts the central design goal (collapse now / native later) at the seam that already exists for it, and it exploits the fact that smelt's analyzer is *already* a stage pipeline. L1 is a viable faster first cut if we want a parse-and-desugar spike before committing, but L2 is the architecture the spec should target.

**Lowering rules (collapse path), per operator:**
- Stages up to the first aggregation collect into one `SELECT_STMT`: `FROM`, pre-agg `|> WHERE` → `WHERE`, `|> JOIN` → joins.
- `|> AGGREGATE a … GROUP BY k …` → `SELECT k…, a… GROUP BY k…` (output order: keys then aggregates). Post-aggregate `|> WHERE` → `HAVING` (or a wrapping subquery).
- `|> SELECT/EXTEND/SET/DROP/RENAME/DISTINCT` → a (re-)projection; when it follows a stage that already fixed the projection, wrap the prior query as a subquery (`SELECT … FROM (<prev>) `).
- `|> WHERE` after a window column → `QUALIFY` or wrapping subquery.
- `|> ORDER BY` / `|> LIMIT` → trailing clauses on the outermost query.
- **Multiple `|> AGGREGATE` stages** → **nest**: each aggregation wraps the previous as a subquery/CTE (standard SQL can't aggregate twice at one level). This is the main place a pipe query becomes a *stack* of `SELECT_STMT`s rather than one.
- `|> UNION (q1),(q2),…` → left-fold into nested binary set-ops smelt already supports.

Identity/printer note (`architecture.md` §"Identity properties"): the byte-identity printer is for the *authored* CST. The collapsed standard SQL is a *generated* artifact, so it doesn't need byte-identity with anything — but the pipe CST itself must round-trip print like any other smelt source.

## 6. Type inference / scope — why this is a good fit

`type_inference/binary.rs::walk_select_columns` already threads a `TypeContext` (`type_context.rs`) through `FROM → WHERE → GROUP BY → HAVING → SELECT`, where `TypeContext` *is* "the set of columns visible here." Pipe semantics need exactly one generalization: instead of a fixed clause order, fold the **ordered stage list**, each stage taking the prior `TypeContext` and returning a new one (`EXTEND` adds a column, `AGGREGATE` replaces scope with keys+aggregates, `DROP`/`RENAME` edit it, `WHERE` passes it through). The existing per-clause logic is reusable nearly verbatim as per-stage transforms. `subquery.rs::build_subquery_context` already builds a context from a nested query's inferred schema, which is what a `(FROM t |> …)` subquery needs.

## 7. Native passthrough (future, but design for it now)

To not back into a corner (project value: don't foreclose features): the L2 architecture reserves the future cleanly. A `supports_pipe_syntax: bool` (plus a per-operator capability set for the Spark/DuckDB gaps in §2) on `BackendCapabilities` lets the dialect printer emit native pipes where supported and lower elsewhere — including **partial** lowering (pass through the operators a backend knows, lower only the ones it doesn't, e.g. lower `RENAME` for Spark). The first pass simply ships with the flag `false` everywhere, so the only emitted form is collapsed standard SQL — but no later rewrite is required to turn native emission on.

## 8. CST / parser integration sketch (non-binding)

- New `SyntaxKind`s: `PIPE_QUERY` (root, holds a `FROM_CLAUSE` then ordered stage nodes), and one node per stage operator (`PIPE_WHERE`, `PIPE_SELECT`, `PIPE_EXTEND`, `PIPE_SET`, `PIPE_DROP`, `PIPE_RENAME`, `PIPE_AS`, `PIPE_AGGREGATE`, `PIPE_ORDER_BY`, `PIPE_LIMIT`, `PIPE_JOIN`, `PIPE_SET_OP`, `PIPE_DISTINCT`). Reuse the existing clause sub-node grammar inside each (a `PIPE_WHERE` wraps the same expression a `WHERE_CLAUSE` does).
- Parser: `select.rs`/`smelt_ext.rs` model-body entry detects a FROM-first body and dispatches to a `parse_pipe_query` that loops on `PIPE_ARROW` + an operator keyword. Follows the meta-pipe precedent (`expr.rs:136`) and the `parse_file` keyword-dispatch precedent (`smelt_ext.rs:18`).
- AST wrappers in `ast.rs` mirroring the `SelectStmt` accessor style.
- Reuse `PIPE_ARROW` token (Option A, §4) — no lexer change.

## 9. Decisions (confirmed by Andrew, 2026-06-27)

1. **Disambiguation** (§4): **Option A** — context-directed parse, reuse the `|>` (`PIPE_ARROW`) token, a FROM-first query body is the pipe-mode trigger. No lexer change, no new glyph; matches BigQuery/Spark/DuckDB syntax.
2. **Lowering architecture** (§5): **L2** — first-class pipe CST nodes, analysed via the existing stage-by-stage `TypeContext`, lowered at the `smelt-dialect` printer seam. Native passthrough later is a `supports_pipe_syntax` capability flag, not a rewrite.
3. **PIVOT/UNPIVOT** (§3): resolved — parse-only, rejected by design (schema not compile-time determinable). Pipe `|> PIVOT`/`|> UNPIVOT` deferred for the same principled reason.
4. **Surface positions** (§5): first pass = **model body + subquery/CTE body**. Defer "pipes appended to a standard leading `SELECT`."
5. **Operator first-cut** (§3 table): ship `FROM`, `WHERE`, `SELECT`, `EXTEND`, `SET`, `DROP`, `RENAME`, `AS`, `AGGREGATE … GROUP BY`, `ORDER BY`, `LIMIT`, `JOIN`, `UNION/INTERSECT/EXCEPT`, `DISTINCT`. Defer `WINDOW`-operator, `CALL`/TVF, `TABLESAMPLE`, `ASSERT`, `PIVOT/UNPIVOT`.

## Severity & tags

- **Critical** — design flaw or contradiction that would propagate into a wrong implementation.
- **Major** — ambiguity likely to cause two implementers to build divergent behaviour.
- **Minor** — clarity, structure, or template-conformance issue. · **Nit** — trivial.

## Executive summary

Even across only 17 specs, the dominant failure mode is **one rule stated more than once and drifting between statements** — within a spec and, more dangerously, between two normative specs that each claim authority. The 14 Criticals are mostly of this kind, plus three first-principles design errors (unsound math) a plausibility read would miss.

**Recurring themes**

1. **Self-contradiction across repeated statements of one rule.** A rule is asserted in Surface, restated in Semantics, pinned again in Constraints — and the three disagree. Worst: the incremental output-clamp described as *write window* in one place and *run window* in three others (C9); cumulative-aggregate idempotence stated backwards relative to the spec's own reprocessing paragraph (C3); the architecture resolution table contradicting the scan-root-stripping note three lines below it (C1).
2. **Two specs, one concern, no owner.** Normative specs define the same surface differently: `functions.md` bans meta-type `smelt.define` parameters that `types.md`'s annotation table admits (C7); `gradual_typing.md` and `functions.md` give opposite call-site return types for Tier 1/2 functions (C8); `lsp.md` and `diagnostics.md` both hard-code namespaces (`smelt.functions.<name>`) that `functions.md` says are directory-derived. Highest-leverage class — invisible inside either spec; only a cross-spec read catches it (that pass is still pending, so expect more).
3. **Unsound math/semantics that reads plausibly.** `schema_evolution.md`'s DECIMAL widening rule `p2≥p ∧ s2≥s` permits `DECIMAL(10,2)→DECIMAL(10,5)`, which loses integer-digit capacity and overflows (C14); the per-source bound tuple conflates a *read* bound (inverse image) with a *write* skew (forward image) and the worked sessionization example comes out wrong (C10); `datagen.md`'s nullable-from-first-shape rule writes nulls into a non-nullable Arrow column on the spec's own example (C6).
4. **Silent-drop / silent-fallthrough against the project's own fail-loud discipline.** The architecture name-mapping is non-injective with no emitted-name collision check, so two models silently materialize into one table (C2); `models.md` silently drops misspelled `columns:` entries; `python_models.md` silently discards a whole frontmatter block on a name mismatch; `cli.md`'s scope fall-through silently retargets a passing command when a new file is added.
5. **Classifier/validation scope stated for the outer query only.** Equivalence-breaking constructs (window functions, `RANDOM()`, `COUNT(DISTINCT)`, `HAVING`) inside CTEs/subqueries escape `cumulative_aggregate.md`'s outermost-SELECT-only classifier (C4, C5).

**Where the specs are strong.** `architecture.md`, `functions.md`, `meta_config_loading.md`, `datagen.md`, `function_schema_inference.md` scored *good* on solution quality — the designs are sound; their findings are under-specified edges and cross-spec seams, not the core idea. No spec scored *poor* on solution quality. `incremental_models.md` is the only spec graded *poor* on correctness/consistency, driven by the window-semantics contradictions (C9, C10) — its design is right in intent, but the text doesn't yet pin it down.

## Critical findings

*All 14 spot-checked by the orchestrator against the cited spec text. The five highest-impact carry an explicit spot-check note; all will additionally pass adversarial verification when the run completes.*

#### C1 — `architecture.md` — Resolution example table contradicts the dedicated-scan-path note for sources and seeds

- **Section:** Resolution: `smelt.<path>` is the universal addressing scheme
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** The examples table, captioned "assuming `paths: [\"models\"]`", shows `sources/raw/events.yml` → `smelt.raw.events` and `seeds/raw/users.csv` → `smelt.raw.users` (prefixes stripped). But the note directly below says functions/, sources/, and tests/ "are **not** in the `paths:` list by default; their scan-root prefix is not stripped" — so the source should be `smelt.sources.raw.events`. Seeds are worse: per seeds.md, a seed is "a `.csv` file under any directory listed in `smelt.yml::paths`", so under `paths: ["models"]` the file is not a seed at all. Two implementers would build different resolvers from this table.
- **Suggested fix:** Fix the two rows: either change the caption to `paths: ["models", "seeds"]` and the sources row to `smelt.sources.raw.events`, or state explicitly which kinds use dedicated scan paths and whether seeds strip. Add seeds to the dedicated-scan-path note one way or the other.
- **Orchestrator spot-check:** Confirmed against `architecture.md:83-95`. The table (caption `paths: ["models"]`) maps `sources/raw/events.yml → smelt.raw.events`, but line 95 says sources keep their full prefix unstripped → should be `smelt.sources.raw.events`. Direct internal contradiction.

#### C2 — `architecture.md` — Underscore-join name mapping is not injective; silent table clobbering is unguarded

- **Section:** Default materialization name mapping
- **Dimension:** solution-quality · **Implication:** `implementation-impact`
- **Finding:** "Table = address path joined with `_`. Underscores already in path components are preserved as-is (no escaping…)" makes the mapping non-injective: `smelt.staging.orders` and `smelt.staging_orders` both emit `main.staging_orders`. The mapping is "mandatory" with no per-entity override, and the only collision check specified (`project_address_collisions`) is over `smelt.<path>` addresses, not emitted (schema, table) names. Two distinct models silently materialize into one table — exactly the "materialize wrong data with exit 0" failure the Diagnostic-parity section calls the worst case, and a direct fail-loud violation.
- **Suggested fix:** Mandate an emitted-name collision diagnostic (Error) computed over the (target schema, joined name) pairs of all persisted entities in a project, analogous to `DuplicateAddress`; or specify an injective join (escape `_` in components).
- **Orchestrator spot-check:** Confirmed by construction: `smelt.staging.orders` and `smelt.staging_orders` both join to `staging_orders`; the only collision check is over addresses, not emitted names. Real silent-clobber path.

#### C3 — `cumulative_aggregate.md` — Idempotence claim is mathematically inverted (reversible vs irreversible swapped)

- **Section:** Semantics — Execution model
- **Dimension:** correctness-consistency · **Implication:** `spec-edit-only`
- **Finding:** "partial progress is intentional and idempotent under fixed input (re-running the same `[run_start, run_end)` ... converges to the same final state for the reversible-aggregator case)" is backwards. Re-merging a partition with SUM/COUNT doubles values and BIT_XOR self-cancels — the reversible combiners are precisely the non-idempotent ones. The idempotent-under-re-merge combiners are MIN/MAX/BOOL_*/BIT_AND/BIT_OR (the spec's "irreversible" set). §Reprocessing semantics itself says a second merge "adds it again". An implementer trusting this sentence would build a broken retry path.
- **Suggested fix:** Rewrite: re-merging is safe only for idempotent combiners (MIN, MAX, BOOL_*, BIT_AND, BIT_OR); SUM/COUNT/BIT_XOR double-apply. State explicitly that re-running a partially-failed window is NOT generally idempotent and defer to §Reprocessing semantics.
- **Orchestrator spot-check:** Confirmed against `cumulative_aggregate.md:107` vs `:161`. Line 107 claims convergence "for the reversible-aggregator case"; line 161 ("a second merge adds it again") proves SUM/COUNT are exactly the non-idempotent combiners. Labels inverted.

#### C4 — `cumulative_aggregate.md` — Equivalence-breaking constructs in CTEs/subqueries escape the outer-body-only classifier

- **Section:** Semantics — Classifier checks
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** Checks 4 and 5 cover only "the outermost SELECT" / "the outer body" ("Any `OVER (...)` clause on a projection in the outermost SELECT"). A window function, RANDOM(), or nested aggregation inside a CTE or subquery feeding the outer SELECT is computed over one partition's slice and breaks cross-partition equivalence identically, yet passes the classifier. The spec is silent on whether subqueries/CTEs are permitted at all (incremental_models.md gates them via allow_subqueries). This hollows out the §Design claim that rejected constructs "cannot be bypassed".
- **Suggested fix:** Specify the classifier's traversal scope: either reject window functions/non-determinism anywhere in the inlined model body (including CTEs and subqueries), or forbid subqueries/CTEs outright in v1. Also state whether the driving-source walk and pushdown cover FROM clauses inside subqueries.

#### C5 — `cumulative_aggregate.md` — DISTINCT, HAVING, ORDER BY/LIMIT unaddressed; COUNT(DISTINCT) reads as allowlisted

- **Section:** Surface — Aggregator allowlist
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** The allowlist admits "direct calls" like `COUNT(...)`. `COUNT(DISTINCT user_id)` is syntactically a direct COUNT call, but per-partition distinct counts summed across partitions ≠ full-refresh COUNT(DISTINCT) — the canonical non-combinable aggregate. The spec never mentions DISTINCT (in aggregates or `SELECT DISTINCT`), HAVING (per-partition HAVING suppresses keys a full refresh would keep), or ORDER BY/LIMIT on the outer SELECT. A second implementer would plausibly accept all of these, silently violating the cross-partition equivalence contract.
- **Suggested fix:** Add classifier checks: reject DISTINCT qualifiers in aggregator calls and SELECT DISTINCT; reject HAVING; reject LIMIT/OFFSET (define ORDER BY treatment). Add corresponding diagnostic codes or fold into CumulativeUnknownAggregator with explicit wording.

#### C6 — `datagen.md` — Nullability-from-first-shape rule contradicts Constraint 7 and the spec's own example

- **Section:** Semantics > `linked_choice` and joint-distribution pools (Arrow type per field)
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** The rule says Arrow type/nullability is "evaluated against the first shape that declares the field" and "nullable iff the referenced field's generator is nullable (`Optional`)". Constraint 7 allows shapes to differ "modulo `Optional` wrapping". The spec's own example has shape 1 declaring `user_id` as plain `foreign_key` (non-nullable) and shape 2 declaring it `optional { prob: 0.0 }` (always null, weight 0.25). Per the rule, the column is non-nullable Arrow, yet ~25% of pool entries hold null `user_id` — nulls written into a non-nullable column. An implementation following the rule literally crashes or corrupts on the spec's own example.
- **Suggested fix:** Change the nullability rule to: a `linked_choice` column is nullable iff ANY shape wraps the referenced field in `Optional`. Also drop "first shape that declares the field" (all shapes must declare all fields per Constraint 7) and take the unwrapped Arrow type from any shape.

#### C7 — `functions.md` — Meta-type signature ban contradicts types.md's smelt.define annotation table

- **Section:** Design — Data-World parameters only
- **Dimension:** correctness-consistency · **Implication:** `design-decision-needed`
- **Finding:** functions.md says "A `smelt.define` parameter cannot be annotated with a meta-language type (`List<T>`, `Map<K, V>`, `Lambda<…>`)... rejected with `InvalidFunctionTypeRef`", and the Surface grammar lists a vocabulary without them. But types.md §"`smelt.define` type annotations" says "Parameter and return positions accept fragment sorts" and its table includes `List<T>` (Meta list) and `Lambda`. Two normative specs disagree on the signature vocabulary; an implementer following types.md accepts annotations functions.md mandates a diagnostic for. (Possibly types.md means generator-file declarations only, but neither spec says so.)
- **Suggested fix:** Reconcile: either restrict types.md's `List<T>`/`Lambda` rows to generator-file declarations explicitly (and have functions.md cite that carve-out), or admit them in functions.md. State which spec owns the smelt.define annotation vocabulary.

#### C8 — `gradual_typing.md` — Tier 1/2 call-site return type contradicts functions.md Semantics rule 16

- **Section:** Tier 1 — call-site expansion
- **Dimension:** correctness-consistency · **Implication:** `design-decision-needed`
- **Finding:** This spec says "A synthesised return type flows up from the body and is consumed by the surrounding expression context" and (§No cross-boundary inference) that a Tier 1 return is "computed at each call site from the expansion". functions.md Semantics 16 says the opposite: "absent return types (Tier 1/2 functions) all produce `Unknown` at the call site." types.md §10 sides with gradual_typing. An implementer of call-site typing would produce opposite behaviour depending on which spec they read.
- **Suggested fix:** Decide which rule is normative (per-call-site synthesis for Tier 1 appears intended), then amend functions.md rule 16 to carve out Tier 1 expansion, or amend this spec. Add an explicit cross-reference stating who owns call-site return typing.

#### C9 — `incremental_models.md` — Outer output clamp: write window vs run window contradiction in four places

- **Section:** Execution model (DuckDB, current)
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** Execution model step 2 says the injected filter is `WHERE partition_column >= write_start AND partition_column < write_end` and "constrains the model's *output* to the same write window the DELETE covers". But §"Run window vs partition granularity" says "the outermost WHERE constrains the output to the 30-day run window", §"Source-filter pushdown" says "The outer WHERE constrains the model's output to the run window", and Constraint 5 says "constraining the model's output to the run window". For a write-rebasing model these differ: DELETE over the write window plus INSERT clamped to the run window permanently destroys the lookback partitions' rows.
- **Suggested fix:** Standardize on the write window everywhere the output clamp is described (§Run window vs partition granularity, §Source-filter pushdown bullet, Constraint 5, and the Design paragraph's `>= start AND < end`). Add a note that write window == run window when the derived skew is zero.
- **Orchestrator spot-check:** Confirmed against `incremental_models.md`: step 2 (`:96`) clamps output to the *write* window; `:108`, `:204`, Constraint 5 (`:296`) clamp to the *run* window. For a rebasing model these differ, and DELETE(write)+INSERT(run) loses the lookback partitions. High-impact.

#### C10 — `incremental_models.md` — One (before, after) tuple conflates read bound (inverse image) with write skew (forward image)

- **Section:** Per-source bound derivation
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** The tuple is defined as "the inverse image of the run window in the source's partition-column space" (a read bound), yet step 1 reuses the same bound to widen the write window — the *forward* image, which points the opposite direction. The spec's own rebasing example is labelled `Bounded(c, 1d, 0)` ("a 1-day lookback"), but under the inverse-image definition a session keyed by `session_start_date` gaining events for 1 day gives (0, 1d). Worked through: with read range `[run_start-1d, run_end)`, a session starting just before `run_end` misses its later events that already exist in the source, violating per-partition equivalence on run-window partitions during backfill.
- **Suggested fix:** Split the model into two derived quantities: write-skew (how far output partitions extend before/after the run window) and read-bound (per-source, derived relative to the *write* window: `[write_start - before, write_end + after)`). Re-derive the sessionization example with both.

#### C11 — `meta_config_loading.md` — Overlay validation contradicts required-field rule for record-shaped roots

- **Section:** Per-target overlay
- **Dimension:** correctness-consistency · **Implication:** `design-decision-needed`
- **Finding:** §Per-target overlay says "A target overlay file that does not validate against the schema emits the same diagnostic family as a base-file mismatch", and §Surface makes every schema field required (`ConfigLoaderRequiredFieldMissing`). But §Design motivates record deep-merge precisely so a user can "override `connection_string` per target without restating every other field" — i.e. a partial overlay omitting required fields. Validated standalone, every legitimate partial overlay errors; the spec never says whether validation is pre-merge (against a relaxed schema) or post-merge (against the merged value, with spans mapped back per-field).
- **Suggested fix:** State the order explicitly: for record roots, overlay fields are validated individually against their schema field types (unknown-field and type checks pre-merge), then required-field completeness is checked on the merged value, with each diagnostic anchored at the file that supplied (or last omitted) the field.

#### C12 — `planner_integration.md` — Filter-pushdown soundness condition via provenance is undefined

- **Section:** Frontmatter properties the planner consumes / Semantics rule 6 & 9
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** The Surface table says provenance 'enables PushFilterIntoTransparentFunction (filters can rewrite using the declared output→input column map)', but the spec never states what semantic relationship a provenance entry asserts. If `out` is computed (e.g. `UPPER(name) AS out`, provenance `out: [name]` — which passes rule 6's validation), rewriting `WHERE out = 'X'` into a predicate on `name` is unsound. The rewrite is only sound for identity/pass-through columns, and the spec never restricts it. Rule 8 claims cardinality is 'the only known soundness gap', which this contradicts.
- **Suggested fix:** Define what provenance asserts (lineage vs identity). State the pushdown precondition normatively: the rule may rewrite a predicate on output_col only when the declared mapping is a single-column identity pass-through (or define the substitution semantics precisely).

#### C13 — `python_models.md` — Circularity trigger condition, read literally, flags every Python model

- **Section:** Circular dependency detection
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** The rule says an error fires when 'a Python model's output would include itself in the project context passed to it in a subsequent round'. But §Iterative evaluation states the round-N context includes 'all Python-derived models from previous evaluation rounds' — so every Python model is included in its own subsequent-round context unconditionally. The intended condition (the model's recorded find_models filters would match the model itself) appears only in a parenthetical. It is also unspecified whether this error fires before or after convergence: a self-matching model can stabilize by round 3, so the two rules conflict.
- **Suggested fix:** Restate the trigger precisely: 'if any recorded find_models(...) call's filters match the calling model itself (by tag/directory), report a circular meta-dependency error'. State explicitly that this check runs per round before the convergence check, and whether an unfiltered find_models() (matches everything, including self) is an error.

#### C14 — `schema_evolution.md` — DECIMAL widening rule permits data-losing changes

- **Section:** Safe scalar type widenings
- **Dimension:** solution-quality · **Implication:** `implementation-impact`
- **Finding:** The rule "`DECIMAL(p,s)` → `DECIMAL(p2,s2)` where p2 ≥ p and s2 ≥ s" is unsound. Counterexample: DECIMAL(10,2) → DECIMAL(10,5) satisfies it (10≥10, 5≥2) but integer-digit capacity shrinks from 8 to 5, so a stored value like 123456.78 overflows on cast. The spec's own definition of safe widening — "cannot cause data loss" — is violated by a change the table classifies Safe and executes via ALTER TABLE without any flag.
- **Suggested fix:** Change the condition to: p2 − s2 ≥ p − s AND s2 ≥ s (integer-digit capacity must not shrink, scale may only grow).
- **Orchestrator spot-check:** Confirmed by counterexample: `DECIMAL(10,2)→DECIMAL(10,5)` satisfies `p2≥p ∧ s2≥s` but integer capacity drops 8→5 digits; `123456.78` overflows. Proposed fix `p2−s2 ≥ p−s ∧ s2≥s` is correct.

### `architecture.md`

- **"Hardcoded `functions/` directory" discovery contradicts "file kind is grammar, not location"** — _Workspace loading parity rule (CLI ↔ LSP)_ · correctness-consistency · `design-decision-needed`  
  §Resolution asserts "`random/x.sql` declaring `smelt.define helper(...)` is callable as `smelt.random.helper(...)`" — functions can live anywhere. The parity rule says function discovery covers "function definitions under the hardcoded `functions/` directory" (plus models under `config.paths`). Under those discovery rules `random/x.sql` is never scanned; and if `random` were added to `paths:`, prefix-stripping would yield `smelt.helper`, not `smelt.random.helper`. No configuration described in the spec produces the example's address. The scan universe (everything under root vs. scan roots only) is left to guesswork.  
  _Fix:_ Define the scan universe normatively: which directories are scanned for each kind, and how a non-`paths:` directory like `random/` gets discovered and addressed without stripping. Reword the parity-rule sentence to match (or mark the `random/x.sql` example as requiring specific config).
- **Layer-2 `name:` "ignored" contradicts the never-silently-ignored frontmatter contract** — _Two-layer multi-model file format_ · correctness-consistency · `spec-edit-only`  
  "A `name:` key inside Layer 2 frontmatter is **ignored**" contradicts the Unified frontmatter rule: an inapplicable-but-known key is "a **Warning** … never silently ignored", "A block is **never silently discarded**", and Constraint 11 (fail-loud). A user who writes frontmatter `name:` believes they named the model; silence is exactly the bug class the contract forbids. Compounding it, the Resolution table row "`models/marts/file.sql` containing `name: customers`" doesn't say whether that `name:` is a Layer-1 delimiter or Layer-2 frontmatter — under the ignored-rule the latter reading makes the row wrong.  
  _Fix:_ Specify that Layer-2 `name:` emits the inapplicable-key Warning (and takes no effect). Rewrite the table row to show the Layer-1 delimiter form explicitly (`--- name: customers ---`).
- **Stem-based directory uniqueness rule conflicts with the address-based one-path-one-entity rule** — _Resolution: `smelt.<path>` is the universal addressing scheme_ · correctness-consistency · `design-decision-needed`  
  "Names must be unique within a directory across all kinds — a `data/users.csv` and `data/users.sql` is a workspace-load error" is a file-stem rule. But for a multi-model `data/users.sql` "the filename ceases to register as a model name and becomes purely a container", and for a function-only file "the filename stem is not a path component" — in both cases no address collides with `smelt.data.users`, so the address-based rule ("one path → one entity", `project_address_collisions`) says no error while the stem rule says error. Implementers will pick different behaviours.  
  _Fix:_ Either make address collision the single normative rule and delete the stem sentence, or state the stem rule as deliberate conservatism applying even when the stem registers no address — and say which diagnostic fires.
- **Generator-file addresses include the file stem; static multi-model files do not — refactor churns every callsite** — _Generator files (`generates: models`)_ · solution-quality · `design-decision-needed`  
  Generator emissions are addressed "`<dir_with_dots>.<file_stem>.<modeldef.name>`", but in a static multi-model file "the filename ceases to register… The model's full path is the directory path joined with the leaf name" (no stem). Converting N hand-written sibling models into a generator — the natural meta-language refactor — therefore renames every model (`smelt.marts.x` → `smelt.marts.file.x`), contradicting the Design rationale that uniform addressing exists so refactors "churn every callsite" no more. No rationale for the asymmetry is given, so a second implementer might "fix" it.  
  _Fix:_ Either align generator addressing with multi-model files (stem is a pure container; collisions caught by `DuplicateAddress`), or add a Design paragraph justifying the extra namespace level (e.g. collision containment for dynamic counts).

### `cli.md`

- **Canonical-display round-trip contradicts the no-prefix argument rule** — _Argument resolution and `--scope`_ · correctness-consistency · `design-decision-needed`  
  The Canonical-display rule says output "uses the full canonical `smelt.<path>` form" and "Copy-pasting any printed identifier back into a `--select` ... or into another command must produce the same resolution." But the same section says "The argument never carries the leading `smelt.` prefix — that prefix is implicit at the CLI surface." A printed `smelt.silver.events_parsed` pasted into a command carries the prefix arguments "never carry"; an implementer reading the latter as a rejection rule breaks the round-trip invariant, and Constraint 10 inherits the contradiction.  
  _Fix:_ Pick one: (a) state that entity arguments accept and strip a leading `smelt.` prefix, or (b) define printed identifiers as prefix-less full paths and reword the Canonical-display rule. Update Constraint 10 to match.
- **Silent scope fall-through reintroduces the shadowing hazard the Design section claims to exclude** — _Argument resolution and `--scope`_ · solution-quality · `design-decision-needed`  
  "Scope expansion fall-through is silent: if `<scope>.<arg>` resolves, use it; otherwise try `<arg>`." Design justifies the no-scope hard error with "adding a second `bronze.events_parsed` later will never change the behaviour of a passing command." But with scope `silver` active and only top-level `events_parsed` existing, the command resolves via fall-through; later adding `silver/events_parsed.sql` silently retargets the identical command to a different entity. The fall-through violates the spec's own stability principle in the most common (cwd-scoped) case.  
  _Fix:_ Either drop the fall-through (scoped shorthand resolves only `<scope>.<arg>`; full path required otherwise), or mandate a notice/warning naming the resolved path whenever fall-through occurs, and reconcile the Design paragraph.
- **Selector expansion rule does not cover graph operators and cites a selector method model_selection.md does not define** — _Argument resolution algorithm_ · correctness-consistency · `implementation-impact`  
  "Selectors that already contain a `:` (selector grammar such as `tag:revenue`, `path:models/silver`) are passed through unchanged — they are not entity identifiers." model_selection.md's grammar is `['+'] method ['+']` with methods `model_name | tag: | generator_file:` — so `+events_parsed` / `events_parsed+` contain no `:` and would be fed through `resolve_ref_path` as literal entity names, which cannot resolve. Also `path:models/silver` names a method absent from model_selection.md's grammar, so the example contradicts the related spec.  
  _Fix:_ Specify that leading/trailing `+` operators are stripped before entity resolution and re-attached to the resolved full path. Replace the `path:` example with a method model_selection.md actually defines, or add `path:` there.
- **Unresolvable selector: hard 'not found' error vs graceful 'no models matched' no-op — both are mandated** — _No-op rebuild output_ · correctness-consistency · `implementation-impact`  
  §Argument resolution algorithm step 4 mandates a "not found" diagnostic (with did-you-mean) when no candidate resolves, and says `--select` values "are expanded through the same algorithm." §No-op rebuild output instead mandates a stderr line "smelt: no models matched the selector(s)" — implying a successful no-op. For `--select typo_name` the two sections require different behaviour (non-zero error vs quiet success). The exit code for an empty selection is never stated either.  
  _Fix:_ State that an entity-name selector that resolves to nothing is a hard error (consistent with the ambiguity-safety design); reserve the no-op stderr message for valid selectors whose result set is empty, and specify its exit code (presumably 0).
- **Exit-code table lets config errors collide with code 1, undermining the `smelt diff` CI-gate claim** — _Exit codes_ · solution-quality · `design-decision-needed`  
  The table defines `1` = "Execution failure ... or schema diff detected changes" and a separate row "Non-zero | Configuration error, missing smelt.yml, selector parse error..." — but 1 is non-zero, so a conforming implementation may exit 1 for config errors. The spec then says diff's exit-1-on-change "makes it suitable as a CI gate", yet a gate cannot distinguish "changes found" from "broken config". Known Divergences acknowledges the gap, but the normative table itself permits the collision rather than reserving a code.  
  _Fix:_ Reserve a distinct code (e.g. `2`) for usage/configuration errors in the normative table; keep "implementation does not yet emit it consistently" in Known Divergences.
- **Lifecycle normatively hardcodes DuckDB DDL, including materialized_view as CREATE OR REPLACE TABLE** — _`smelt build` lifecycle_ · solution-quality · `spec-edit-only`  
  Step 4 mandates "`CREATE TABLE <schema>.<name> AS SELECT * FROM read_csv_auto('<path>')`" and step 6 "`table` / `materialized_view`: `CREATE OR REPLACE TABLE`". `read_csv_auto` exists only on DuckDB, yet smelt is multi-backend (`smelt seed` loads "into the target database", which may be Databricks) — a Spark implementer has no guidance. Materializing `materialized_view` as a plain TABLE contradicts the mode's name and duplicates models.md's ownership of materialization modes, inviting drift between the two specs.  
  _Fix:_ Describe steps 4 and 6 behaviourally ("load the CSV into a table with inferred schema"; "materialize per models.md §materialization modes") and delegate per-backend DDL to models.md / a seeds spec / a backend capability matrix.

### `cumulative_aggregate.md`

- **Merged-partition detection mechanism is unspecified** — _Semantics — Reprocessing semantics_ · solution-quality · `design-decision-needed`  
  "The rule rejects reprocessing at planning time when it can detect it (the partition has been merged before...)" — but the output table has no partition_column, so the table itself cannot reveal which partitions were merged. Refusing reprocessing, resuming after partial failure, and the §--auto staleness analysis all require a persistent merge-history ledger whose location, format, and lifecycle (e.g. behaviour after --full-refresh, after manual truncation) are nowhere defined. The hedge "when it can detect it" invites divergent implementations, including one with no detection at all — making Constraint 9 vacuous.  
  _Fix:_ Specify the merge-history state: where it is stored (state table / metadata), what it records (partition ids per model), and how --full-refresh and CTAS bootstrap reset it. Or explicitly scope detection to a named mechanism and state the undetectable cases.
- **Partial-progress recovery contradicts the reprocessing refusal** — _Semantics — Execution model_ · correctness-consistency · `design-decision-needed`  
  Execution model: "Earlier committed partitions do not roll back on a later failure — partial progress is intentional". But Constraint 9 / §Reprocessing semantics reject any run window that "overlaps already-merged source partitions". After a mid-run failure (D₁–D₃ merged, D₄ failed), re-running the same `[run_start, run_end)` overlaps D₁–D₃ and is rejected — the natural recovery action is refused. The spec never says whether the step loop skips already-merged partitions or rejects the whole window; two implementers will diverge.  
  _Fix:_ Decide and state: either the step loop skips partitions already recorded as merged (making same-window re-runs the supported resume path), or the window is rejected and the user must re-run from the first unmerged partition. Update Constraint 9 to match.
- **Combiner examples ignore NULL semantics, breaking the equivalence contract** — _Semantics — Execution model_ · solution-quality · `implementation-impact`  
  The merge step combines "target's value ... with delta's value via the cross-partition combiner (`target.event_count + delta.event_count`, `LEAST(target.first_seen, delta.first_seen)` ...)". Per-partition `SUM(x)`/`MIN(x)` is NULL when a key's inputs are all NULL in that partition; `target + delta` then propagates NULL into the accumulated state, whereas full refresh ignores NULLs — violating §Cross-partition equivalence. LEAST/GREATEST NULL behaviour also differs across backends, undermining multi-backend portability.  
  _Fix:_ Specify NULL-aware combine semantics normatively: combiners must treat a NULL delta (or NULL target) as the identity element, e.g. COALESCE-wrapped addition and NULL-ignoring LEAST/GREATEST, and require backends' merge_into to honour this regardless of native function semantics.
- **v1 staleness answer for reversible aggregators is unactionable under the reprocessing refusal** — _Semantics — Interaction with `--auto` / staleness_ · correctness-consistency · `spec-edit-only`  
  "v1 returns 'any partition ≥ the earliest stale partition' for safety" — but those partitions were already merged, so running them is reprocessing, which §Reprocessing semantics refuses; the only executable v1 remedy is --full-refresh, exactly as for the irreversible branch. The reversible/irreversible distinction this section draws collapses in v1, and an implementer following it would emit a staleness plan the rule itself then rejects.  
  _Fix:_ State that in v1 both branches resolve to "force a full refresh when any already-merged partition is stale"; keep the reversible/irreversible distinction only as the future delta-history behaviour (Known Divergences).
- **Equivalence contract silently assumes immutable lookup sources** — _Semantics — Cross-partition equivalence_ · solution-quality · `spec-edit-only`  
  `cumulative_aggregate_run(model, π(S)) == full_refresh(model, source.where(partition_col ∈ S))` only holds if non-driving sources are frozen: lookups are "read in full on every partition step", so each delta is joined against the lookup state at merge time, while full_refresh joins everything against the current state. A lookup row changing between partition steps (or between runs) bakes stale joins into the accumulated state with no detection and no remediation short of full refresh. The contract as stated is unsound without this caveat.  
  _Fix:_ Add a normative caveat to §Cross-partition equivalence: the contract holds only when non-driving sources are unchanged across the processed partition steps; lookup mutation requires --full-refresh. Consider listing it under Known Divergences as a staleness-detection gap.

### `data_catalog.md`

- **Contradiction: missing lineage is 'omitted' (Semantics) vs source.type = "unknown" (Constraint 5)** — _Constraints & Invariants_ · correctness-consistency · `spec-edit-only`  
  Semantics §"Column description sources" says type inference supplies "`data_type`, `nullable`, `expression`, and `source`" and "If type inference cannot determine a field, that field is omitted." Constraint 5 says "If the type inference system cannot determine lineage, `source.type` is `\"unknown\"`." Design hedges with "degrades gracefully (omitted or `unknown`)". An implementer cannot tell whether an undeterminable column emits no `source` key or `{"type": "unknown"}` — JSON consumers will see different shapes depending on which sentence is followed.  
  _Fix:_ Pick one: state that `source` is always present, with `type: "unknown"` as the fallback (matching the enum that already includes `unknown`), and amend Semantics so the omit-if-undetermined rule covers only `data_type`, `nullable`, `expression`. Fix the Design hedge accordingly.
- **Model `path` is "workspace-relative" in Wide-reflection visibility but "<absolute path>" in the JSON schema** — _Wide-reflection visibility_ · correctness-consistency · `design-decision-needed`  
  The wide-reflection section claims the accessors "observe the same model and source identities that the catalog renders: workspace-relative `path`, short `name`, and merged `tags`", yet the JSON catalog schema declares `"path": "<absolute path>"`. These cannot both be "the same" identity. Additionally, absolute paths in `catalog.json` embed machine-specific directories, breaking the Design goal of JSON as "the integration format for programmatic consumers" — the artifact is non-portable and non-reproducible across CI machines.  
  _Fix:_ Decide on one representation — workspace-relative is the portable choice and matches `origin.generator_file` ("<workspace-relative path>") — and update the JSON schema comment and/or the wide-reflection sentence to agree.
- **Stale output files: 'overwritten' is specified but deletion is not** — _Output directories_ · solution-quality · `design-decision-needed`  
  "All output files are written fresh on each invocation — previous output is overwritten." Overwriting is not removal: a model deleted or renamed since the last run leaves a stale `models/<old>.md` that `index.md` no longer links; a `--select` run leaves pages of unselected models from a previous full run; switching `--format` leaves the other format's files behind. Constraint 1 ("regenerated in full") implies a clean artifact but never mandates clearing. Two implementers will diverge (rm-then-write vs write-in-place), and consumers deploying `<output>` as a static site will serve stale pages.  
  _Fix:_ Specify whether `<output>/models/` (or the whole `<output>` dir) is cleared before generation, and whether that is safe given users may place other files there. State the rule in both §Output directories and Constraint 1.
- **Partial-catalog semantics under --select are unspecified (dangling deps, model_count, tag index)** — _`--select` and test models_ · solution-quality · `design-decision-needed`  
  "When `--select` is specified, only selected models appear in the output." Unanswered: do a selected model's `upstream`/`downstream` arrays (and markdown dependency links) still name excluded models — producing dangling JSON references and broken links — or are they filtered? Does `project.model_count` count selected models or all? Is `tag_index` restricted to selected models? Design even promises "consumers can traverse the catalog recursively to compute transitive graphs", which is impossible on a partial catalog with dangling edges. Implementations will diverge on every one of these.  
  _Fix:_ Specify: upstream/downstream entries always reflect the true graph but links to non-rendered models are rendered unlinked (or entries are kept as names in JSON); `model_count` and `tag_index` cover only rendered models; note the recursive-traversal claim holds only for unselected runs.

### `datagen.md`

- **Date/timestamp generators emit strings, defeating the stated Parquet-over-CSV rationale** — _Design > Parquet output, not CSV / Surface > Dates and timestamps_ · solution-quality · `design-decision-needed`  
  Design rejects CSV because "a `DATE` column round-trips through CSV as a `VARCHAR` unless the reader applies inference rules that may disagree with smelt's". But the Surface defines `date` as "output as `YYYY-MM-DD` string" and `timestamp` as "output as ISO 8601 string", and Partitioning says the partition column is "of type `DATE` string" (itself self-contradictory). So temporal columns land in Parquet as Utf8 and downstream models must cast strings anyway — exactly the fragility the rationale claims Parquet avoids.  
  _Fix:_ Decide: either emit native Parquet `DATE32`/`TIMESTAMP` for `date`/`timestamp` generators (and update Surface), or soften the Design rationale to claim type fidelity only for int/float/bool and acknowledge temporal columns ship as strings. Clarify "row-level column of type `DATE` string".
- **Seed hierarchy ambiguous: --seed vs per-dataset seeds, and dataset_seed derivation undefined** — _Semantics > Determinism_ · clarity · `design-decision-needed`  
  Two ambiguities. (a) "`--seed` CLI flag (overrides all)" vs the Surface help text "[default: from config, or 42]" — does `--seed` replace per-dataset `seed:` overrides or only the global seed? (b) Nothing defines how a dataset's effective seed is derived from the global seed when no per-dataset seed is given. If every dataset's stream is seeded with the bare global seed, two datasets with identical generator configs produce byte-identical output and all datasets share the entity-pool offset (`+1`) — cross-dataset correlation a second implementer would avoid by mixing in dataset index/name.  
  _Fix:_ State explicitly: (a) whether `--seed` displaces per-dataset seeds; (b) the formula for an un-overridden dataset's seed (e.g. `global_seed.wrapping_add(dataset_index)` or a hash of the dataset name), and that distinct datasets get distinct streams.
- **foreign_key bound adjustment specified only for scale_factor < 1** — _Surface > Scale factor_ · clarity · `spec-edit-only`  
  "When `scale_factor < 1`, `foreign_key` generators automatically adjust their upper bound to match the scaled dimension table size." Behaviour for `scale_factor > 1` is unstated: does the bound also grow to the scaled size (referencing new dimension rows), or stay at the unscaled `num_rows` (new rows never referenced, skewed distribution)? Also ambiguous whether the table-row entry "`[1, referenced_dataset_row_count]`" already means the effective (post-scale) count, which would make the `< 1` sentence redundant.  
  _Fix:_ Replace with: "`foreign_key` always draws in `[1, floor(referenced_num_rows × scale_factor)]` — the effective row count of the referenced dataset — for any scale_factor." Update the generator table to say "effective row count".
- **Remainder handling unspecified when num_rows is not divisible by days** — _Semantics > Partitioning_ · clarity · `spec-edit-only`  
  "`num_rows` total rows are distributed evenly across `days` partitions" — with `num_rows = 100`, `days = 7` (or any non-divisible pair, especially after `floor(num_rows × scale_factor)`), the per-partition counts are undefined. Implementers could floor-per-partition and drop rows, give the remainder to the first/last partitions, or round-robin. Because the spec elsewhere pins byte-level determinism, exact per-partition row counts are load-bearing and must be normative.  
  _Fix:_ Pin the rule, e.g.: "partition i (0-based) receives `floor(N/days)` rows, plus one extra row for `i < N mod days`; total always equals the effective row count."
- **Unclear whether the partition column is materialized inside data.parquet or only in the directory path** — _Semantics > Partitioning / Surface > Output format_ · clarity · `spec-edit-only`  
  "The partition column is a row-level column of type `DATE` string" suggests it appears in the file's schema, but Hive-style layouts conventionally encode the partition key only in the path (`<col>=<value>/`), and readers with hive_partitioning reconstruct it — duplicating it in the file can conflict or double the column. Two implementers would produce different Parquet schemas, and downstream model column lists differ accordingly.  
  _Fix:_ State explicitly: "the partition column IS (or IS NOT) written into each `data.parquet`; readers must enable hive partitioning to recover it" — pick one and note the expected downstream schema.
- **Entity pools underspecified: scale-factor interaction, selection stream, column-name collisions** — _Semantics > Entity pools_ · solution-quality · `design-decision-needed`  
  "pre-generates a pool of `floor(num_rows × pool_ratio)` entities. Each row randomly selects one entity" leaves three gaps. (a) Is `num_rows` here pre- or post-`scale_factor`? Constraint 6 answers this explicitly for `linked_pools` (not scaled) but is silent for entity pools — if unscaled, scaling down changes the rows-per-entity ratio and cardinality realism. (b) Selection distribution/RNG stream is unstated (uniform? row stream? interaction with `day_seeds`?), unlike the precise `linked_choice` row-time sampling rules. (c) Behaviour on a name collision between `entity.columns` and `columns` is undefined.  
  _Fix:_ Mirror the `linked_choice` treatment: state whether the entity pool size uses effective (scaled) rows, that selection is uniform from the per-row/per-partition stream, and that duplicate column names across entity/row columns are a configuration error.

### `diagnostics.md`

- **DecimalPrecisionOverflow trigger omits UNION coercion, contradicting types.md** — _Types_ · correctness-consistency · `spec-edit-only`  
  The catalogue trigger says "A decimal arithmetic expression (`+`, `-`, `*`, `%`) produces a result whose precision exceeds the 38-digit portable maximum." The owning spec types.md says the code is "emitted when a decimal arithmetic expression **or UNION coercion** computes a result precision p' > 38" and specifies a UNION-keyword anchor. An implementer working from the catalogue would not emit on UNION coercion; the two normative texts contradict.  
  _Fix:_ Extend the trigger to "…or a UNION set-operation coercion produces a result precision exceeding 38"; optionally note the dual anchor (operator token / UNION keyword) to match types.md.
- **ColumnTypeUnresolved absent from catalogue though types.md lists it as an emitted code; "None currently open" is wrong** — _Known divergences_ · correctness-consistency · `spec-edit-only`  
  types.md (Surface, line 95 and the Unknown-reason table) presents `ColumnTypeUnresolved` as part of the diagnostic surface ("Yes, at the origin (TypeMismatch, ColumnTypeUnresolved, …)"), and function_schema_inference.md records it as "reserved and not yet minted". diagnostics.md — the canonical catalogue — never mentions it and states "Known divergences: None currently open." The coverage gate (enum → catalogue) cannot catch a reserved-but-unminted code, so the catalogue silently disagrees with two sibling specs.  
  _Fix:_ Add a Known Divergences entry: `ColumnTypeUnresolved` is reserved by function_schema_inference.md / types.md but not yet minted in the enum; or add a "Reserved codes" subsection in the catalogue.
- **UndefinedModelRef vs UndefinedSource: overlapping triggers for a failed bare smelt.<path>** — _Models & core analysis_ · clarity · `spec-edit-only`  
  Both triggers claim the same syntax: `UndefinedModelRef` fires when "a `smelt.ref()` or `smelt.<path>` call resolves to a model that does not exist" and `UndefinedSource` when "a `smelt.source()` or `smelt.<path>` call resolves to a source that does not exist." A bare `smelt.<path>` that fails to resolve cannot be known to be a model vs a source, and "resolves to … that does not exist" is self-contradictory wording. Two implementers would pick different codes (or invent a third behaviour) for the unresolvable-path case.  
  _Fix:_ State the tie-break rule explicitly, e.g. "an unresolvable bare `smelt.<path>` emits `UndefinedModelRef` unless the path prefix is under a declared sources namespace", and reword "resolves to X that does not exist" as "fails to resolve to any X".
- **BackendsWideningNotAllowed overloads an unrelated malformed-frontmatter condition that collides with FrontmatterParseError** — _Functions & expansion_ · correctness-consistency · `design-decision-needed`  
  `BackendsWideningNotAllowed` triggers when "a `smelt.define`'s `backends:` set is broader than what the body implies, **or the frontmatter itself is malformed**." The same table has `FrontmatterParseError` for frontmatter that "could not be parsed (Error) or contained an unknown key/malformed sub-entry (Warning)." Which code fires for a malformed `smelt.define` frontmatter is ambiguous, and packing an unrelated structural condition into a widening-specific code defeats the stated purpose of codes ("code-action lookups and stable cross-references").  
  _Fix:_ Drop the "or the frontmatter itself is malformed" clause (route those cases to `FrontmatterParseError`), or define a precise partition: parse failure → FrontmatterParseError; well-formed but semantically invalid `backends:` → BackendsWideningNotAllowed.

  Surface defines Code only as "a `DiagnosticCode` variant (enables code-action lookups and stable cross-references)" — a Rust enum identity. The spec never says what string the user sees in CLI output or in the LSP `Diagnostic.code` field (PascalCase variant name? kebab-case? numeric?), nor whether codes are renameable. For "stable cross-references" to mean anything in production (suppression comments, CI baselines, docs links), the serialized form and its stability guarantee must be specified; otherwise a variant rename silently breaks downstream tooling.  
  _Fix:_ Specify the wire/display form (e.g. "the variant name verbatim, rendered in CLI output and as LSP `Diagnostic.code`") and a stability rule (codes are append-only; renames are breaking and require a Known Divergences entry).

### `expansion.md`

- **Invariant 6 ("calls remain symbolic through Level-1") contradicts planner_integration.md's L1 rule list** — _Constraints & Invariants_ · correctness-consistency · `design-decision-needed`  
  Invariant 6 states "Codegen-time expansion is lazy. Calls remain symbolic through Level-1 planning and materialise at Level-2", and Semantics says codegen expansion is "Performed at the planner's Level-2 strategy lowering". But planner_integration.md (a named Related spec) lists `ExpandTransparentFunctionCalls` and `PushFilterIntoTransparentFunction` as **L1** logical-to-logical rules. One spec is wrong about which planner level expands transparent calls; an implementer following expansion.md would refuse to expand at L1, breaking the rules the planner spec documents.  
  _Fix:_ Decide whether transparent-call expansion is an L1 logical rewrite or an L2 lowering step (or both, with distinct names), then align invariant 6, the Semantics "Codegen-time expansion" paragraph, and planner_integration.md's level table.
- **Caller(span) has no file identity; tag rewriting under nested expansion is unspecified** — _Provenance origin tags_ · solution-quality · `design-decision-needed`  
  `Caller(span)` carries only a span, unlike `Callee(fn_id, span)`. Under nested codegen expansion (B expanded into A's body, A then expanded into model M), a node tagged `Caller(span)` during the inner expansion points into A's file, but after the outer expansion that node is callee (A) material. The spec only says tags "must propagate through every subsequent CST transformation" — propagating the stale `Caller` tag mislabels the node and leaves its span unresolvable (no file id). No rule says whether outer expansions re-tag inner `Caller` tags.  
  _Fix:_ Either give `Caller` a file/owner identifier, or add a normative rule: when an already-tagged subtree is spliced by an outer expansion, existing tags are preserved verbatim and `Caller` is defined relative to the outermost model file (with the re-tagging rule for intermediate bodies spelled out).
- **Invariant 5 references `param_bindings`/`frame_bindings` fields that do not exist in the FrameInfo shape** — _Frame-stack invariants_ · correctness-consistency · `implementation-impact`  
  Invariant 5 says "When a single frame's `param_bindings` contains multiple bindings (e.g. several parameters bound at the same call), the producer chooses an order — currently the parameter-declaration order via `frame_bindings.first()`". But §FrameInfo defines scalar `param` and `bound_type` fields — one binding per frame. The spec contradicts itself on whether a frame carries one binding or many, and `frame_bindings.first()` suggests all but the first binding are dropped, which contradicts "chooses an order". A second implementer would design a different struct.  
  _Fix:_ Either change the FrameInfo table to `param_bindings: Vec<(name, type)>` with the ordering rule, or rewrite invariant 5 to say a multi-parameter call produces one frame carrying only the binding relevant to the error (or the first declared parameter), and delete the phantom field names.
- **`column_origin: Option<TextRange>` carries no file path, so the promised `<file>:<line>` trailer is unconstructible** — _Surface — `FrameInfo` shape (`column_origin`)_ · solution-quality · `implementation-impact`  
  `column_origin` is "an optional `column_origin: Option<TextRange>` field carrying the source span of the column's declaration in the upstream `ModelSchema`" — a bare range with no file identity, while the sibling extensions `ModelOrigin`/`SourceOrigin` both bundle `path: String` plus a span. The upstream schema lives in a different file from the diagnostic, and Known Divergences promises a renderer trailer "(column declared at <file>:<line>)" which cannot be rendered from a `TextRange` alone.  
  _Fix:_ Define a `ColumnOrigin { path: String, span: Option<TextRange> }` shape mirroring `ModelOrigin`/`SourceOrigin`, or state explicitly how the renderer recovers the declaring file (e.g. via a model id field).
- **Generator-frame stamping scope contradicts invariant 4 and the Surface description** — _Surface — `<generator>` frame for multi-model production_ · correctness-consistency · `spec-edit-only`  
  Surface says the frame is carried by "Diagnostics that surface from inside the generator body's HOF chain"; Known Divergences says it is "stamped on every body-evaluation diagnostic (whether or not it already carries inner HOF anonymous frames)". A top-level body-evaluation diagnostic involves no expansion in either of the spec's "two senses", so stamping it violates invariant 4 ("A diagnostic that did not arise from an expansion carries no ExpansionFrames payload") as written. Implementers can legitimately read invariant 4 as forbidding the frame on non-HOF generator diagnostics.  
  _Fix:_ In Semantics, define generator-body evaluation as a third expansion sense (or amend invariant 4 to name it), and make Surface and Known Divergences agree that every body-evaluation diagnostic — not only HOF-chain ones — carries the `<generator>` frame.
- **`Synthesized(fn_id, reason)` is underspecified for nodes synthesized outside any function expansion** — _Provenance origin tags_ · clarity · `implementation-impact`  
  The tag is defined as `Synthesized(fn_id, reason)` and "A planner rule that produces a new CST node must label it `Synthesized`". But planner "strategy injection" (named as a synthesis source) can create nodes in a plain model with no function in scope — there is no `fn_id` to supply. Relatedly, invariant 2 scopes the no-untagged-nodes rule to "every CST node produced by expansion", yet the planner-rule obligation applies to all rewrites, leaving unclear whether mixed tagged/untagged trees on never-expanded models are legal.  
  _Fix:_ Make `fn_id` optional in `Synthesized` (or define a model-level owner id), and state explicitly that nodes of never-expanded CSTs are untagged and that `Synthesized` tags may coexist with untagged neighbours there.
- **Timing of the CTE-collision diagnostic is ambiguous (type-check vs build/codegen)** — _Hygiene v1_ · clarity · `implementation-impact`  
  Surface and Hygiene rule 3 both say the diagnostic fires "at codegen time" ("When a function body declares a CTE whose name would collide with a CTE in the caller's scope at codegen time, the compiler emits a collision diagnostic"). Read literally, the check runs only during `smelt build` and is invisible to the LSP — at odds with the project's LSP-first diagnostics pipeline and with Known Divergences, which describes `CteShadowsCallerCte` firing on a model/function pair with no timing qualifier. Implementers could put detection in the planner or in `file_diagnostics` and both claim conformance.  
  _Fix:_ State explicitly whether the collision check runs during diagnostic collection (LSP-visible, since caller scope is known at Tier 1 expansion / call-site analysis) or only at codegen, and rephrase "at codegen time" to qualify when the collision *manifests*, not when it is detected.

### `function_schema_inference.md`

- **Known-Divergences claim of 'no trigger' for ColumnTypeUnresolved contradicts Semantics 3+6** — _Known Divergences / Open Questions_ · correctness-consistency · `implementation-impact`  
  Semantics 3 says "with multiple `TableExpr` parameters a bare `*` is `Unresolved`"; Semantics 6 and Constraint 4 then mandate a `ColumnTypeUnresolved` diagnostic at origin for every `Unresolved` column. But Known Divergences asserts "The one remaining way a function contributes an `Unknown` column is a *malformed* signature" and "`ColumnTypeUnresolved` therefore has no trigger today." The multi-param bare-`*` case is a well-formed-signature trigger the note denies — so today it is a silent Unknown, violating Constraint 4 ("No silent `Unknown`").  
  _Fix:_ Either mint `ColumnTypeUnresolved` for the multi-TableExpr bare-`*` case, or amend the divergence entry to acknowledge this case as a known silent-Unknown gap with a plan link, and drop the 'no trigger today' claim.
- **Return-resolution clauses overlap; Tier 2 is never addressed** — _Semantics — 1. Scalar returns_ · clarity · `spec-edit-only`  
  The rule lists "Tier 1 resolves by per-call-site expansion" and "`Expr<Any>` and unannotated returns resolve to `Unknown` with reason `Dynamic`" as parallel clauses. A Tier 1 function has an unannotated return, so both clauses apply with opposite outcomes (concrete expanded type vs Dynamic Unknown). A Tier 2 function (all params annotated, no return type — per gradual_typing.md's dispatch table) matches neither named tier clause; whether it gets body synthesis, expansion, or Dynamic Unknown is unstated. A second implementer could make every unannotated return Dynamic, discarding Tier 1 expansion results.  
  _Fix:_ Restate as an ordered dispatch: Tier 3 → declared type; Tier 2 → (synthesis or expansion, state which); Tier 1 → per-call-site expansion; only `Expr<Any>` (explicit) → Dynamic. Say explicitly which clause wins when several apply.
- **Row-tail `.*` divergence breaks Constraint 2 with no specified failure surface** — _Known Divergences / Open Questions_ · solution-quality · `design-decision-needed`  
  "A row-tail return contributes zero columns from the spread at the schema layer; the `.*` passes through to generated SQL verbatim" — the emitted SQL produces columns the `ModelSchema` does not record, which is exactly the schema/codegen divergence Constraint 2 forbids and the Design section calls a schema that "lie[s] about its own shape." The entry specifies no diagnostic or user-visible signal, so downstream consumers (schema diffs, catalog, column refs) silently see an incomplete schema — the failure mode the whole spec exists to prevent.  
  _Fix:_ Until unified, specify a loud interim behaviour: e.g. a diagnostic on `.*` over a row-tail return, or resolve the spread's tail columns to `Unknown(Unresolved)` with `ColumnTypeUnresolved`, so the gap is visible rather than a silent wrong schema.
- **Bare-`*` expansion is keyed to TableExpr-parameter count, not the body's FROM scope** — _Semantics — 3. `TableExpr` returns in FROM_ · solution-quality · `implementation-impact`  
  "A bare `*` in the body expands against the sole `TableExpr` parameter when there is exactly one; with multiple `TableExpr` parameters a bare `*` is `Unresolved`." This ties `*` to the function's parameter list rather than the body's actual FROM scope. A body like `SELECT * FROM smelt.users` (param unused, or zero TableExpr params), or `SELECT * FROM source JOIN smelt.dim ...`, is unhandled or mis-resolved by the rule as written — standard SQL expands `*` against the FROM scope. Implementers will diverge between parameter-count logic and FROM-scope logic.  
  _Fix:_ Define bare `*` as expanding against the body's FROM-scope schema (per scoping.md), seeded with each TableExpr argument's resolved schema; reserve `Unresolved` for FROM entries whose schema cannot be resolved, not for parameter multiplicity per se.
- **Spread misuse and column-name collisions have no specified behaviour** — _Semantics — 2. Struct returns and `.*` spread_ · solution-quality · `design-decision-needed`  
  Two failure modes a second implementer must guess: (a) `.*` applied to a non-struct return (`Expr<Double>`) — the Surface section disclaims other codes ("argument-shape and row-requirement errors are owned by gradual_typing.md / types.md") but the delegated codes (ArgTypeMismatch, MissingArgument, RowRequirementUnsatisfied) do not cover spread misuse; (b) spread fields colliding with other SELECT items or a second spread (`a.*, f(x).*` both yielding `id`) — duplicate names in a `ModelSchema` poison schema diffs and the catalog, and backends disagree on legality.  
  _Fix:_ Specify a diagnostic (owned here or explicitly delegated by name) for `.*` on a non-struct/open return, and a normative rule for duplicate contributed column names (error, or last-wins with diagnostic).
- **Contributed column name for an unaliased scalar call is unspecified** — _Surface — Contributed columns by return shape_ · clarity · `design-decision-needed`  
  The table's only scalar call form is "`<name>(args) AS c` (SELECT scalar) … one column `c` of type `T`". An unaliased call `SELECT smelt.functions.add_margin(price) FROM ...` is legal SQL, and the contributed column's name is load-bearing (ModelSchema feeds schema_evolution diffs and the catalog), yet undefined. Backends auto-name expressions differently, so leaving it implicit hurts multi-backend portability and invites divergent implementations.  
  _Fix:_ Specify the name for the unaliased form (e.g. the function's bare name, or require an alias with a diagnostic when absent).

### `functions.md`

- **Workspace-wide single name namespace contradicts directory-derived call paths** — _Constraints & Invariants_ · correctness-consistency · `design-decision-needed`  
  Constraint 4: "`smelt.extern` and `smelt.define` share one workspace-wide name namespace with built-ins. A clash is a hard error"; `DuplicateFunctionDefinition` fires when two defines "share a name in the workspace". But Surface derives a define's identity from directory + name (`smelt.utils.safe_divide` vs `smelt.random.helper`), so two `helper`s in different directories have distinct, unambiguous call paths — yet are a hard error. Also, a define colliding with a built-in has no listed code (`ExternCollidesWithBuiltin` covers externs only), and defines are never called by bare name, so the collision is unmotivated. Known Divergences flags this as unconfirmed, yet Constraint 4 states it normatively.  
  _Fix:_ Decide: workspace-wide bare-name uniqueness for defines, or per-directory (per-call-path) uniqueness. If workspace-wide stands, state the rationale, name the define-vs-builtin diagnostic, and remove the hedging divergence; otherwise rewrite Constraint 4 and the DuplicateFunctionDefinition trigger.
- **Empty list-splice (`= ()`) only specifies comma elision; dangling clause keywords unaddressed** — _Semantics_ · solution-quality · `implementation-impact`  
  Rule 9: "Empty list-splice points elide adjacent commas at codegen (so `SELECT id, name, metrics` with `metrics = ()` becomes `SELECT id, name`)". Trace `smelt.define f(ord: OrderSpec = ()) AS (SELECT … ORDER BY ord)` with the default: comma elision leaves `ORDER BY` followed by nothing — invalid SQL on every backend. Same for an empty `SelectItems` that is the sole content of `GROUP BY`, or the entire SELECT list. The spec claims `= ()` is the "splice nothing" idiom but only defines half its codegen.  
  _Fix:_ Specify clause-level elision: when an empty splice leaves a clause (`ORDER BY`, `GROUP BY`, `PARTITION BY`) with zero items, the whole clause is dropped; an empty SELECT list is a compile error with a named diagnostic.
- **`-> Numeric` widening to Double at call sites is unsound without a CAST rule** — _Semantics_ · solution-quality · `design-decision-needed`  
  Rule 16: a return annotation "resolves to a specific concrete type … or to `Numeric` (which widens to `Double`)". A body returning `Integer` satisfies `Numeric` (no `ReturnTypeMismatch`), so the inferred schema says Double while the generated SQL yields an integer column — exactly the cross-backend schema drift Design §"CAST-enforced canonical return types" exists to prevent, but rule 6's CAST is specified only for built-ins. Also inconsistent treatment: `Ordered`/`Any` produce `Unknown`, `Numeric` silently widens; a second implementer could defensibly make `Numeric` produce `Unknown` too.  
  _Fix:_ Either require codegen to wrap `-> Numeric` calls in `CAST(... AS Double)` (extending rule 6 to user functions), or treat `Numeric` like other polymorphic constraints (`Unknown` at call site). State the choice and why.
- **"Externs declare no fragment-sort parameters" contradicts rule 8; AggExpr/WindowExpr on externs unaddressed** — _Semantics_ · correctness-consistency · `spec-edit-only`  
  Surface §PASSING says "externs declare no fragment-sort parameters", and rule 8 says extern parameters "must be non-fragment sorts — `Expr<T>` and `TableExpr` are accepted". But per types.md (which this spec cites for vocabulary), `Expr<T>` and `TableExpr` ARE fragment sorts; the spec is using "fragment sort" to mean only `SelectItems`/`OrderSpec`. Additionally, `AggExpr<T>` and `WindowExpr<T>` on an extern are neither accepted nor listed as triggering `ExternFragmentParamUnsupported` — implementers will guess differently.  
  _Fix:_ Replace "fragment sort" with a precise term (e.g. "list-valued splice sorts") in both places, and explicitly state whether `AggExpr`/`WindowExpr` extern parameters are accepted or rejected.
- **Argument-binding failure modes lack diagnostics** — _Diagnostic codes_ · solution-quality · `spec-edit-only`  
  The catalogue covers `MissingArgument`, `ArgTypeMismatch`, and `UnknownPassingParameter`, but not: an unknown named argument (`f(nonexistent => 1)`), the same parameter bound twice (two named args; positional + named; inline arg + `PASSING` clause for the same name — Design explicitly allows inline fragments "as a fallback", so the overlap is reachable), excess positional arguments, or named-argument use at a variadic position (the Surface rule "Named-argument syntax does not apply to variadic positions" has no enforcement code). Each gap invites an invented code or silent acceptance, violating fail-loud discipline.  
  _Fix:_ Add codes (e.g. `UnknownArgument`, `DuplicateArgumentBinding`, `TooManyArguments`) and a rule that a parameter may be bound by at most one of {positional, named, PASSING}.
- **`backends` key has two incompatible value shapes and an undefined default for externs** — _Function-declaration frontmatter_ · clarity · `spec-edit-only`  
  The table gives `backends` the shape "`all` (string) or list of backend names" with default "inferred from body" — but `smelt.extern` has no body, so the inferred set is undefined for externs (universal? empty?). Meanwhile the extern sugar expands to `backends: { duckdb: { emit: read_parquet } }`, a structured-map shape the `backends` row does not admit. Whether `backends: [duckdb]` and the map shape can coexist, and whether the map shape also narrows, is unspecified. Also unclear which of `BackendsWideningNotAllowed` ("frontmatter … malformed in this dimension") vs `FrontmatterParseError` fires for a malformed value.  
  _Fix:_ Define the full `backends` grammar in one row (scalar `all` | list | map of backend → `{emit}`), state the extern default explicitly (e.g. universal unless declared), and assign malformed-value cases to exactly one diagnostic.
- **as_struct capability gate against the default universal backend set makes any undeclared use an error** — _`smelt.as_struct(...)`_ · solution-quality · `design-decision-needed`  
  `AsStructUnsupportedBackend` fires when "the declared backend set includes a backend without struct-literal support." Per rule 7, a canonical body with no `backends:` frontmatter infers the universal set — which by assumption includes struct-less backends — so every `smelt.as_struct` use without explicit `backends:` narrowing errors. Contrast: a `duckdb.…` call narrows inference instead of erroring. Whether capability gates narrow (like backend-namespace calls) or error is a design fork two implementers would resolve oppositely. "Declared backend set" is also ambiguous when nothing is declared (inferred? resolved?).  
  _Fix:_ State whether `smelt.as_struct` contributes to backend inference (intersecting with struct-capable backends) or requires explicit `backends:` narrowing, and define the gate against the resolved (inferred ∩ declared) set.

### `gradual_typing.md`

- **Healthy-case call-site return type for Tier 2 is never specified** — _Tier 2 — isolated body check + call-site argument check_ · solution-quality · `design-decision-needed`  
  §LSP stability says the Tier 2 return "degrades to Unknown" under a broken body — implying a non-Unknown return when healthy — and the row-polymorphism paragraph says the row variable "propagates into the call's synthesised return type". But no rule states what a healthy Tier 2 call returns: the body's once-synthesised return propagated to callers, or Unknown. Propagation collides with the Design rationale against cross-boundary inference ("an unrelated body edit changes the inferred return … none of it is visible at the signature level"), which applies equally to Tier 2 body edits.  
  _Fix:_ Add an explicit rule to §Tier 2: state whether the isolated check's synthesised return (with row variables instantiated per call) is the call-expression type, and reconcile with the no-cross-boundary-inference rationale (e.g. scope that rationale to per-call-site instability).
- **"Tier escalation is non-breaking for callers" contradicted by Known Divergences** — _Tier dispatch is implicit_ · correctness-consistency · `spec-edit-only`  
  Surface states "Tier escalation is non-breaking for callers" and Design repeats "monotonic and non-breaking — adding annotations strictly improves diagnostics". Known Divergences admits the opposite: "Annotating a previously Tier 1 parameter with a type narrower than what some caller was passing will surface a new `ArgTypeMismatch` at that caller." With no implicit coercion, an annotation can introduce errors at call sites that previously type-checked (e.g. Integer passed where the new annotation says Double but the body worked under Integer). The unqualified normative claim is false.  
  _Fix:_ Qualify the Surface/Design claims: escalation preserves the error format and surface API, and is non-breaking only when annotations are at least as wide as every existing caller's usage; narrower annotations may surface new ArgTypeMismatch errors.
- **Tier 1 expansion under non-concrete (row-variable / abstract) bindings is unspecified** — _Tier 2 calling Tier 1 (research §16 #17)_ · solution-quality · `design-decision-needed`  
  When a Tier 2 body whose parameter is `TableExpr<{…, ..r}>` or bare `TableExpr` forwards that parameter into a Tier 1 helper, step 2's "checker collects argument types from the surrounding Tier 2 TypeContext" yields an abstract, row-variable-bearing type — but Tier 1 expansion is defined for concrete bindings ("concrete types in, concrete types out", FrameInfo carries "the rendered concrete bound type", and format guarantee 3 forbids row variables in messages). A second implementer would guess differently: reject, close the row, or carry the abstract type and risk leaking row variables.  
  _Fix:_ Specify the behaviour: e.g. the Tier 1 body is checked under the abstract row type with errors reporting only declared fields, or forwarding an open-row parameter into a Tier 1 callee is rejected with a named diagnostic. State how FrameInfo renders an abstract bound type.
- **Tier 1 broken-body caller behaviour is vague and misuses UnknownSmeltFn** — _LSP stability under broken bodies_ · clarity · `implementation-impact`  
  "Callers see `UnknownSmeltFn`-shaped degradation or a propagated body-error frame, depending on how far the parser got" is non-normative hand-waving in a Surface section. diagnostics.md defines `UnknownSmeltFn` as "a function name not registered in the workspace" — emitting it for an existing function with an unparseable body is misleading UX. Also "While a Tier 1 body fails to parse or type-check, calls to it cannot be checked" conflates parse failure (blocks expansion) with type-check failure, which for Tier 1 only exists per call site — the call was checked; that is how the error surfaced.  
  _Fix:_ Specify normatively: on parse failure, what diagnostic (if any) fires at each caller and what the call's type is (Unknown); on per-call-site type failure, state that the expansion ran, frames are attached, and the synthesised return degrades to Unknown.
- **Tier 3 body: "checking mode" contradicts "after body synthesises" / tail-anchored error** — _Tier 3 — isolated body check against declared return + call-site argument check_ · correctness-consistency · `spec-edit-only`  
  Semantics step 1 says "The body is walked in **checking mode** against the declared return type" then immediately "The body's synthesised type must match the declared return". The Surface table says `ReturnTypeMismatch` fires "after body synthesises", and Design says the mismatch "fires at the body's tail" (matching types.md §10's "checking target"). Full checking-mode pushdown would anchor errors at inner subexpressions (e.g. one CASE branch); synthesise-then-compare anchors at the tail. The two readings produce different primary spans, which is exactly the surface this spec guarantees.  
  _Fix:_ Pick one formulation: "the body synthesises bottom-up; the result is compared against the declared return at the body's tail, firing ReturnTypeMismatch there" — and remove the "walked in checking mode" phrasing (or define precisely how far the expected type pushes down).

### `incremental_models.md`

- **"Write-rebasing model" has no detection criterion; unclear which bounded models widen the write window** — _Execution model (DuckDB, current)_ · solution-quality · `design-decision-needed`  
  Step 1 first says "The write window is the run window widened by the model's derived lookback/lookforward bound" (i.e., always), then distinguishes "a model with no bound" from "a write-rebasing model". Nothing defines how the optimizer detects write-rebasing or derives its skew — `BoundResult` has no write-skew field, and neither Form A nor Form B expresses output-partition skew. A pure read-lookback model (`LAG ... RANGE BETWEEN INTERVAL '30 minutes' PRECEDING`, non-derived partition column) read literally would get a non-granularity-aligned write window `[run_start - 30min, ...)` whose boundary rows are recomputed with truncated input.

PRECEDING` frame" — exactly the sessionization shape (`PARTITION BY device_id`) the safety-check section would reject. An implementer of the safety check, following its own subsection, rejects the model the batch-safety section promises to admit.

But Design says "MERGE remains in the `IncrementalStrategy` enum (Surface §\"Strategy enum\") for backends that want to opt in", Constraint 3 says "the backend chooses `DeleteInsert` / `Merge` / etc.", and the scope callout plans "MERGE on Spark/Databricks". A reader cannot tell whether MERGE is a forthcoming incremental strategy or permanently the cumulative_aggregate primitive only.  
  _Fix:_ Pick one: either add `Merge` to the enum (with a note it is unused today) and soften "is not an incremental strategy", or remove the Merge mentions from Design, Constraint 3, and the scope callout's planned list.
- **Chunk-sizing rule undefined and unit-confused** — _First-run and backfill_ · clarity · `spec-edit-only`  
  `BoundedSafe(n)` chunking is specified only as "Auto-sized sub-ranges (the existing 3× context, clamped 7–90 partitions rule)". The rule is never defined here or pointed at; "the existing ... rule" is implementation-history vocabulary (timeless-oracle violation). Units are mixed: `n` "is rendered in the source's partition-column unit" while the clamp is in model partitions — for an hourly source feeding a daily model the computation is ambiguous. A second implementer cannot reproduce chunk sizes.

- **PerPartitionOnly execution semantics unspecified** — _Batch safety classification_ · solution-quality · `design-decision-needed`

For `PerPartitionOnly` (one or more `Unbounded` sources, "One partition at a time, sequential"), the spec never says what filter an Unbounded source receives (presumably `c < partition_end` with no lower bound — unstated), whether the outer clamp is per-partition, or what property makes "temporal order" load-bearing. A whole row of the execution table has no defined source-read semantics; implementers will guess differently.

Since the model's partition column is an output expression, not a queryable alias, it is unclear what SQL shapes Form B actually matches — a correlation against the model's own output cannot appear in a flat model body. Form B is the core derivation vocabulary; an ill-typed example invites divergent matchers.

What `backbuild` does that `run` does not is never stated, and "expand" suggests writing partitions outside the user-supplied `[start, end)`, which would contradict the run-window contract without explanation.

### `lsp.md`

- **Watched-file globs hard-code `models/` and `functions/` directory names that smelt_yml.md says are not semantic** — _Watched files_ · correctness-consistency · `implementation-impact`  
  The spec normatively watches "`**/models/**/*.py`" and "`**/functions/**/*.sql`". But `smelt_yml.md` defines a configurable `paths:` list (default `["models"]`) and states kind is determined by file content, not directory — a function (`smelt.define`) may live in any scanned directory (functions.md's own example uses `random/x.sql`). Per functions.md, the call path is derived from the declaring file's directory — `smelt.define helper` in `random/x.sql` is called as `smelt.random.helper(...)`, with no `functions.` segment. With scan root `sources`, stripping yields `smelt.raw.events`. sources.md's own table maps `models/sources/raw/users.yml` → `smelt.sources.raw.users`, so the file path in the comment is wrong. The seed comment (`seeds/my_seed.csv`) also silently assumes `seeds` is in `paths:` though the stated default is `["models"]`.  
  _Fix:_ Change the comment to `-- source at models/sources/raw/events.yml`, and annotate the seed example with the `paths:` assumption (e.g. `paths: ["models", "seeds"]`).
- **Multi-model grammar underspecified: scope of the `--- X ---` hard-error rule and optionality of section frontmatter** — _File format_ · clarity · `spec-edit-only`  
  "Any other `--- X ---` form is a hard parse error" has no stated scope: read literally, a SQL comment line `--- section header ---` anywhere in any file (single-model included, or inside a string literal) is a parse error. architecture.md §Resolution limits the bare-`--- ---` error to "a delimiter line in a multi-model file"; models.md states it broader. The spec also never says whether a section's Layer 2 frontmatter block (and its closing bare `---`) is optional — what does a section with no frontmatter look like? Two implementers will write different parsers.  
  _Fix:_ State where delimiter scanning applies (line-start, outside Layer 2 frontmatter, only in files containing at least one Layer 1 delimiter), and state explicitly that the per-section frontmatter block is optional, with an example section that is delimiter + bare SQL.
- **CTE naming and collision rules for inlined ephemerals are unspecified** — _Ephemeral inlining_ · solution-quality · `design-decision-needed`  
  "An `ephemeral` model's SQL is substituted as a CTE at each point a downstream model references it" — but the spec never says what the CTE is named. `smelt.staging.cleaned` contains dots (invalid as a bare CTE identifier); two ephemerals can share a leaf name (`staging.users`, `archive.users`) and both be referenced by one model; the downstream model may already define a CTE with the chosen name. An unpinned mangling scheme risks silently wrong SQL on collision, and transitive chains ("`a` gets both `b` and `c` as CTEs") compound it.  
  _Fix:_ Pin a deterministic CTE-name scheme derived from the full canonical address (e.g. path joined by `_` with a reserved prefix), and state that a collision with a user-written CTE name is a hard error or is avoided by the reserved prefix.
- **Materialization-change semantics don't cover transitions to non-materialized modes or say how the current type is known** — _Materialization change_ · solution-quality · `design-decision-needed`  
  "smelt drops the existing database object (whatever type it currently is) and creates the new one" only covers persisted→persisted transitions. `table` → `ephemeral`/`test` has no "new one" to create and ephemeral/test models produce no DDL (Constraints #2/#3) — is the stale object dropped or orphaned in the warehouse? The spec also doesn't say how smelt learns the current object type (catalog introspection vs stored state), and `cumulative_aggregate` ↔ `table` transitions involve stateful tables where a silent drop loses accumulated state.  
  _Fix:_ Specify: (a) detection mechanism (introspection or run-state); (b) transitions to ephemeral/test drop the stale object (or document the orphan); (c) transitions out of `cumulative_aggregate` drop+rebuild and the state-loss implication.
- **Misspelled column names in `columns:` are silently dropped, contradicting the spec's own fail-loud rationale** — _`columns:` — column metadata_ · solution-quality · `design-decision-needed`  
  "Columns named in `columns:` but absent from the inferred schema are silently dropped from catalog output." §Design argues the opposite doctrine for keys: "silently ignoring unknown keys hides configuration mistakes." A typo'd column name is the same class of mistake but worse in consequence: its `tests` (e.g. `not_null`) silently never run and its schema-evolution `default`/`backfill` silently never apply. The spec only defines the catalog's behavior; what testing and schema evolution do with an unknown column name is unstated.  
  _Fix:_ Emit a warning diagnostic (e.g. `ColumnMetadataUnknownColumn`) for any `columns:` key absent from the inferred schema; make it an error when the entry carries `tests`, `default`, or `backfill`.

### `planner_integration.md`

- **`deterministic` defined as byte-identical output is unachievable for SQL** — _Semantics rule 4 (Property semantics at execution)_ · solution-quality · `implementation-impact`  
  're-execution of the same input must produce byte-identical output (modulo non-canonical timestamp encodings)'. SQL bodies without ORDER BY have engine-dependent row order (parallel scans), so virtually no model can honestly declare `deterministic: true` under this definition — or implementers will silently weaken it. 'Non-canonical timestamp encodings' is also undefined. The planner's replay reasoning needs multiset-of-rows equality, not byte equality.  
  _Fix:_ Define determinism as 'same multiset of rows for the same inputs' (or specify a canonical ordering/serialisation if byte-level comparison is truly intended, e.g. for fingerprinting), and define or drop the timestamp-encoding carve-out.
- **L1 contract says 'same set of rows' — should be multiset** — _Semantics rule 3_ · correctness-consistency · `spec-edit-only`  
  'L1 rewrites must produce a logical plan that computes the same set of rows for any input.' SQL has bag semantics; 'set' licenses a duplicate-eliminating rewrite as correctness-preserving, which would change query results. Also the rule's heading says 'L2/L3 rules preserve equivalent output schema' while the body requires 'schema and contents' — the heading undersells the obligation.  
  _Fix:_ Change to 'the same multiset (bag) of rows' and retitle rule 3 to 'L2/L3 rules preserve output schema and contents'.
- **Diagnostic anchoring contradicts itself for the pushdown advisory** — _Diagnostic codes / Semantics rule 9_ · correctness-consistency · `spec-edit-only`  
  Surface §Diagnostic codes says all four codes are 'Anchored at the declaration's name range', but Semantics rule 9 says 'the planner emits MissingProvenancePushdownAdvisory at the WHERE clause range'. These cannot both hold; the advisory fires at a call site, so 'the declaration's name range' is also ambiguous (caller vs callee).  
  _Fix:_ In the Surface table, state per-code anchoring: the three validation codes at the declaration's name range; MissingProvenancePushdownAdvisory at the call site's WHERE clause range.
- **'Only known soundness gap' claim is false by the spec's own rules** — _Semantics rule 8 (Cardinality soundness caveat)_ · correctness-consistency · `spec-edit-only`  
  Rule 8 says misdeclared cardinality 'is the only known soundness gap in v1'. But rule 5 says deterministic/idempotent/append_only are author-declared and not derived, rule 4 says the planner 'may rely on' them for replay/resume/incremental-append, and no validator checks them. A misdeclared `deterministic: true` on a body calling now() (the Design section's own example) is an equally unverified soundness gap.  
  _Fix:_ Reword: 'cardinality is the only trusted declaration that gates an L1 rewrite today; deterministic/idempotent/append_only are equally trusted and become soundness gaps once L2/L3 rules consume them.'
- **Author-side contract of deterministic/idempotent/append_only never defined** — _Frontmatter properties the planner consumes / Semantics rule 4_ · clarity · `design-decision-needed`  
  The spec defines only the planner privileges each property grants, never the assertion the author makes. What does `idempotent: true` mean on a pure `smelt.define` SELECT that performs no writes? What does `append_only` assert — 'later runs only add rows'? And `append_only` 'enables the partition-DELETE+INSERT path', which deletes — an odd fit for a property named append-only. Authors and validator implementers will guess these contracts differently.  
  _Fix:_ Add a normative definition per property of what the author asserts about the body (and to which declaration kinds each property meaningfully applies), separate from the planner effect column.
- **Monotonicity invariant is contradicted by `backends:` narrowing** — _Constraints & Invariants 6 (Property-to-effect monotonicity)_ · correctness-consistency · `spec-edit-only`  
  'Setting a property to its non-default value must not block any optimisation that was available at the default.' But the Surface table says `backends:` (default: inferred from body) 'narrows physical strategy choice... narrows engine routing' at L2/L3 — declaring `backends: [duckdb]` blocks lowering strategies available at the default. As written, the invariant forbids the documented behaviour of one of the six listed properties.  
  _Fix:_ Scope the invariant to the rewrite-enabling properties (deterministic, idempotent, append_only, joins, provenance) and explicitly carve out `backends:` as a constraint key, not an optimisation hint.
- **Termination argument is insufficient and no fuel/failure mode is specified** — _Semantics rule 10 (Fixed-point loop semantics)_ · solution-quality · `design-decision-needed`  
  Termination is 'guaranteed by... each rule being individually monotone over a finite plan size' — but expansion grows the plan while elision shrinks it, and individual monotonicity does not prevent two rules oscillating (A rewrites X→Y, B rewrites Y→X) under a restart-on-Changed loop. Nothing obliges future rules (which 'inherit these obligations') to preserve a global decreasing measure, and there is no iteration budget or defined behaviour if a fixed point is not reached.  
  _Fix:_ State a per-rule termination obligation (e.g. each rule must be idempotent on its own output, and the rule set must admit a decreasing measure) plus a normative iteration cap with a defined internal-error diagnostic on exhaustion.
- **'Source columns of that item' undefined when the outermost SELECT reads CTEs** — _Semantics rule 6 (Provenance validation rule)_ · clarity · `implementation-impact`  
  Validation compares declared source_cols against 'the body's outermost SELECT'. If the body uses CTEs or subqueries, the outermost SELECT references intermediate columns, not source columns. Is the 'source columns' set the syntactic references in the item expression, or resolved through CTEs to base inputs? Under the syntactic reading, any provenance declared against true inputs always mismatches; under the resolved reading, a lineage analyser (which rule 5 says doesn't exist) is required. Implementers will diverge.  
  _Fix:_ Define 'source columns of a SELECT item' precisely (syntactic references in the outermost SELECT) and state explicitly that bodies with CTEs/subqueries either skip validation or validate against the immediate references only.
- **--show-plan behaviour for multi-item files is unspecified** — _`smelt build --show-plan` CLI surface_ · clarity · `implementation-impact`  
  The surface takes 'a model file path' and 'builds the logical plan for the given file', but functions.md (referenced in the scope callout) allows a file to contain any number of bare model SELECTs plus smelt.define/extern items. Whether --show-plan prints one plan per model, all plans concatenated, only defines' call sites, or errors on multi-model files is undefined — and byte-determinism of the output ('Output shape is stable') cannot be tested without fixing this.  
  _Fix:_ Specify: --show-plan renders the plan of every model declaration in the file in declaration order (or errors with a named diagnostic on multi-model files), and how smelt.define-only files behave.

### `python_models.md`

- **Special '--- name: X ---' fence contradicts 'processed identically to SQL model files'** — _Returned SQL string_ · correctness-consistency · `implementation-impact`  
  §Compile-time evaluation says returned strings 'are then parsed and processed identically to SQL model files', but the grammar in §Returned SQL string opens frontmatter with '--- name: <model_name> ---' — a fence format models.md does not use (SQL files use a bare '---' fence). The spec also says 'When a name: field appears' and 'If frontmatter is absent, defaults apply', implying name-less frontmatter is legal, yet the only opening delimiter shown embeds name:. A second implementer cannot tell whether a returned string starting with a plain '---' block is valid frontmatter or SQL.  
  _Fix:_ Either adopt the standard bare '---' fence (with name: as an ordinary optional key) so the 'identical processing' claim holds, or explicitly define both opening forms ('--- name: X ---' and bare '---') and state how a returned string with plain '---' frontmatter is parsed.
- **Name mismatch drops the entire frontmatter, silently discarding materialization/tags** — _Model name derivation_ · solution-quality · `design-decision-needed`  
  'A name: value that differs from the function name is a PythonModelNameMismatch diagnostic (Error severity); the frontmatter is dropped and model defaults apply.' Dropping the whole block discards unrelated, valid keys (materialization, tags, owner) — a model intended as `table` silently becomes the default `view` in any path that continues past the Error (LSP analysis at minimum). The spec also never says whether an Error here aborts the build or whether the defaults-applied model actually runs — two implementers will diverge.  
  _Fix:_ Decide and state: either the model is excluded entirely on mismatch (fail-loud), or only the name: key is ignored and the rest of the frontmatter is honored. Specify build vs. LSP behavior explicitly.
- **No determinism or side-effect constraints on @model functions** — _Compile-time evaluation_ · solution-quality · `design-decision-needed`  
  Evaluation runs 'during smelt build, smelt run, or LSP analysis', and convergence requires output 'identical to the previous round'. Nothing requires @model functions to be deterministic functions of the project context. Nondeterministic Python (time, random, network, file reads) breaks convergence (spurious 5-round errors), caching, and CLI↔LSP parity — and means the LSP executes arbitrary user Python with side effects on open/edit. This is a missing load-bearing invariant for a compile-time-evaluation design.  
  _Fix:_ Add a Constraints entry: @model functions must be deterministic functions of the project context; side effects are unsupported (behavior undefined or diagnosed). Note the LSP-executes-user-code consequence explicitly, ideally with a statement on when re-evaluation is triggered.
- **Interpreter config vs. PyO3 embedded mode — import environment unspecified** — _Python interpreter configuration_ · solution-quality · `design-decision-needed`  
  The Surface table presents SMELT_PYTHON / python: / PATH fallback unconditionally, but §Execution modes says the default mode embeds Python via PyO3 — where a configured interpreter path is presumably inert. The spec never says whether @model files may import third-party packages, nor which environment (embedded interpreter's site-packages vs. the configured interpreter's venv) imports resolve in. The two modes would therefore differ in which user code even runs — a parity gap beyond the SDK-path edge cases noted in Known Divergences.  
  _Fix:_ State per mode: which settings apply (does SMELT_PYTHON select the PyO3-linked interpreter's venv via virtualenv activation, or only subprocess mode?), and whether third-party imports are supported. Add a parity requirement that the import environment is identical, or document the divergence normatively.
- **Constraint 4's canonical-address definition is self-contradictory** — _Constraints & Invariants_ · clarity · `implementation-impact`  
  'Uniqueness is keyed on the full canonical address (the function name), not on the bare leaf name in isolation.' If the canonical address *is* the function name, 'full canonical address' and 'bare leaf name' are the same string and the contrast is vacuous. If smelt.<path> addresses for SQL models can be directory-qualified (architecture.md §Resolution, via models.md), the spec never says how a Python model's address incorporates (or ignores) its .py file's directory — so whether two same-named functions in different directories collide is undecidable from this text.  
  _Fix:_ Define the canonical address of a Python-derived model explicitly (e.g., 'always smelt.<function_name>, regardless of file location' — or directory-qualified like SQL models), then restate the uniqueness rule without the circular parenthetical.
- **Which .py files are executed, and the import path for helpers, are unspecified** — _File format_ · solution-quality · `implementation-impact`  
  'Python model files are .py files in any directory listed under paths:' and 'a file must import and use the @model decorator'. Unstated: is every .py under paths: executed (so a helper module with top-level side effects runs as if it were a model file), or only files textually/AST-detected to contain @model? Can a model file import a sibling helper module (is the models directory on sys.path)? Each choice yields observably different behavior; a second implementer would guess differently.  
  _Fix:_ Specify the execution predicate (e.g., 'a .py file is executed iff decorator scanning finds @model/@model(); other .py files are never executed') and the sys.path contract for imports between files under paths:.

### `schema_evolution.md`

- **NULL → NOT NULL "unless default: is set" does not handle existing NULL rows** — _Change classification_ · solution-quality · `design-decision-needed`  
  "Change NULL → NOT NULL — **Blocked** — requires `--allow-full-refresh` unless `default:` is set" implies `default:` makes the change safe. But a column DEFAULT only affects future inserts; `ALTER COLUMN SET NOT NULL` still fails if existing rows contain NULLs. `backfill:` is defined only for column addition ("after the column is added"). Implementers will diverge: emit DDL that fails at runtime, or silently `UPDATE ... WHERE col IS NULL` rewriting data without an explicit rule. Neither the DDL sequence nor the NULL-rows failure mode is specified.  
  _Fix:_ Specify the migration sequence (e.g., UPDATE existing NULLs to the default/backfill expression, then SET NOT NULL), or drop the `default:` escape and require `--allow-full-refresh`/`backfill:` for NULL→NOT NULL. State the failure mode when NULLs exist.
- **Flag gating unspecified when a Safe change hits an incapable backend** — _Migration actions_ · solution-quality · `design-decision-needed`  
  Classification marks changes universally "Safe", but the capability matrix shows e.g. ADD COLUMN (NOT NULL) ✗ and ALTER COLUMN TYPE ✗ on Spark. Design says the planner "fall[s] back to TableRewrite or FullRefresh when DDL is unavailable" — but the MigrationAction table gates FullRefresh on `--allow-full-refresh` only for "Unsafe change". Whether a safe-in-principle change that needs FullRefresh on Spark+Parquet halts without the flag, or silently drops and recreates the table, is unstated. Two implementers will read this opposite ways; one reading destroys data without consent.  
  _Fix:_ Add a rule: when backend capability forces a destructive action (FullRefresh) for an otherwise-safe change, the same `--allow-full-refresh` gate applies; state whether TableRewrite (data-preserving) needs a flag.
- **TableRewrite is undefined: "complex change", data source, and flag requirement all unspecified** — _Migration actions_ · clarity · `design-decision-needed`  
  TableRewrite's condition is "Spark backend, complex change" — "complex change" is never defined. The behavior "CREATE TABLE AS SELECT + rename" does not say what the SELECT reads: the old table with casts (data-preserving) or the model SQL (a recompute, equivalent to full refresh, which would lose incremental history). No flag gates it. A second implementer would guess each of these differently, with materially different durability outcomes.  
  _Fix:_ Define which classified changes map to TableRewrite, specify the CTAS source (old table with per-column cast expressions), and state its flag requirement.
- **Discovery criterion "a corresponding .sql file exists" breaks for multi-model files and generator emissions** — _Stale schema cleanup_ · correctness-consistency · `implementation-impact`  
  "A model is discovered if a corresponding `.sql` file exists under `paths:`" implies one file per model name. models.md allows multi-model files (several models in one .sql), and this spec's own Known Divergences entry says generator-emitted models have stored schemas "keyed by the emitted `smelt.<path>` identifier" with no per-model file. Taken literally, cleanup after a successful build would delete the deployed-schema records of every model not matching a filename — silently destroying migration state for valid models.  
  _Fix:_ Redefine discovery as membership in the compiled project's model set (post-parse, including multi-model files and generator emissions), not filename existence.
- **Which materializations participate in schema evolution is unspecified** — _Stored schemas_ · solution-quality · `implementation-impact`  
  "When a model is materialized by `smelt run` or `smelt build`, smelt writes the deployed schema" — with no restriction by materialization mode. ALTER TABLE is meaningless for `view`/`materialized_view` (recreated each run) and `ephemeral` models have no deployed object at all. Whether stored schemas are written for views, whether a view column change is reported by `smelt diff`, and whether blocked-change flags apply to views are all guessable in multiple ways.  
  _Fix:_ State explicitly which materializations get stored schemas and MigrationAction processing (presumably `table`/incremental only) and that views/ephemerals are exempt, with `smelt diff` reporting accordingly.
- **No coverage of FullRefresh interaction with incremental models** — _Migration actions_ · solution-quality · `design-decision-needed`  
  "`FullRefresh` … Table dropped and recreated" is specified without addressing incremental models, whose tables hold accumulated history that may not be reproducible from sources, and whose interval ledger (run_state.md) records coverage. Dropping such a table without resetting the ledger leaves state claiming intervals are covered when the data is gone; and the history loss itself deserves an explicit warning/consent rule. The spec links incremental concerns nowhere; this is the single most dangerous schema-evolution path and it has no failure-mode coverage.  
  _Fix:_ Add a Semantics subsection: FullRefresh on an incremental model resets its interval ledger (cross-link incremental_models.md/run_state.md) and emits an explicit history-loss warning; consider a stronger gate than `--allow-full-refresh`.

- **[Minor]** null→empty-Text coercion is a backdoor optional that conflates null with empty string — _Design — Why no `Optional<V>` for missing fields_. The spec rejects `Optional<V>` ("A field declared on the schema is required"), yet a YAML/JSON `null` at a `Text` field coerces to `''` with only a warning (`ConfigLoaderNullCoercion`). This gives `Text` fields a silent optional-with-default that no other type gets, and consumers cannot distinguish an authored empty string from a null. The message "declare a default in the source file" also presumes a defaulting mechanism the spec never defines. _Fix:_ Consider making null at any field a hard `ConfigLoaderTypeMismatch` until `Optional<T>` ships (the precedent in `smelt.config.var` need not bind a new surface); at minimum, justify the Text-only carve-out in §Design and fix the message wording.
- **[Minor]** Symlink escape and non-escaping `..` semantics unspecified — _Path resolution_. Only "a `..` segment that would escape the workspace root" is rejected, so `configs/../models/x.yaml` is presumably admitted; and §Constraints' "path-canonicalisation check before file open" does not say whether canonicalisation resolves symlinks. An in-workspace symlink pointing outside the root either passes or fails containment depending on that choice — a security-relevant divergence point. _Fix:_ State whether non-escaping `..` is allowed (suggest: reject all `..` for simplicity) and that containment is checked on the symlink-resolved real path, with `ConfigLoaderPathEscapesWorkspace` on violation.
- **[Nit]** Signature notation `-> Schema` and scope callout's `Map<K, V>` are imprecise — _Loader calls_. `load_yaml(path: Text, schema: Schema) -> Schema` uses `Schema` both as the argument's kind and as the return type; the return type is the type the schema argument *denotes*, not `Schema` itself. The scope callout also says "`Map<K, V>` over such a schema" while §Schema authoring restricts keys to `Map<Text, S>`. _Fix:_ Write the signature as `load_yaml(path: Text, schema: S) -> S` with a note that `S` ranges over the admissible schema set, and change the callout to `Map<Text, V>`.

### `models.md`

- **[Minor]** Asymmetric trigger conditions and unstated precedence between constraint rows — _Constraint violations_. Hard-error rows trigger on `incremental` presence ("`ephemeral` + `incremental` | Hard error") while warning rows trigger only on "`incremental.enabled: true`". So `ephemeral` + `incremental.enabled: false` is a hard error but `view` + `incremental.enabled: false` is silently fine — likely unintended asymmetry. Also unstated: a `view` model with `incremental` and no `timeseries` matches both the "Warning … incremental config ignored" row and the "Hard error (`TimeseriesRequiredForIncremental`)" row; precedence between rows is undefined. _Fix:_ Normalize trigger conditions (presence vs `enabled: true`) across rows and add a sentence defining evaluation order when multiple rows match (e.g. hard errors win; ignored config is not further validated).
- **[Minor]** Warnings hard-coded to stderr and most rows lack diagnostic codes — _Constraint violations_. "Warning (stderr); incremental config ignored" pins a CLI output channel into normative spec text, which conflicts with the diagnostics-based CLI/LSP parity model (diagnostics.md defines severities, not channels — an LSP client has no stderr). Three rows cite codes (`TimeseriesRequiredForIncremental`, `CumulativeForbidsTimeseries`, `CumulativeForbidsIncremental`) while the other six hard errors and two warnings cite none, so implementers will invent uncatalogued codes. _Fix:_ Replace "(stderr)" with "Warning diagnostic" and assign catalogue codes (diagnostics.md) to every row.
- **[Minor]** "Five materialization modes, not three" contradicts the six-mode Surface table — _Design_. Design says "dbt has three modes; smelt adds `materialized_view` … and `test`" — i.e. five — but the Surface table lists six modes (`cumulative_aggregate` is omitted from the rationale). dbt also ships more than three materializations (view, table, incremental, ephemeral, materialized view), so the comparison is factually off in both directions. _Fix:_ Retitle the paragraph (e.g. "Materializations beyond dbt's") and enumerate all six modes, correcting the dbt count.
- **[Minor]** Spec defers authority to user docs for parameterised-call status — _Design_. "The note in user docs is the authoritative statement of current status" (§Design, Named parameters parsed but deferred) inverts the documentation hierarchy — specs are normative and user docs must agree with them, per the project's spec-first rule. Implementation status also belongs in Known Divergences (where an entry already exists), not in §Design. _Fix:_ Delete the sentence; let the existing Known Divergences entry ("Parsed, not executed") be the single status statement.
- **[Minor]** Symlink-following has no cycle or duplicate-visit rule — _Model discovery_. "smelt recursively walks each path in `paths:` …, following symlinks" — without a cycle rule, a symlink loop is an infinite walk, and the same file reachable via two links (or via overlapping `paths:` entries) yields the same model twice: is that a `DuplicateAddress` error or deduplicated by canonical real path? Implementations will differ. _Fix:_ Specify dedup by canonicalized real path and that a symlink cycle is detected and skipped (or is a discovery error).
- **[Minor]** Per-model `target` override: no failure mode for unknown targets, no cross-target dependency rule — _YAML frontmatter keys_. "Override execution target for this model (overrides `smelt.yml` and `--target`)" — overriding an explicit CLI `--target` is a strong semantic, but the spec gives no failure mode when the named target is not declared in `smelt.yml` (load-time error vs run-time?), and says nothing (not even a pointer) about a model whose upstream resolves to a different target — the core multi-backend case this key creates. _Fix:_ Add: unknown target name is a hard error at load time; add a pointer to the spec that owns cross-target reference semantics (or state it is currently unsupported).

### `planner_integration.md`

- **[Minor]** Cycle-tainted nodes are transparent:true with body:None, contradicting the transparency definition — _Constraints & Invariants 1 & 5_. Surface says 'transparent: true — ... Body is reachable', and Constraint 1 says 'The body field on FunctionCall is None for opaque calls by construction'. Constraint 5 then says cycle-tainted plans 'reach the planner with body: None' — implying a transparent:true node with no body, a state the Surface says cannot exist. Rules pattern-matching transparent:true and unwrapping the body would panic; whether cycle-tainted nodes are demoted to transparent:false is unstated. _Fix:_ State that cycle-tainted FunctionCall nodes are constructed with transparent: false (or that transparent: true with body: None is legal and rules must treat it as black-box).
- **[Minor]** Stale claim that diagnostics.md does not yet exist — _Known Divergences / Open Questions — Diagnostic codes pre-diagnostics.md_. 'Codes listed in this spec are owned here until a diagnostics.md spec lands.' diagnostics.md exists in the same directory (last_reviewed 2026-06-11) and already catalogues all four codes (ProvenanceMismatch, JoinsMismatch, DeclaredCardinalityUnverifiable, MissingProvenancePushdownAdvisory). The ownership statement is stale and leaves the two specs without a defined precedence if their wording drifts. _Fix:_ Update the bullet: state that diagnostics.md now owns the catalogue entries (or that this spec owns trigger semantics while diagnostics.md owns naming/severity tiers), and add diagnostics.md to Related specs.

### `python_models.md`

- **[Minor]** Failure surface for Python exceptions is unspecified — _Constraints & Invariants_. Constraint 3 says returning a non-string 'is a Python-level runtime error during compilation', and §Design promises 'Python exceptions with tracebacks', but the spec never defines the user-visible behavior: what diagnostic (code, severity) fires when a @model function raises, where it is anchored (file? decorator line?), whether other models in the same file/round still evaluate, and how this surfaces in the LSP vs. CLI. _Fix:_ Add a failure-modes paragraph in §Semantics: diagnostic code and anchor for Python exceptions and bad return types, plus whether evaluation of remaining @model functions continues.
- **[Minor]** Hard-coded 5-round cap silently bounds generator-chain depth — _Iterative evaluation_. 'Python model discovery runs in rounds (up to 5)'. A legitimate chain of N Python generators, each consuming the previous one's output, needs roughly N+1 rounds; chains deeper than ~4 are inexpressible, and the cap is not configurable. The spec presents 5 as a fixed invariant (Constraint 5) without acknowledging it constrains valid (non-oscillating) workloads, not just divergent ones. _Fix:_ State the rationale for 5 and whether deep-but-converging chains are intentionally unsupported; consider making the cap configurable or distinguishing 'still making progress' from 'oscillating' in the error.
- **[Nit]** Scope callout omits out-of-scope pointers required by the template — _What this is (scope callout)_. The callout lists what the spec covers but has no 'Out of scope: ... (see <other_spec>.md)' pointers, unlike SPEC_TEMPLATE.md's required shape ('naming the adjacent specs that own neighbouring concerns'). E.g., model frontmatter semantics (models.md), multi-model production (meta_language.md), and diagnostics registry (diagnostics.md) are adjacent concerns a reader may land here looking for. _Fix:_ Append out-of-scope bullets to the callout naming models.md (frontmatter/materialization semantics), meta_language.md (multi-model production), and smelt_yml.md (python: key).

### `schema_evolution.md`

- **[Minor]** Example shows VARCHAR → TEXT as an ALTER TABLE migration, but that widening is not in the table — _smelt diff output_. The text-output example lists "ALTER COLUMN status VARCHAR → TEXT" and concludes "Migration: ALTER TABLE (2 statements)", implying VARCHAR→TEXT is a safe widening. The widening table contains no VARCHAR→TEXT row (only CHAR→VARCHAR and VARCHAR(n)→VARCHAR). If TEXT and VARCHAR are the same type, no change should be reported at all; if distinct, the change is unclassified. The example contradicts the normative table either way and could lead an implementer to add an undocumented widening. _Fix:_ Replace the example with a widening from the table (e.g. INTEGER → BIGINT), or add a row stating TEXT ↔ VARCHAR are aliases and never diffed.
- **[Minor]** backfill: lifecycle and standalone use are underspecified — _Column evolution annotations_. "`backfill` | SQL expression applied in an UPDATE statement after the column is added" leaves open: (a) whether backfill runs exactly once at the addition migration and is inert thereafter (a reader could re-apply it every run, repeatedly overwriting data); (b) whether `backfill:` alone (without `default:`) permits a NOT NULL column addition via add-nullable → UPDATE → SET NOT NULL; the classification table keys only on `default:`. Also, Surface says `default:` is "Required when adding a NOT NULL column", while Semantics says its absence is merely Blocked-without-`--allow-full-refresh` — "required" overstates. _Fix:_ State that backfill executes exactly once, as part of the column-addition migration; specify whether backfill-only NOT NULL addition is supported; soften Surface "Required" to match the classification table.
- **[Minor]** Backend used by offline smelt diff is unspecified though output is backend-dependent — _smelt diff output_. `risk.migration_action` and `statements` depend on the backend capability matrix ("the planner resolves the most capable action the backend supports"), yet the surface is `smelt diff [--select <selector>] [--json]` with no `--target`, and the spec never says which target's backend the offline diff plans against. The same model edit yields `alter_table` on DuckDB and `full_refresh` on Spark+Parquet, so this choice is observable. _Fix:_ State that `smelt diff` accepts/uses `--target` (default `dev`, per cli.md) and that migration_action/statements are computed for that target's backend.
- **[Minor]** Scope callout omits the required out-of-scope boundaries — _What this is (scope callout)_. The template requires the callout to state "what it does not — naming the adjacent specs that own neighbouring concerns." This spec's callout is a single in-scope sentence with no out-of-scope pointers, even though boundaries are genuinely load-bearing here: `.smelt/` layout is owned by run_state.md, reuse decisions by virtual_environments.md, change detection by output_fingerprint.md (these only surface deep in Known Divergences/References). The Spec-first and Timeless-oracle blockquote lines are also absent. _Fix:_ Extend the callout: "Out of scope: the `.smelt/` storage layout (run_state.md); fingerprint-keyed reuse (virtual_environments.md); change-detection equivalence (output_fingerprint.md); materialization modes (models.md)." Add the standard rule lines.

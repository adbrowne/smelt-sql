## Executive summary

The single highest-leverage result is that **the cross-spec pass found a different and more severe class of defect than any single-spec read could** — references to primitives that do not exist, codes referenced but never defined, and two normative specs flatly contradicting each other on the same rule. These are invisible inside any one file. The recurring patterns, in rough order of how much trouble they will cause:

1. **Dangling references to undefined primitives and sections.** `cumulative_aggregate.md` is built on a `merge_into` backend primitive that `architecture.md` does not define; multiple specs point `merge_into`/`Backend primitives` at a nonexistent `architecture.md` section. `ColumnTypeUnresolved` is referenced as a live diagnostic across several specs but is absent from the `diagnostics.md` catalogue (which states "None currently open"). A spec that cites a contract that doesn't exist cannot be implemented as written.
2. **Two specs, one rule, opposite answers.** `gradual_typing.md` forbids nullability-in-signatures that `types.md` §11 fully specifies; `functions.md` and `gradual_typing.md` give opposite Tier 1/2 call-site return types; `functions.md` bans meta-type `smelt.define` params that `types.md`'s table admits; the cumulative CLI flags (`--start/--end`) contradict the incremental flags (`--event-time-start/--event-time-end`) they claim to mirror; the seed-loader story in `cli.md`/cluster contradicts `seeds.md` (the `read_csv_auto` loader was removed).
3. **Self-contradiction across repeated statements of one rule** (within a spec). The incremental output-clamp is the *write window* in one place and the *run window* in three others — a data-loss bug for rebasing models; cumulative idempotence is stated backwards relative to the spec's own reprocessing paragraph; the architecture resolution table contradicts the scan-root-stripping note three lines below it.
4. **Unsound math/semantics that reads plausibly.** `schema_evolution.md`'s DECIMAL widening rule permits `DECIMAL(10,2)→DECIMAL(10,5)`, which overflows; the per-source incremental bound tuple conflates a read bound with a write skew; `datagen.md`'s nullable-from-first-shape rule writes nulls into a non-nullable Arrow column on the spec's own example.
5. **Silent-drop / silent-fallthrough against the project's own fail-loud discipline.** Non-injective table-name mapping silently clobbers two models into one table; `models.md` silently drops misspelled `columns:` entries; `python_models.md` silently discards a whole frontmatter block on a name mismatch.
6. **Architectural-invariant contradictions.** A finding claims `smelt-logical` ownership of `RuleContext`/classifiers contradicts every planner spec — directly touching a `stable` architecture invariant.

**Systemic, low-effort wins** (flagged independently by many units — fix once, corpus-wide):

- **The "owned here until `diagnostics.md` lands" dead conditional.** At least 6 specs (`functions`, `planner_integration`, `scoping`, `types`, + the ownership and infrastructure agents) still carry this clause; `diagnostics.md` has landed. One find-delete pass.
- **Diagnostic call-path drift.** Trigger text and messages still spell calls three ways — `smelt.fn.<path>`, `smelt.functions.<name>`, and the current `smelt.<path>`. The retired spellings should be swept.
- **`workspace`-vs-`project` vocabulary drift.** Specs written before the project-isolation invariant still say "workspace" where they mean "project" (`diagnostics`, `lsp`, `architecture`).

**Where the specs are strong.** The conservative-analysis cores — `output_fingerprint` determinism, `types` nullability soundness, incremental batch-safety — are consistently well-specified and well-reviewed. No spec's central design was judged unsound; the defects cluster at the **seams between** these conservative analyzers and the generative front-ends (generator files, Python models, the meta-language) that feed them.

## Critical findings

*26 confirmed Critical findings (21 internal to a single spec, 5 cross-spec/systemic). All verified and spot-checked.*

### Internal to a single spec

#### C1 — `architecture.md` — Resolution example table contradicts the dedicated-scan-path note for sources and seeds

- **Section:** Resolution: `smelt.<path>` is the universal addressing scheme
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** The examples table, captioned "assuming `paths: [\"models\"]`", shows `sources/raw/events.yml` → `smelt.raw.events` and `seeds/raw/users.csv` → `smelt.raw.users` (prefixes stripped). But the note directly below says functions/, sources/, and tests/ "are **not** in the `paths:` list by default; their scan-root prefix is not stripped" — so the source should be `smelt.sources.raw.events`. Seeds are worse: per seeds.md, a seed is "a `.csv` file under any directory listed in `smelt.yml::paths`", so under `paths: ["models"]` the file is not a seed at all. Two implementers would build different resolvers from this table.
- **Fix:** Fix the two rows: either change the caption to `paths: ["models", "seeds"]` and the sources row to `smelt.sources.raw.events`, or state explicitly which kinds use dedicated scan paths and whether seeds strip. Add seeds to the dedicated-scan-path note one way or the other.

#### C2 — `architecture.md` — Underscore-join name mapping is not injective; silent table clobbering is unguarded

- **Section:** Default materialization name mapping
- **Dimension:** solution-quality · **Implication:** `implementation-impact`
- **Finding:** "Table = address path joined with `_`. Underscores already in path components are preserved as-is (no escaping…)" makes the mapping non-injective: `smelt.staging.orders` and `smelt.staging_orders` both emit `main.staging_orders`. The mapping is "mandatory" with no per-entity override, and the only collision check specified (`project_address_collisions`) is over `smelt.<path>` addresses, not emitted (schema, table) names. Two distinct models silently materialize into one table — exactly the "materialize wrong data with exit 0" failure the Diagnostic-parity section calls the worst case, and a direct fail-loud violation.
- **Fix:** Mandate an emitted-name collision diagnostic (Error) computed over the (target schema, joined name) pairs of all persisted entities in a project, analogous to `DuplicateAddress`; or specify an injective join (escape `_` in components).

#### C3 — `cumulative_aggregate.md` — No merged-partition tracking mechanism, and retry-after-partial-failure is unspecified/refused

- **Section:** Reprocessing semantics
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** "The rule rejects reprocessing at planning time when it can detect it (the partition has been merged before…)" — but the output has no partition column, and no watermark/ledger mechanism is specified, so 'detect it' is unimplementable as written. Worse, §Execution model blesses partial progress ("Earlier committed partitions do not roll back"), yet Constraint 9 rejects any window overlapping already-merged partitions — so the obvious retry of the same window after a mid-run failure is refused, forcing full refresh. Implementers will invent divergent state stores and resume policies.
- **Fix:** Specify the merged-partition state (e.g., per-model merged-partition set or high-watermark in smelt state), whether empty partitions are recorded, and a resume rule: a re-run skips already-merged partitions within the window rather than rejecting, distinct from genuine reprocessing of changed data.

#### C4 — `cumulative_aggregate.md` — Classifier misses HAVING, DISTINCT aggregates, LIMIT/ORDER BY/set ops — all break cross-partition equivalence

- **Section:** Classifier checks
- **Dimension:** solution-quality · **Implication:** `implementation-impact`
- **Finding:** The five-check list ("rejected at planning time if any of these hold") omits HAVING: `HAVING COUNT(*) >= 2` over a key with one row in each of three partitions keeps the key under full refresh (count 3) but filters every per-partition delta — equivalence broken. `COUNT(DISTINCT x)` is literally "a direct call to" COUNT per the allowlist wording, yet SUM-combining per-partition distinct counts double-counts cross-partition repeats. Outer LIMIT/ORDER BY and set operations are also unaddressed. Incremental's spec gates HAVING (`allow_having`), making the omission here look deliberate.
- **Fix:** Add classifier rejections: HAVING on the outer SELECT, DISTINCT (and ORDER BY) modifiers inside allowlisted aggregate calls, outer LIMIT/OFFSET, and set operations — each with its diagnostic code or folded under existing codes.

#### C5 — `datagen.md` — First-shape nullability rule contradicts Constraint 7 and the spec's own example

- **Section:** Semantics — `linked_choice` and joint-distribution pools (Arrow type per field)
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** "Nullability follows the same rule: nullable iff the referenced field's generator is nullable" — where 'the same rule' is "evaluated against the first shape that declares the field". In the flagship example, shape 1 declares `user_id` as plain `foreign_key` (non-nullable) while shape 2 uses `optional { prob: 0.0 }`, always emitting null. The first-shape rule yields a non-nullable Arrow column containing nulls — invalid data or a builder panic for the spec's own example. Constraint 7's "(modulo Optional wrapping)" explicitly permits this mix, so the rule is internally contradictory and shape-order-dependent.
- **Fix:** Change the nullability rule to: a `linked_choice` column is nullable iff the referenced field's generator is `Optional` in ANY shape. Keep the Arrow base type from the (uniform-by-constraint-7) underlying type.

#### C6 — `expansion.md` — "Codegen-time expansion is lazy / materialises at Level-2" contradicts planner_integration.md's shipped L1 ExpandTransparentFunctionCalls rule

- **Section:** Constraints & Invariants
- **Dimension:** correctness-consistency · **Implication:** `design-decision-needed` · **Verify:** unverified
- **Finding:** Constraint 6 states "Calls remain symbolic through Level-1 planning and materialise at Level-2 … no rule expands speculatively", and Semantics §"Two senses of expansion" says codegen-time expansion is "Performed at the planner's Level-2 strategy lowering". But planner_integration.md lists `ExpandTransparentFunctionCalls` as an **L1** (Logical → Logical) rule and explicitly says "L1 is the only level with shipped rules". An implementer following expansion.md would refuse to expand at L1, breaking the shipped pipeline; one following planner_integration.md violates expansion.md's normative constraint. Neither spec acknowledges the conflict.
- **Fix:** Decide where expansion runs (eager L1 rule vs lazy L2 materialisation). Either rewrite Constraint 6 and §"Two senses" item 2 to match the L1 rule, or record the L1-eager behaviour as a Known Divergence with the lazy-L2 design as intent — and cross-link planner_integration.md.

#### C7 — `incremental_models.md` — Outer WHERE clamp: write window vs run window stated inconsistently in four places

- **Section:** Execution model (DuckDB, current)
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** Step 2 says the injected filter uses `write_start`/`write_end` and "constrains the model's *output* to the same write window the DELETE covers" — load-bearing, since DELETE range and INSERT range must match or you get data loss/duplicates. But §"Run window vs partition granularity" says "the outermost WHERE constrains the output to the 30-day run window", §"Source-filter pushdown" says "The outer WHERE constrains the model's output to the run window", and Constraint 5 repeats "to the run window". For any model with a nonzero bound these windows differ; an implementer following the three "run window" statements deletes lookback partitions and re-inserts nothing into them.
- **Fix:** Pick one window (write window, per step 2's idempotence rationale) and rewrite the run-window section, the pushdown section, and Constraint 5 to say "write window", noting it equals the run window when the model's write bound is zero.

#### C8 — `incremental_models.md` — Write-window derivation conflates source-read bounds with output-partition skew

- **Section:** Execution model (DuckDB, current)
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** Step 1: "The write window is the run window widened by the model's derived lookback/lookforward bound (§ Per-source bound derivation)". Per-source bounds are the *inverse image of the run window in source space* (how far to read); the write window needs the *forward image in output-partition space* (how far output partitions can skew). These coincide only for symmetric rebasing. Trace a plain-lookback model (partition=event_date, LAG 7d): widening DELETE+clamp by 7d re-inserts partitions [D-7,D) whose LAG needs source data back to D-14, but pushdown stops at run_start-before=D-7 — wrong rows written. The hedge "for a write-rebasing model … the write window is wider" gives no rule for detecting rebasing or computing the write bound.
- **Fix:** Define a separate write-skew bound (forward image of source rows in output-partition space), specify how it is derived and when it is zero (partition_column passed through, not derived), and require source pushdown to be computed from the write window, not the run window, when the write window is wider.

#### C9 — `incremental_models.md` — Sessionization example is unsound: bounded frame does not bound session_start_date skew

- **Section:** Batch safety classification
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** The spec's flagship case — "This is what lets a sessionization model partition its windows by device_id … while the model itself is partitioned by a derived session_start_date" — claims a `RANGE BETWEEN INTERVAL '30 minutes' PRECEDING` frame makes the model bounded. But the 30-minute frame bounds the *inter-event gap*; chained gaps make total session length unbounded, so an event in the run window can belong to a session whose `session_start_date` is arbitrarily early. No finite write window covers every partition the INSERT rewrites; the DELETE-covers-INSERT guarantee in step 1 and per-partition equivalence both fail. The chained-window problem is never acknowledged.
- **Fix:** Either classify chained-gap sessionization as Unbounded/PerPartitionOnly (and pick a different example for bounded write-rebasing, e.g. UTC→local-date), or specify an explicit max-session-length cap from which the write skew is derived.

#### C10 — `incremental_models.md` — Two conflicting window-function admission rules

- **Section:** Safety checks (rejected by default)
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** §"Batch safety classification" admits a window whose PARTITION BY excludes the partition_column "when the OVER clause carries a bounded RANGE BETWEEN INTERVAL frame", citing the device_id sessionization case. §"Partition-aligned window functions" requires keys be "a **superset** of the model's `timeseries.partition_column`", explicitly rejects `OVER (PARTITION BY user_id)`, and says no-PARTITION-BY windows are "always rejected by this check" — with no mention of the bounded-frame exemption. The same SQL passes one gate and fails the other; the spec never says whether both apply or which wins.
- **Fix:** State one unified admission rule: a window is admissible iff (PARTITION BY ⊇ partition_column) OR (bounded RANGE frame with no UNBOUNDED bound), and rewrite §Partition-aligned window functions to reference the frame exemption.

#### C11 — `meta_language.md` — Spread/pipe precedence contradicts the columns_of build-path example

- **Section:** Pipe operator / Reflection: smelt.columns_of build-path example
- **Dimension:** correctness-consistency · **Implication:** `design-decision-needed`
- **Finding:** §Pipe operator says `|>` is "Lower precedence than every other meta-language operator (`...`, function call, field access)" (line 156), making `...` bind tighter than `|>`. But the reflection build-path example `SELECT ...smelt.columns_of(smelt.orders) |> map(fn c => c.name)` (line 321) requires `|>` to bind tighter than `...` — the `map` must run on the `List<ColumnRef>`, then the result is spread. Under the stated precedence this parses as `(...smelt.columns_of(...)) |> map(...)`, spreading the list before the map, which is ill-typed (spread consumes the list; map gets nothing). One of the two is wrong.
- **Fix:** Decide the precedence: either make `...` lowest (outermost) so it applies after the pipe chain, or parenthesise the example as `SELECT ...(smelt.columns_of(smelt.orders) |> map(fn c => c.name))`. Update line 156 and/or line 321 to agree.

#### C12 — `meta_language.md` — ModelRef.name/path: render-as-string-literal contradicts lift-to-identifier

- **Section:** Build-path execution / Reflection: smelt.models… (Semantics rule 8)
- **Dimension:** correctness-consistency · **Implication:** `design-decision-needed`
- **Finding:** Build-path §408 states the projections "`m.name` / `m.path` … are resolved … to their concrete `Text` values, rendered as SQL string literals (a model name is a data value, not a column reference)." Semantics rule 8 (§881) states "`m.name` and `m.path` are meta-`Text` values; in one of the four lift positions (column-reference, AS-alias, ORDER BY…, GROUP BY…) they lift to identifiers." The same `m.name` in a column-reference or AS-alias position is rendered as a string literal by one rule and as an identifier by the other. An implementer cannot satisfy both.
- **Fix:** Decide one rule. If wide-reflection Text follows the four-position identifier lift like ColumnRef.name, drop the "rendered as SQL string literals" clause from Build-path; otherwise carve ModelRef/SourceRef Text out of the lift table and amend rule 8.

#### C13 — `meta_language.md` — Wide-reflection ordering contradicts itself: "by path" vs "by path then name"

- **Section:** Semantics → Reflection: smelt.models, smelt.sources (rule 2 "Ordering" and rule 7)
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** Rule 2 states `with_tag` and `all` "return lists sorted ascending by `path`" (line 867). Rule 7 states `smelt.models.all` returns the union "sorted ascending by `path` then by `name` (the `name` is the tiebreaker when multiple `ModelRef` values share a generator-file `path`)" (line 966). Since every generator-emitted model carries the generator file's `path` (rule 7 line 961), sorting by `path` alone is non-deterministic for co-emitted models, directly violating the byte-equal determinism guarantee (rule 1/10). The two ordering rules cannot both be the contract.
- **Fix:** Make rule 2 the single authoritative ordering: "sorted ascending by `path`, then by `name` as a deterministic tiebreaker when paths collide (generator co-emissions)." Remove the divergent phrasing in rule 7 or have it cite rule 2.

#### C14 — `python_models.md` — `--- name: X ---` delimiter clashes with models.md's authoritative multi-model delimiter semantics

- **Section:** Surface — File format / Semantics — Returned SQL string
- **Dimension:** correctness-consistency · **Implication:** `design-decision-needed`
- **Finding:** The returned-SQL example and prose use `--- name: combined_events ---` as a *frontmatter* header whose `name:` must equal the function name or raise `PythonModelNameMismatch`. But `models.md` defines exactly `--- name: <model_name> ---` as the Layer-1 multi-model section delimiter whose name IS authoritative, and where any other `--- X ---` form is 'a hard parse error'. So the same token means two opposite things: in SQL files it sets identity; in Python output it must merely echo the function name. A parser shared between paths cannot honour both.
- **Fix:** Either reuse plain `---`/`---` single-model frontmatter (no `name:` in the delimiter) for Python output, or state explicitly how the Python path reinterprets the Layer-1 delimiter and reconcile with models.md §Model naming.

#### C15 — `python_models.md` — Circular-dependency rule forbids the self-referential generation the design exists to support

- **Section:** Semantics — Circular dependency detection vs Design — Iterative evaluation
- **Dimension:** solution-quality · **Implication:** `design-decision-needed`
- **Finding:** Circular detection fires when 'a model queries for models with a tag it itself carries'. Yet Design (§Iterative evaluation) endorses exactly that: 'a "tag all staging models" generator that a marts generator queries', and Constraint 5 frames multi-round evaluation as the supported mechanism. A generator that adds tag `staging` and also calls `find_models(tag="staging")` would be the canonical convergent case, but the stated rule errors on it. The boundary between legitimate fixed-point growth and an illegal cycle is undefined.
- **Fix:** Define circular-ness in terms of non-convergence/oscillation (output never stabilises), not 'queries a tag it carries'. A monotonically-growing-then-stable set should converge, not error.

#### C16 — `schema_evolution.md` — DECIMAL widening rule permits data loss / overflow

- **Section:** Safe scalar type widenings
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** The rule `DECIMAL(p,s) → DECIMAL(p2,s2) where p2 ≥ p and s2 ≥ s` is unsound. Integer-digit capacity is p−s. Widening DECIMAL(5,2) (3 integer digits, max 999.99) to DECIMAL(6,4) satisfies p2≥p and s2≥s yet has only 2 integer digits (max 99.9999): the value 123.45 overflows. Implemented as written, this misclassifies a lossy change as Safe and emits an unsafe ALTER COLUMN TYPE.
- **Fix:** Require both s2 ≥ s AND (p2 − s2) ≥ (p − s) for a safe DECIMAL widening, i.e. integer-digit capacity must not shrink.

#### C17 — `scoping.md` — FragmentKindMismatch example has the subtyping direction backwards

- **Section:** Diagnostic codes (Surface) / Call-site fragment validation (Semantics)
- **Dimension:** correctness-consistency · **Implication:** `implementation-impact`
- **Finding:** Both the Surface table and Semantics describe the error as "a bare scalar passed where `SelectItems<Agg>` is expected" (lines 52, 133). But `types.md` defines `SelectItems<Scalar> <: SelectItems<Agg> <: SelectItems<Window>`, so a Scalar value *satisfies* an Agg requirement (subtype substitutes for supertype). Passing a scalar where `SelectItems<Agg>` is expected is legal; the actual error is the reverse — an Agg/Window fragment landing at a position that only admits a lower kind (e.g. WHERE: Scalar only). The example would lead an implementer to reject valid fragments and accept invalid ones.
- **Fix:** Reverse the example: FragmentKindMismatch fires when a fragment's kind is *higher* than the splice point admits (e.g. an aggregate passed where a Scalar-only position is required). Align wording with the kind-ceiling table in types.md.

#### C21 — `virtual_environments.md` — Reuse-soundness invariant contradicts the accept_current escape hatch

- **Section:** Constraints & Invariants / Semantics (Reuse decision)
- **Dimension:** correctness-consistency · **Implication:** `spec-edit-only`

  The combine is specified as `target.event_count + delta.event_count`, `LEAST(target.first_seen, delta.first_seen)`, etc. A partition where a key's summed column is all-NULL yields delta `SUM = NULL`; `target + NULL = NULL` poisons the cumulative value, while full refresh ignores NULLs. `LEAST`/`GREATEST` NULL handling also diverges across backends (Postgres/DuckDB skip NULLs; MySQL and others return NULL), undermining multi-backend portability of the equivalence contract.  
  _Fix:_ Define combiners as NULL-aware: e.g., `combine(a,b) = COALESCE(a+b, a, b)` for SUM-class and NULL-skipping LEAST/GREATEST semantics, and require backends to implement these exact semantics regardless of native function behaviour.
- **NULL values in unique_key break merge matching vs GROUP BY equivalence** — _Cross-partition equivalence_ · solution-quality · `design-decision-needed`  
  Full refresh `GROUP BY` collapses NULL keys into one group, but standard `MERGE ON target.k = delta.k` never matches NULLs, so a NULL-key group inserts a fresh row on every partition step — the claimed equivalence `cumulative_aggregate_run(model, π(S)) == full_refresh(...)` fails for any nullable key column. The Surface example even sidesteps it with `WHERE user_id IS NOT NULL`, but the spec never requires null-safe key equality nor rejects nullable keys.  
  _Fix:_ Specify that merge_into key matching uses null-safe equality (`IS NOT DISTINCT FROM`), or add a classifier/runtime rule that key columns must be non-nullable (with a diagnostic).
- **--auto reversible-aggregator answer contradicts the v1 reprocessing refusal** — _Interaction with `--auto` / staleness_ · correctness-consistency · `spec-edit-only`  
  For reversible aggregators, "v1 returns 'any partition ≥ the earliest stale partition' for safety" — but re-merging any already-merged partition double-counts SUM/COUNT and is refused at planning time per §Reprocessing semantics / Constraint 9, so this answer either corrupts state or dead-ends in a rejection. Only the irreversible bullet adds "force a full refresh if earlier-than-current partitions are stale" — and "earlier-than-current" is undefined for an output with no partition column.  
  _Fix:_ Make both bullets force a full refresh whenever an already-merged partition is stale under the v1 refusal policy, and define "current" as the merged-partition high watermark.
- **Self-referential cumulative is NOT rejected by the driving-source rule as claimed** — _Known Divergences / Open Questions_ · correctness-consistency · `implementation-impact`  
  "Rejected in v1 by the general 'exactly one driving source' rule when the target itself is in the FROM clause." The cumulative target declares no `timeseries:` (the spec forbids it), so in its own FROM clause it is a non-timeseries lookup — the driving-source cardinality stays 1 and `CumulativeMultipleDrivingSources` never fires. An implementer trusting this would admit a model reading its own partially-merged state, producing order-dependent output. Only a generic DAG-cycle check (not cited here) would catch it.  
  _Fix:_ Either cite the actual rejection mechanism (dependency-cycle diagnostic) or add an explicit classifier check: the model's own target must not appear in the inlined FROM clause.
- **GROUP BY forms (ordinals, expressions) are unspecified** — _`unique_key` and column naming_ · clarity · `design-decision-needed`  
  "`unique_key` — the columns named in `GROUP BY`" assumes plain column references. `GROUP BY 1` ordinals (used in models.md's own example) and expressions (`GROUP BY DATE_TRUNC('month', ts)`) are neither admitted nor rejected, and an expression key has no obvious output column name for merge matching. Check 3's partition-column detection (`CumulativeGroupByContainsPartitionColumn`) is similarly undefined for qualified, aliased, or wrapped forms. Implementers will diverge on all of these.  
  _Fix:_ State whether GROUP BY may contain ordinals and expressions; if only plain column references are admitted, add the rejection diagnostic; define how key columns map to projection aliases for merge matching.

#### `timeseries.md`

- **granularity: hour with a DATE partition_column loses sub-day pruning, but is unconstrained** — _Surface / Semantics — "Granularity arithmetic"_ · solution-quality · `design-decision-needed`

It is left unclear whether `Char(5) = Text` holds and via what mechanism, especially since `Char` has semantically distinct padding behaviour in SQL. _Fix:_ State precisely how Char participates: either extend normalize() to fold Char into the string family for equality, or scope the interchangeability claim to Text/Varchar and treat Char distinctly.
- **[Minor]** _[cross-spec · types]_ types.md lists `AmbiguousColumn` as a live code; scoping.md says ambiguity has no dedicated code yet — _Diagnostic codes (user-visible)_. types.md §"Diagnostic codes" lists `AmbiguousColumn` flatly among the checkable codes "from `crates/smelt-db/src/lib.rs::DiagnosticCode`". scoping.md §"Resolution order" step 4 says bare-column ambiguity is "currently surfaced as `UnknownIdentifier` with a hint until a dedicated `AmbiguousColumn` code lands", and Constraints item 7 lists the dedicated `AmbiguousColumn` diagnostic as out of scope for v1. So types.md presents as live a code that the owning resolution spec says is not yet wired for its primary trigger. _Fix:_ Either annotate `AmbiguousColumn` in types.md's catalogue as not-yet-wired-for-bare-column-ambiguity (cross-link scoping.md Known Divergences), or have scoping.md clarify the enum variant exists but is unused for this case.

### `virtual_environments.md`

- **[Minor]** "non-breaking ⇒ reuse downstream" is ambiguous about the changed model itself — _Semantics (Plan categorization)_. Categorization labels a fingerprint-differing model whose change "cannot alter any consumed column" as non-breaking, glossed "⇒ reuse downstream". But the changed model's own fingerprint differs, so M itself must rebuild; only its downstream is spared. The word "reuse" without qualifying "downstream models reuse, M rebuilds" invites a reading where M is reused too, which would be unsound. _Fix:_ State explicitly: "non-breaking ⇒ rebuild M but spare (reuse) its downstream dependents, since no consumed column changes."
- **[Minor]** "A model may narrow but not widen the project posture" — narrow direction undefined — _Surface (state.mode) / Semantics_. The spec says a model may "narrow but not widen the project posture" across stateless/intervals/environments but never defines the ordering or what a narrowed model means for reuse. If a project is environments and a model declares stateless, condition 1 ("A stateless model is never snapshot-reused") fires — but this interaction is never stated, and "narrow" vs "widen" is left to the reader to infer (environments > intervals > stateless). _Fix:_ Define the posture lattice explicitly (environments ⊇ intervals ⊇ stateless) and add one line on the effect: a model narrowed to stateless opts out of reuse even in an environments project.
- **[Minor]** References claims cli.md covers smelt plan/apply, which it does not — _References_. Related specs lists "cli.md (smelt plan/apply/status)". cli.md's command table contains run/build/backbuild/seed/test/diff/.../status but NOT plan, apply, or promote — these commands exist only in this spec (and Known Divergences flags them unbuilt). The cross-reference overstates what cli.md currently owns. _Fix:_ Change to "cli.md (smelt status; plan/apply/promote to be added there when built)" or add the three commands to cli.md's surface.

## Completeness critic — coverage gaps & recommended follow-up passes

The review's own blind spots, surfaced by a final critic agent. These are seams **no reviewer owned** — candidates for a second, targeted review round.

**Coverage gaps**

- INCREMENTAL-ANALYSIS x META/PYTHON-GENERATED BODIES went unowned. incremental_models.md derives lookback/batch-safety from the model's SQL, and several sub-checks (find_inadmissible_over, the NotDerivable refusal gate) explicitly text-scan the *unexpanded outer SQL*. Generator-emitted incremental models (incremental_models.md:315) and any Python-generated model build their body as a meta-constructed TableExpr — whether the SQL-text-based bound derivation and OVER-clause scan see a meaningful body at the time they run is never specified. cluster-time-incremental only caught the frontmatter-location conflict (finding 5), not the analysis-input seam.
- PYTHON_MODELS x INCREMENTAL/TIMESERIES is entirely empty: python_models.md has zero mentions of incremental, timeseries, partition, or materialization-mode constraints, so whether a @model-decorated Python-generated model can be incremental/cumulative, and which spec's rules govern it, is unspecified. No reviewer dimension owned this pair.
- IDENTIFIER QUOTING / ESCAPING IN GENERATED SQL is unspecified corpus-wide and unreviewed. Model names (file stems), seed column names (CSV headers), datagen column names, and meta-language-emitted aliases all flow into generated DDL/SELECT, but no spec states how a name containing a reserved word, space, quote, or non-identifier character is quoted on emission. This is a correctness AND injection-adjacent concern; the per-spec reviewers' three dimensions (solution/clarity/correctness) did not include a security/codegen-safety lens.
- CONCURRENCY / CRASH-ATOMICITY was reviewed only where run_state.md explicitly disclaims it ('single process at a time'). The incremental DELETE+INSERT (non-atomic across DELETE then INSERT on DuckDB), cumulative merge, and CREATE-OR-REPLACE materialization-change path were not reviewed for mid-statement crash / partial-write recovery beyond the spec's own 'idempotent re-run' assertion — and cumulative_aggregate's own reviewer already flagged that retry-after-partial-failure is unspecified, suggesting this seam is broader than one spec.
- SPEC_TEMPLATE CONFORMANCE was checked only ad hoc (several units noted a missing scope callout or Out-of-scope blockquote as individual findings: datagen, diagnostics, function_schema_inference, lsp, schema_evolution, virtual_environments). No agent ran the template as a corpus-wide checklist, so the true rate of missing required sections (Spec-first, Timeless-oracle, Out-of-scope pointers, Related specs) across all 30 specs is unknown — it was sampled, not swept.
- BACKEND-MATRIX CONSISTENCY across specs (which backends each feature supports) was only touched inside schema_evolution (Spark ALTER NULLABILITY) and types (decimal divergences). cli.md hardcodes DuckDB DDL, incremental_models is DuckDB-only with MERGE deferred, cumulative_aggregate references a nonexistent merge_into primitive — but no agent cross-checked the per-feature backend-support claims against a single source of truth (smelt_yml target shape), so contradictory 'supported on Spark/Databricks' claims could persist.

**Recurring corpus themes**

- Two-layer 'derive from SQL, not YAML' doctrine recurs across incremental_models, cumulative_aggregate, timeseries, and the meta-language reducers — but the reviews treated each spec's instance locally; the doctrine's soundness when the SQL itself is *machine-generated* (generator files, Python models, meta-language bodies) is the recurring untested edge.
- 'Owned until diagnostics.md lands' staleness: at least 6 units (functions, planner_integration, scoping, types, ownership-boundaries, cluster-infrastructure) independently flagged the same dead conditional now that diagnostics.md has landed. This is a single corpus-wide find-replace gap, not 6 distinct findings.
- Diagnostic-code drift is the single highest-volume defect class (appears in nearly every unit): retired call-path syntax (smelt.fn vs smelt.functions vs smelt.<path>), codes referenced live in consumer specs but absent/reserved in the owner, and severity disagreements between lsp.md and diagnostics.md. The registry agent caught the catalogue-level cases but per-pair consumer/owner reconciliation was uneven.
- Project-isolation vs 'workspace-scoped' language conflict recurs (diagnostics, lsp, architecture) — a systemic vocabulary drift where specs written before the project-isolation invariant still say 'workspace'.
- Conservative-fallback / sound-upper-bound framing (output_fingerprint determinism, types nullability, incremental batch-safety) is consistently strong and well-reviewed; the gaps are at the *boundaries between* these conservative analyzers and the generative front-ends that feed them.

**Recommended follow-up review passes**

- Run a focused cross-spec review of the seam 'incremental & cumulative rule-analysis inputs vs machine-generated model bodies': for incremental_models.md, cumulative_aggregate.md, python_models.md, meta_language.md (Multi-model production), and timeseries.md, verify that every SQL-text-based or pre-expansion analysis (per-source bound derivation, find_inadmissible_over, the NotDerivable refusal gate, the cumulative driving-source classifier) is well-defined when the model body is emitted by a generator file or a Python @model — including what 'the model's SQL' means before vs after meta-evaluation, and whether the frontmatter-location conflict (file-wide incremental: vs no-file-frontmatter) changes the answer.
- Add a codegen-safety / identifier-quoting review pass (a dimension the original review lacked): audit every spec that lets a user- or data-derived string become a SQL identifier on emission (models.md file stems, seeds.md CSV headers, datagen.md column names, meta_language.md emitted aliases, cli.md CREATE TABLE/CTE names) and determine whether reserved words, whitespace, quotes, and non-ASCII in those names are specified to be quoted/escaped, or are an unhandled injection/parse hazard.
- Sweep all 30 specs against SPEC_TEMPLATE.md as an explicit checklist (Scope callout with Out-of-scope + adjacent-specs pointers, Spec-first blockquote, Timeless-oracle blockquote, Surface/Semantics/Design/Constraints/Known-Divergences/References sections) and produce a single conformance table — replacing the ad-hoc per-spec 'missing scope callout' findings with a complete corpus picture.
- Reconcile diagnostic call-path/syntax drift in one pass: build the authoritative call-path spelling (smelt.<path> vs smelt.functions.* vs smelt.fn.*) from functions.md + architecture.md addressing, then grep every spec for the other two spellings in diagnostic trigger text and message templates; also do the one-shot removal of all 'owned here until diagnostics.md lands' conditionals now that diagnostics.md exists.
- Cross-check per-feature backend-support claims against smelt_yml.md's target shape as the single source of truth: enumerate every 'supported/unsupported on DuckDB/Spark/Databricks/Postgres' assertion across cli.md, incremental_models.md, cumulative_aggregate.md, schema_evolution.md, types.md, and resolve the merge_into / MERGE / ALTER NULLABILITY / CREATE-OR-REPLACE contradictions into a consistent matrix.

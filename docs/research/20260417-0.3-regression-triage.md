## Bug #1: `smelt build` not idempotent

**Reproduction** (workspace: `/tmp/triage_smelt/repro/`, single mart with
`materialization: table`):
```bash
cd /tmp/triage_smelt/repro
rm -f triage.duckdb
/tmp/triage_smelt/venv/bin/smelt build      # OK
/tmp/triage_smelt/venv/bin/smelt build      # fails:
# Catalog Error: Existing object mart_agg is of type Table, trying to drop type View
```

**Code path on main**:
- `crates/smelt-backend/src/lib.rs:82-118` — `Backend::execute_model`. Phase 7
  added `self.drop_view_if_exists(...)` before `self.drop_table_if_exists(...)`
  for the `Materialization::Table` branch (line 95).
- `crates/smelt-backend-duckdb/src/lib.rs:158-161` — `drop_view_if_exists`
  literally executes `DROP VIEW IF EXISTS <name>`. **DuckDB's `IF EXISTS`
  guards on object existence, not on object type**: when the catalog already
  contains a Table by that name, `DROP VIEW IF EXISTS` raises
  `Catalog Error: Existing object <name> is of type Table, trying to drop type View`.
  The Phase 7 fix unconditionally calls `drop_view_if_exists` for `Table`
  materialization, which is exactly the path that explodes.

**Prior fix commit**: `0ed8078` ("Phase 7: …; execute_model: drop both view
and table before creating either type (materialization changes)").

**Released wheel includes commit?**: yes (verified
`git merge-base --is-ancestor 0ed8078 v0.3.0` → 0).

**Classification**: **coverage** — the fix exists but the implementation is
wrong for DuckDB. Phase 7 assumed `DROP <kind> IF EXISTS` is type-tolerant;
DuckDB rejects type mismatches even with `IF EXISTS`.

**What needs to change in Phase B1**:
- Either (a) make `drop_view_if_exists` / `drop_table_if_exists` swallow the
  "object is of type X" Catalog Errors (catch-and-continue), or (b) precede
  the drop with an `information_schema.tables` lookup to discover the actual
  object kind and drop only that, or (c) issue an unconditional
  `DROP <name> CASCADE` via a generic helper after probing the catalog.
  Option (b) is the cleanest — `SELECT table_type FROM
  information_schema.tables WHERE table_schema = ? AND table_name = ?`. The
  same fix is needed for `smelt seed` (Bug #6 in FINDINGS), which uses the
  same path. A regression test should drop+recreate a model whose
  materialization changed from `view` → `table` *and* a re-run of an
  unchanged `table` materialization (the case that breaks here).

## Bug #2: Seeds not resolvable via `smelt.ref()`

**Reproduction** (workspace as above with `seeds/category_lookup.csv` and a
model that does `FROM smelt.ref('category_lookup')`, no `sources.yml`
declaration):
```bash
cd /tmp/triage_smelt/repro
/tmp/triage_smelt/venv/bin/smelt build
# Error: Dependency validation failed
# Caused by: Dependency resolution failed:
#   Model 'stg_categories' references undefined model/source 'category_lookup'
```

**Code path on main**:
- `crates/smelt-cli/src/logical_graph.rs:39-96` — `LogicalGraph::build`. Builds
  `nodes` from SQL models and `sources` from `SourcesConfig` only. Seeds are
  never queried.
- `crates/smelt-cli/src/logical_graph.rs:101-123` — `LogicalGraph::validate`
  emits the exact error message above when a dep is neither a node nor a source.
  This is what the CLI run/build/explain/diff/docs paths all call (see
  `crates/smelt-cli/src/commands/run.rs:138-142`,
  `commands/explain.rs:51-55`, `commands/backbuild.rs:79-83`,
  `commands/diff.rs:67-71`, `commands/docs.rs:48-52`).
- `crates/smelt-db/src/lib.rs:384-405` — `resolve_ref` (the function Phase 6
  changed) **does** include seeds. But this Salsa query lives in `smelt-db`,
  which is consumed by the LSP and the type checker; **the CLI dependency
  validator (`logical_graph.rs`) is a separate code path that was never
  updated**.

**Prior fix commit**: `6fd01b3` ("Phase 6: Seeds as first-class smelt.ref()
targets"). The fix added seed lookups to `smelt-db::resolve_ref` and to the
type-inference `process_table_ref`. It did not touch the CLI logical graph.

**Released wheel includes commit?**: yes (verified ancestor of `v0.3.0`).

**Classification**: **coverage** — Phase 6 fixed the LSP/type-inference
visibility of seeds but missed the CLI dependency validator, which is the
code path the user actually runs.

**What needs to change in Phase B1/B2**:
- Pass the seed list (or seed names) into `LogicalGraph::build`. Cleanest:
  add a `seeds: &[SeedInfo]` parameter alongside the existing
  `sources: Option<&SourcesConfig>`, and have `validate` accept a dep that
  matches a seed name (treated like a source — no upstream node, just exists).
- Wire `discover_seed_infos(&project_dir, &config.seed_paths)` into every
  `LogicalGraph::build` call site (5 commands listed above).
- Regression test: a workspace with a top-level seed referenced via
  `smelt.ref('<seed_name>')` and **no** matching entry in `sources.yml` must
  build cleanly. The Stage A2 e2e test already plans this.
- Bonus: also include seeds as nodes in `smelt explain` output so the graph
  is honest about what runs first.

## Bug #3: Aggregate type narrowing in `_smelt_typed` wrapper

**Reproduction** (workspace as above with one mart `mart_sum_ref` that does
`SUM(line_gross)` on a column from an upstream model):
```bash
cd /tmp/triage_smelt/repro
/tmp/triage_smelt/venv/bin/smelt build
# Error: Failed to execute model: upstream_with_double
#   ... SQL emitted: "SELECT CAST(id AS SMALLINT) AS id, CAST(_col2 AS DECIMAL(2,1)) AS _col2 FROM ( ... )"
#   Binder Error: Column "_col2" referenced that exists in the SELECT clause -
#                  but this column cannot be referenced before it is defined
```

The wrapper inferred `id INTEGER` → narrowed to `SMALLINT` and inferred
`1.5::DOUBLE` → `DECIMAL(2,1)` (it looked at the literal `1.5` instead of
the cast). It also lost the column alias `line_gross` and substituted
`_col2` because `infer_name()` doesn't recognise CAST expressions
(`crates/smelt-parser/src/ast.rs:650-678`). The same path produces the
FINDINGS examples: `SUM(line_gross)`→BIGINT and `SUM(decimal_expr)`→DECIMAL(2,1).

**Code path on main**:
- `crates/smelt-cli/src/compiler.rs:117-162` — `apply_type_casts`. Constructs
  `let ctx = TypeContext::new();` (line 128) — **an empty type context**.
  Then calls `infer_select_column_types(&select_stmt, &ctx)`. Because the
  context has no upstream-model columns, no source columns, and no seed
  columns, every `smelt.ref('upstream').col` resolves to `Unknown`.
- `crates/smelt-db/src/type_inference.rs:574-594` — `SUM` inference. When the
  argument type is unknown (or the argument is missing), the function falls
  through to `DataType::BigInt` (lines 590-593). This is the source of the
  `SUM(line_gross)` → `BIGINT` narrowing the user observed.
- `crates/smelt-db/src/type_inference.rs:569-572` — `COUNT` always returns
  `BigInt`, so the FINDINGS report's `COUNT(DISTINCT order_id)` → `SMALLINT`
  must come from a different path (likely the wrapper inferring the *outer*
  column type from a literal somewhere, or the upstream model's COUNT result
  being mis-typed downstream and then SUMmed). Not yet pin-pointed; Phase B3
  should add a focused regression for it.
- `crates/smelt-dialect/src/type_conformance.rs:20-49` — `wrap_with_type_casts`
  is just plumbing; it faithfully emits whatever types it's handed. The bug
  is upstream in the empty `TypeContext`.

**Prior fix commit**: none — bug #3 was not in the 20260409 plan.

**Released wheel includes commit?**: n/a (no fix exists).

**Classification**: **not actually fixed** (never targeted). The
`_smelt_typed` wrapper has been silently narrowing aggregates since the
wrapper was introduced. The cross-model type tests in
`crates/smelt-db/tests/` exercise `infer_select_column_types` with a
populated `TypeContext`, so they don't catch this — the bug is specifically
that the **CLI's wrapper-emission path constructs an empty context**.

**What needs to change in Phase B3**:
- The CLI compiler must populate `TypeContext` from upstream model schemas,
  source schemas, and seed schemas before calling
  `infer_select_column_types`. This is the same data the LSP/type checker
  already assembles via `db.resolved_model_schema(...)`, but the batch
  compiler can't use Salsa — `apply_type_casts` needs to take `model_schemas:
  &HashMap<String, ResolvedSchema>`, sources, and seeds as parameters.
- Independently, fix `infer_name()` in
  `crates/smelt-parser/src/ast.rs:650-678` to recognise CAST expressions and
  propagate the inner column reference name (`CAST(line_gross AS DOUBLE)`
  with no alias should be named `line_gross`, not `_col2`).
- Defer to DuckDB as the oracle for SUM/AVG/COUNT(DISTINCT) widening rules
  (per the plan's Phase B3 instruction). Property test should use a populated
  context so the bug is caught upstream of the wrapper.
- Until both fixes are in, the wrapper is silently corrupting financial data
  in any model that aggregates a column from an upstream `smelt.ref()`.

## Distribution gap (incidental)

While installing the wheel, the published `smelt-sql==0.3.0` **sdist** is
broken — it doesn't include `crates/smelt-backend-spark/`, so any
`pip install smelt-sql==0.3.0` on a platform without a prebuilt wheel falls
back to the sdist and fails with `failed to read … smelt-backend-spark/Cargo.toml`.
Wheels are only published for cp311 manylinux x86_64/aarch64, cp312 win_amd64,
and cp314 macos arm64 — there is no cp312 / cp313 / cp314 manylinux wheel.
This affects users on Linux + Python 3.12+. Worth fixing as part of the
Stage D release work even though it isn't one of the three bugs.

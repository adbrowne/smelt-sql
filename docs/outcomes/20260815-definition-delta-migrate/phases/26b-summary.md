# Phase 26b summary — per-arm `INTERSECT`/`EXCEPT` mutation-sensitivity classification

**Shipped:**
- `crates/smelt-logical/src/maintenance/grouping.rs`: replaced the blanket `QueryNode::SetOp` early-return collapse with a real per-arm derivation — `classify_arm` (shared by the single-`SELECT` path and each set-op arm), `setop_arm_trees` (pure re-rooting of an already-normalized `SetOpNode`'s branches, hoisting the compound's `ctes`), and `derive_setop_column_groups` (the combination rule: value provenance unions/first-arm-only per output position, membership sensitivity couples every arm's own admission-scope membership plus, for every operator except `UNION ALL`, every arm's raw referenced-source set).
- Fallback (whole-model collapse, fail-closed) for: a mixed-operator chain, an arm that is not itself a plain `SELECT` (defensive — unreachable via the current parser's full chain-flattening, proven by a unit test constructing the tree directly), an arity mismatch across arms, and an arm with its own unresolvable column reference (preserving that arm's own per-column reason).
- Spec: `docs/specs/model_properties.md` §"Per-column mutation-sensitivity / column provenance" gains an "Across set-operation arms" paragraph stating the combination table; its Known Divergences `INTERSECT`/`EXCEPT` bullet is narrowed to filter-distribution only. `docs/specs/incremental_models.md` drops its now-landed "unclassified set operations" bullet.
- Tests: 8 new cases in `crates/smelt-logical/tests/maintenance_grouping.rs` (union-all combination, except-membership-only, intersect-both-legs, union-distinct-vs-union-all membership coupling, mixed-chain/arity-mismatch/unresolvable-ref fallback, a single-`SELECT` regression anchor) + 1 unit test in `grouping.rs` itself for the nested-compound-arm branch, + 1 plan-level test in `maintenance_plan_admission.rs` proving a `UNION ALL` model's plan carries a narrower cell than the old blanket whole-model group.
- Updated `crates/smelt-cli/tests/property_discovery/coverage_matrix_gaps.rs`'s EX-41/EX-42 test (renamed `..._derives_per_arm_provenance`) and `maintenance_plan_conformance.rs`'s `CLAIMED` note to assert the real per-arm verdict instead of the collapse they used to pin.

**Decisions:**
- Fixed a real regression caught only by the full-workspace sweep: switching the single-`SELECT` path's per-column accumulator from `BTreeMap<String, _>` (alphabetized by construction) to a plain `Vec` broke column *order* within a group (select-list position order vs. alphabetical) — `crates/smelt-cli/tests/maintenance_conformance/repair.rs`'s `OrderMonotone`/`DiffPatch` recipe exact-matches a group's `columns` list against a declared write pin, so this silently desynced a targeted write's column list from the table schema. Fixed by keeping the per-column build step keyed through a `BTreeMap<String, BTreeSet<String>>` before bucketing, in both the single-arm and set-op paths — restores byte-identical single-`SELECT` output. **Lesson for future grouping.rs changes: `cargo test --workspace` (not just the plan's named test targets) is load-bearing — this bug never touched a set-op construct itself, only the shared single-arm refactor, and only two conformance tests out of the whole suite exercised the exact-match consumer that caught it.**
- Chose to test the "nested compound arm" fallback (`setop_arm_trees` returning `None`) as a `#[cfg(test)]` unit test inside `grouping.rs` rather than via `derive_column_groups`+real SQL: empirically verified (via throwaway probes, since discarded) that the parser's `normalize()` fully and transparently flattens any parenthesized sub-chain — single or double parens, same or mixed operators — into the enclosing arm chain, so no SQL text can produce a branch that is itself `QueryNode::SetOp`. The guard is real defensive code (a future parser relaxation could reach it) but currently dead through the public API; the unit test documents and locks in that finding rather than skipping the case.

**For the next planner:**
- 26c (hour-granularity propagation) and 26d (finer-than-partition column-group dirt) are next per the table; neither depends on this phase's internals.
- If `normalize()`'s flattening logic is ever changed to preserve nested compound arms (rather than transparently flattening them), `setop_arm_trees`'s `None` branch becomes reachable via real SQL and the unit test in `grouping.rs` should be supplemented (or replaced) with an integration test through `derive_column_groups`.
- Not attempted: widening the set-op combination rule past a single repeated operator (e.g. proper operator-precedence handling of a genuinely mixed `UNION ALL ... EXCEPT ...` chain) — the spec explicitly scopes this phase to the single-repeated-operator shape and states the fallback list as a stated limitation, not a silent one.

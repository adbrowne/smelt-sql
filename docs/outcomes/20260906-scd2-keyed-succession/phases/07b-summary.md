- **Bug fix (production code):** `SuccessionRecipe::from_verdict` (`crates/smelt-logical/src/maintenance/succession.rs`) didn't append the `QUALIFY NOT <flag>` operand's own column into `row_local_projection` — since the model's `SELECT` list never *projects* the delete flag (it's a filter, not an output column), the classifier's `row_local` naturally omitted it, so `emit_succession_event_delta`'s `SELECT` had no `is_deleted` column even though `build_domain_cte` unconditionally references it (`{delete_flag_expr} AS __smelt_is_delete FROM ({event_delta_select}) AS __smelt_batch`). Any real model using `QUALIFY NOT <flag>` failed EVERY run with a DuckDB binder error inside the clock-tie probe. Fixed by appending the flag column to `row_local_projection` (deduped) while still excluding it from `payload_columns`. This had never been exercised end-to-end before phase 7b — 07a's smoke recipes both had `delete_filter: false`.

**Decisions:**
- 2026-09-07: Leg 6 (`repeated_window_application_is_idempotent`) uses a plain (no delete filter) recipe, not a delete-flagged one as first drafted. A delete-flagged refold (re-running a window whose delta already landed a delete once tombstoned) trips `SuccessionClockTie`: `build_domain_cte`'s tombstone-table branch NULLs payload columns for an already-recorded delete, while the SAME event replayed from the physical source in the fresh `event_delta` batch carries its real payload — the tie-signature comparison (`is_delete || payload`) sees `'TRUE|'` vs `'TRUE|bronze'` and calls it a genuine content collision. This looks like a real, separate bug in the probe's domain construction (delete rows' payload should not participate in the tie signature at all, or the tombstone branch should not NULL it), but it's out of this leg's scope — flagged below for the next planner.
- 2026-09-07: Leg 10 (`identical_re_presented_row_is_a_no_op`) does NOT use `drive_succession_window_and_assert_for` for its second (redelivery) step, because the family quartet's oracle (`render_succession_oracle_body_over`) is literally the model's raw SQL over the raw physical source with no dedup: a genuine second physical row at the same `(k, t)` makes the naive oracle emit two (identical) rows where the MERGE-keyed presented table can only ever hold one, so oracle-equivalence is the wrong check for this leg. Drives directly (`insert_row_succession_for` + `run_quiet`) and asserts only that the presented table and tombstone ledger are byte-identical before/after — the actually meaningful claim.

**For the next planner:**
- **Real bug, not yet fixed:** refolding an already-processed window containing a delete-flagged event fails with a spurious `SuccessionClockTie` (see Decisions above). This is a re-run-tolerance regression for any delete-using succession model and should be scheduled — likely a fix in `emit_succession_clock_tie_probe`/`build_domain_cte` (`crates/smelt-logical/src/maintenance/emit/succession.rs`) so a tombstone-branch row's NULLed payload never collides with the batch's real payload for the same underlying event. Serves this outcome's criterion 6 (conformance) and criterion 5 (re-run tolerance) directly.
- Phase 7c (cross-suite widening: `state_deletion.rs`, `repair.rs`, the `deferral` leg) can build directly on today's widened `gate_succession.rs`/`SuccessionRecipe` combinators.
- Not investigated: whether the same payload-NULL-vs-real-payload tie-signature issue also affects the ledger-rebuild path (`--full-refresh`/`smelt repair`) — worth a quick check before or during the delete+refold bugfix above.

## Goal

Make the documented surface and the implemented surface agree across the `smelt.yml` config and the selection-flag tables, and close the one genuine code drift so unknown config keys are *visibly* non-fatal rather than silently swallowed:

- **BUG-046 (docs drift, minor)** — `model_selection.md:45` §Flags lists `backbuild` in the `--select (-s)` "Available on" cell. `crates/smelt-cli/src/main.rs:154-203` `BackbuildArgs` instead takes a **positional** `selector: String` (no `--select`/`-s`, no `--exclude`), and backbuild always forces upstream `+` expansion. The spec over-promises a flag that does not exist. Fix: amend the spec — remove `backbuild` from the `--select` row and add a note that `backbuild` takes a single **positional** selector, always forces `+` upstream, and has no `--exclude`. **No code change.**
- **BUG-059 (docs drift, minor)** — `smelt_yml.md:52-59` §"Model-config shape" lists `materialization`/`incremental`/`tags`/`target` but omits `timeseries`, which `ModelConfig` (`crates/smelt-core/src/config.rs:191-203`) accepts. Fix: add a `timeseries` row to the spec table. **No code change.**
- **BUG-061 (docs drift, minor)** — `smelt_yml.md:22` §"Top-level keys" says `default_materialization` accepts `table, view, ephemeral, materialized_view, test` but omits `cumulative_aggregate`, which the shared `Materialization` deserialiser accepts (`config.rs:31,46`; `default_materialization` is typed `Materialization`). Fix: add `cumulative_aggregate` to the accepted-values list. **No code change.**
- **BUG-060 (code drift, minor)** — `smelt_yml.md` §"Unknown keys" (line ~70) + Semantics §7 (line ~82) already say "an unknown top-level key produces a warning, not an error", but `config.rs:447-463` `parse_with_warnings` only warns for the two legacy keys `model_paths`/`seed_paths`, and `Config` (config.rs:73-97) has no `deny_unknown_fields`, so any other unknown top-level key (e.g. the typo `default_matrialization:`) is silently dropped with **no** warning. Fix (code): make `parse_with_warnings` iterate the raw YAML top-level map against the known-key set and emit a warning for each unrecognised key — **not** an error, and **not** via `deny_unknown_fields` (forward-compat must hold; Constraints §3).

## Design decisions (resolved — do not re-litigate)

- **Spec-first, but the spec edits here are *corrections*, not *changes*.** Every P1 edit aligns prose with already-shipped code (the `Config`/`ModelConfig`/`BackbuildArgs` structs are the source of truth per smelt_yml.md Constraints §1). There is no behaviour change in P1, so no code, no fixtures, no gates beyond a docs build — these rows are pure documentation reconciliation. They are grouped into one phase because they are independent one-line table edits with no ordering between them.
- **BUG-060 stays a WARNING, never an error, and never `deny_unknown_fields`.** smelt_yml.md Constraints §3 and Semantics §7 make forward-compatibility load-bearing: a newer project that adds a top-level key must keep parsing on an older binary, with the field absent. `deny_unknown_fields` would turn that into a hard parse error and foreclose staged rollouts. So the fix is a *post-parse audit* of the raw YAML top-level mapping against an explicit known-key allow-list, emitting a warning string per unknown key — the same channel the legacy-key warnings already use.
- **The known-key allow-list is the seven `Config` struct keys plus three caveats.** The `Config` top-level keys are `name`, `version`, `paths`, `targets`, `default_materialization`, `models`, `python`. The allow-list must **also** include: the two legacy keys `model_paths` and `seed_paths` (already warned-about separately — they must not *also* trip the generic unknown-key warning, or a legacy file gets a doubled warning), and `unstable_schema` (documented at `smelt_yml.md:25`, read by the separate text helper `parse_unstable_schema_flag` and **not** a `Config` struct field — without allow-listing it, a perfectly valid `unstable_schema: true` would false-positive as unknown). Miss any of these three and the fix produces spurious warnings on valid configs.
- **Keep the legacy-key warnings distinct from the generic one.** `model_paths`/`seed_paths` already get a *targeted* warning ("Use `paths:` instead …"). The generic unknown-key warning must skip them so the user sees the helpful migration hint, not a generic "unknown key" line. Implement by allow-listing them (so the generic pass ignores them) while leaving the existing targeted pass intact.
- **Warning text is informative, names the key, and points at the spec.** Mirror the existing legacy-key warning style: `warning: smelt.yml: unknown top-level key '<key>' (ignored). See smelt_yml.md §Top-level keys.` The exact wording is not load-bearing; the test asserts a warning *mentioning the offending key* exists, not an exact string.
- **No new public API.** The fix is internal to `parse_with_warnings`, which already returns `(Config, Vec<String>)`. Callers already surface the warnings; the new warnings flow through the existing channel for free.

## Per-phase routine
1. **Pre-flight.** `cargo test --quiet 2>&1 | tail -40`. If red, check **what** is red: if the failure is this phase's own acceptance target (the test this phase exists to make green), that is expected — **proceed**. If the red is unrelated breakage, treat it as a block (record + continue, per §"Block conditions"); do not build on a broken baseline. (P1 is docs-only — pre-flight is informational there.)
2. **Spec increment** (only the phases that list one — P1's three table edits and P3's Known-Divergence retraction): edit the named spec section first; keep it timeless (no phase/ledger vocabulary in the spec body). Then update any drifting `docs-site/` mirror named in §Docs.
3. **Red-green `/smelt:implement`** (P2 only): write the failing unit test(s) first, then the implementation, spec as oracle. Implementer pass, then reviewer pass (material findings only). P1 and P3 carry no code; their "test" is the docs build (`cd docs-site && uv run mkdocs build`) and a visual diff of the edited tables.
4. **Verify.** `cargo fmt --all`; `cargo clippy --all-targets` (zero warnings); `cargo test` green; plus the dual gate: `cargo test -p smelt-cli --test example_diagnostics` **and** `cargo test -p smelt-lsp --test example_workspaces`. For P2 the most direct gate is `cargo test -p smelt-core` (where the `parse_with_warnings` unit tests live). For docs-only phases (P1, P3), the gate is the mkdocs build succeeding and the example gates staying green (no regression).
5. **Record + commit.** Update the status-table row to `done` + date; commit and push tests + impl + spec/docs + table together with the phase's commit message. Emit `<<PHASE_COMPLETE>>` (or `<<ALL_DONE>>` on the last green phase).

## Block conditions (`<<PHASE_BLOCKED>>` — record and continue, no hard-stop)
When a phase hits a condition below, **do not halt**. Instead: (1) set the row to `blocked` with a one-line reason; (2) append a dated entry to §"Blocked phases" (phase id, reason/decision, candidate options); (3) restore the tree to a clean committed state; (4) commit + push; (5) emit `<<PHASE_BLOCKED>>`. The next iteration skips the blocked row.

Conditions:
- The phase needs a design decision **not** answered by this plan (the decisions above are settled) or the spec — e.g. it turns out a `backbuild --select` flag *does* exist on a different code path than `BackbuildArgs`, so the spec was right and the bug is mis-filed; or the unknown-key warning surfaces a key that is legitimately consumed somewhere outside `Config` and the allow-list needs a product call.
- Pre-flight is red on **unrelated** breakage (not this phase's own target).
- The tree can't be returned to green after the phase.

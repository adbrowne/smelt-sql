## Goal

Make the spec's **strict-by-default family rejection** real for the binary arithmetic operators, end to end — degrade the type *and* surface the diagnostic:

- **BUG-017 (correctness, major)** — `SELECT 42 + '3'` today infers `SMALLINT` (the left operand type) instead of the spec-mandated `Unknown`, and emits **no** diagnostic. The compiler silently synthesises an implicit cast across the numeric/string family boundary — exactly the behavior §1 forbids and §14 tables as `Unknown` + `TypeMismatch`. The fix has two halves, both in scope:
  1. **Degrade the type.** A cross-family operand pair (e.g. numeric + string, boolean + numeric) on `+`, `-`, `*`, `/`, `%` must resolve to `DataType::Unknown`, never the left operand's type. No implicit cross-family cast.
  2. **Emit the diagnostic.** Per §14, the cross-family case must raise exactly one `TypeMismatch` anchored at the operator span. This deliberately pulls in a slice of the deferred no-silent-`Unknown` enforcement (`types.md:~296`) — but **only** for the binary arithmetic operators (see Design decisions).

## Design decisions (resolved — do not re-litigate)

- **Full scope: degrade *and* diagnose.** The fix is not merely "stop returning SMALLINT." Halving it (degrade to `Unknown` with no diagnostic) would convert a wrong-type bug into a silent-`Unknown` bug — itself a §296 invariant violation. §14 names `TypeMismatch` explicitly, so the diagnostic is part of the acceptance criteria, not a follow-up.
- **Mirror the family-aware promotion that already exists.** Binary arithmetic uses its **own** helper `promote_numeric_operands` (`crates/smelt-db/src/type_inference/binary.rs:29`), called from the `+` arm (`binary.rs:154`), the `*`/`/`/`%` arm (`binary.rs:186`), and the binary `-` arm. Its bug is the catch-all `(Some(l), _) => Some(l)` (`binary.rs:63-66`): when neither operand matched a numeric priority (e.g. left numeric, right `Text`), it returns the **left** type with no family check. The family-aware sibling to mirror is `promote_types` (`crates/smelt-db/src/type_inference/dispatch.rs:542`), whose family guard (`dispatch.rs:585-588`, via `DataType::is_numeric`/`is_string`/`is_temporal` at `crates/smelt-types/src/lib.rs:93,106,122`) falls through to `DataType::Unknown` (`dispatch.rs:639/643`) when families don't match. P1 either routes the arithmetic arms through `promote_types` or adds the same `is_numeric`/`is_string`/`is_temporal` family guard to `promote_numeric_operands` so a cross-family pair yields `Unknown`. Numeric/numeric promotion and the existing `INTERVAL * numeric` / `INTERVAL / numeric` special cases (`binary.rs:160-185`) must keep working unchanged.
- **Scope the no-silent-`Unknown` enforcement to the arithmetic operators only — do not silently widen it.** The sibling strict paths (array literal `composite.rs:56-59`, UNION) today **do not** actually emit `TypeMismatch` — they degrade to `None` → `CannotInferType`, which is the admitted gap the §296 Known Divergence tracks. This plan emits `TypeMismatch` for **cross-family binary arithmetic only**. Whether to extend consistent `TypeMismatch` emission to the array-literal/UNION composite paths is **explicitly out of scope here** and remains tracked in `docs/plans/20260519-functions-meta-gaps.md`. P3's spec edit narrows the §296 line to reflect that the arithmetic-operator case is now enforced while the composite paths are not — it does **not** delete the divergence.
- **Diagnostic anchor: the operator span.** §14 reads as "the operation is rejected"; the natural anchor is the binary operator token. P2 anchors the single `TypeMismatch` there. If the existing diagnostic plumbing in `binary.rs` cannot cleanly reach the operator token's `TextRange` (the inference path may currently thread only types, not spans, into this arm), that is a plumbing question answered by the surrounding code, not a product call — wire the span through. If it turns out the operator span genuinely isn't recoverable without a structural change to the inference signature, block for review.
- **Proptest exposure is LOW (verified) — re-validate, don't pre-register a divergence.** The `BinaryOp` generator (`crates/smelt-db/tests/prop_helpers/generators.rs:989-1026`) filters arithmetic operands to `is_numeric()` only (lines 990-993) and only emits `||` between two `is_string()` columns (1019-1024); it **never** generates Numeric+String arithmetic, so the DuckDB oracle never exercises this path, and `divergences.rs` has no conflicting entry. No new `divergences.rs` entry is **expected**. The proptest gate is still a mandatory acceptance check (256-case + `PROPTEST_CASES=1000`); **if** a regression surfaces, add a `divergences.rs` entry per the CLAUDE.md guidance and document it in the phase. A failure that needs a divergence judgment beyond a mechanical add is a block.
- **Salsa purity holds.** The change is to pure inference logic in `type_inference/`; no Salsa query shape changes. Diagnostics already flow through the existing file/type-diagnostic surface — P2 routes the new `TypeMismatch` through that same path, it does not invent a new query.

Conditions:
- The strict fix breaks the green example suite or the proptest in a way that needs a `divergences.rs` judgment **beyond a mechanical add** (e.g. the oracle and smelt genuinely disagree on a *numeric/numeric* case the family guard now routes differently) — that is a type-semantics call, block for review.
- The operator span genuinely isn't recoverable for the `TypeMismatch` anchor without changing the inference function signature in a way this plan didn't scope (P2's anchor decision).
- A request to widen scope to the sibling composite paths (array literal / UNION) surfaces — that is explicitly deferred to `20260519-functions-meta-gaps.md`; record and continue.
- Pre-flight is red on **unrelated** breakage (not this phase's own target).
- The tree can't be returned to green after the phase.

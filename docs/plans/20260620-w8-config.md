### Phase P1: `format` in `ModelConfig` + three-tier precedence `get_format` (D-32)

**Goal.** `smelt.yml` `models.<name>` entries accept a `format: delta|parquet` field. A new `Config::get_format` method resolves the three-tier precedence: SQL frontmatter `format:` (from `ModelMetadata.format`) > `smelt.yml` `models.<name>.format` > `targets.<name>.format` (Spark default `delta`). The override wins over the target, matching the `materialization:` precedence pattern. (`smelt_yml.md` §"Model-config shape", §"Precedence rules" rule 5; `models.md` §"YAML frontmatter keys" — `format` row.)

**Critical files.** `crates/smelt-core/src/config.rs` — add `pub format: Option<TableFormat>` to `ModelConfig` (around line 211); add `pub fn get_format(&self, model_name: &str, sql_metadata: Option<&ModelMetadata>, target: &Target) -> Option<TableFormat>`. Then audit call sites with `rg -n "\.format\b" crates/smelt-runtime/src/ crates/smelt-cli/src/` and route them through the new method.

**Test idea.** In `config.rs` unit tests: a model with `format: parquet` in `smelt.yml` model config and a Spark target defaulting to `delta` → `get_format` returns `Parquet`. Frontmatter `format: delta` overrides the model config `format: parquet`. A DuckDB target always returns `None` regardless of model config. Absent format at all tiers returns `None` for DuckDB and `Some(Delta)` for Spark (inheriting target default).

### Phase P2: Reject `default_materialization: test/cumulative_aggregate` at load time (D-33)

**Goal.** A `smelt.yml` with `default_materialization: test` or `default_materialization: cumulative_aggregate` is rejected at project-load time with a clear validation error — not silently accepted. Only `table`, `view`, `materialized_view`, and `ephemeral` are legal as the project-wide default. The rejection must be a **hard error** (not a warning), surfaced by `Config::parse_with_warnings` or a new `Config::validate_project_defaults` method called from `Config::load`. (`smelt_yml.md` §"Top-level keys" `default_materialization` row; §"Semantics §8".)

**Critical files.** `crates/smelt-core/src/config.rs` — add project-default validation in `Config::parse_with_warnings` or as a post-parse step in `Config::load`. The `Materialization` enum already deserialises `test` and `cumulative_aggregate` without error (they are valid per-model values); the rejection must happen at the *project default* level, not at the serde layer. Return a `serde_yaml::Error`-compatible error or convert to an `anyhow::Error` with a clear message naming the forbidden value and the spec rule.

**Test idea.** In `config.rs` unit tests: `default_materialization: test` in a full valid config → `parse_with_warnings` returns `Err` naming the forbidden value. Same for `cumulative_aggregate`. `default_materialization: ephemeral` parses without error (ephemeral is a defensible default per Semantics §8). `default_materialization: table` / `view` / `materialized_view` all continue to parse cleanly.

### Phase P3: Add `state:` to `KNOWN_KEYS`; suppress spurious unknown-key warning (D-34)

**Goal.** A `smelt.yml` that includes a top-level `state:` block does not produce a spurious `warning: unknown top-level key 'state'` message. Add `"state"` to the `KNOWN_KEYS` slice in `Config::parse_with_warnings` (currently around line 490 of `config.rs`), alongside the already-present `"vars"`. No changes to the `Config` struct are needed — `state:` remains out-of-band, consumed by `virtual_environments`-level logic, just like `vars:` is consumed by `smelt-db::config_vars`. (`smelt_yml.md` §"Top-level keys" `state:` row; §"Known Divergences" — "User-extensible top-level keys" note.)

**Critical files.** `crates/smelt-core/src/config.rs` lines ~490–503 — the `KNOWN_KEYS` slice in `parse_with_warnings`. One-line change: add `"state"` to the array.

**Test idea.** Extend the existing `valid_config_with_all_known_keys_emits_no_generic_warnings` test (currently around line 1449) to include a `state:` block in the YAML input and assert zero warnings. Add a standalone test `state_key_does_not_warn` confirming a minimal config with `state: { mode: stateless }` produces no unknown-key warning. Confirm `vars:` still produces no warning (regression guard).

# Plan: smelt-shop 0.3 Follow-up Fixes (Iterative)

## Context

The smelt-shop reporting pipeline was re-implemented against `smelt-sql==0.3.0`
to verify that the fixes from `20260409-smelt-shop-fixes.md` actually shipped.
The full report lives at `~/smelt_shop/FINDINGS.md`. The pipeline builds and
`validate.py` reports 21/21 acceptance checks, but only after applying
significant workarounds. Three bugs the prior plan **claimed to fix in Phase 6
and Phase 7 are still present in the released wheel**, plus a new
type-narrowing bug surfaced that the prior plan did not cover.

The prior plan failed because its tests passed before the user's workspace
did. **This plan is structured as a loop**: fix → re-run the spec
implementation in a fresh worktree via a sub-agent → diff the new findings →
fix again. Exit when a sub-agent can implement the spec from scratch with
zero workarounds against a freshly-built wheel.

**Each iteration starts from a clean baseline.** `~/smelt_shop` is a git
repo. Before any sub-agent runs we collapse the repo down to just the spec
and the bare uv setup (everything the user wrote is removed); the sub-agent
gets a git worktree of that baseline branch and never sees the previous
attempt's models, seeds, or findings. This is the only way to be sure each
loop iteration is testing the wheel and not accumulating artefacts from prior
runs.

## Bugs to address (initial list from FINDINGS.md)

| # | Bug | Prior status | Severity |
|---|-----|--------------|----------|
| 1 | `smelt run` not idempotent — `DROP VIEW IF EXISTS` then `CREATE TABLE` collides | Allegedly fixed in 20260409 Phase 7, still broken in 0.3.0 | **Critical** |
| 2 | Seeds not resolvable via `smelt.ref()` — dependency resolver ignores them | Allegedly fixed in 20260409 Phase 6, still broken in 0.3.0 | **Critical** |
| 3 | `_smelt_typed` wrapper narrows aggregate types: `SUM(double)`→`BIGINT`, `SUM(decimal)`→`DECIMAL(2,1)`, `COUNT(DISTINCT)`→`SMALLINT` | Not in prior plan | **Critical (silent data loss)** |
| 4 | `smelt-datagen` geometric default emits zeros; `min` not in `--help` | Parameter added in 20260409 Phase 7, default + UX still poor | Medium |
| 5 | `smelt run --dry-run --verbose` is silent and exits 0 even when live run fails | Not in prior plan | Medium |
| 6 | `smelt seed` does not clean up on CSV schema change (same root cause as #1) | Subsumed by #1 | Medium |
| 7 | Spec docs say `COALESCE(col, 'ALL')` for CUBE rollup, which collides with real NULLs | Doc gap | Low |

Bug #3 is the most consequential because it silently truncated `net_revenue`
from $10.8M to integer dollars and zeroed a 6 % `return_rate`. Tests passed
locally because the workaround (manual `CAST(... AS DOUBLE)` on every
aggregate) hid the issue.

## Cross-cutting principles

1. **Tests must use the compiled CLI binary**, not `smelt-cli` as a library.
   The prior plan's library-level tests caught none of bugs #1, #2, or #3.
2. **No fix counts as done until the loop validates it** — the sub-agent
   re-implements the spec in a clean worktree against a freshly-built wheel
   and reports zero workarounds for that bug.
3. **Treat the FINDINGS report as authoritative**; if a fix lands but a new
   FINDINGS report still complains, the fix is incomplete.

## Stage A — Triage & Scaffold (run once)

### Phase A0: Reproduce & triage `[ ]`

**Goal**: Before changing code, confirm exactly what the released 0.3.0 wheel
does versus what `main` does. The prior plan was marked complete, so either
the fix was reverted, the fix was on a branch that never released, or the fix
addressed a different code path than the smelt-shop usage.

**Work**:

  reproduce each bug from FINDINGS.md against `~/smelt_shop/`. Capture exact

  - Bug #2: `smelt-db/src/lib.rs::resolve_ref` and seed discovery — does

  - Bug #3: `smelt-db/src/type_inference.rs` SUM/COUNT/COUNT(DISTINCT)

  `docs/research/20260417-0.3-regression-triage.md`.

**Exit criteria**: For each of bugs #1, #2, #3 we know whether this is a

- `.claude/skills/smelt.md` — the skill the user wants kept up to date.

**Files to remove on `baseline`** (everything from the prior solution):
- `models/`, `seeds/`, `sources.yml`, `smelt.yml`, `datagen.yaml`
- `load_raw.py`, `validate.py`, `main.py`

- `FINDINGS.md` (kept separately; see below)

**Process**:
- Stash a copy of the current `FINDINGS.md` into the smelt-sql plan

- `cd ~/smelt_shop && git checkout -b baseline && git rm -r <files-to-remove>

- Verify: a `git ls-files` on `baseline` shows only the keep-list above.
- Tag this commit `baseline-v1` so we can compare across iterations if the

**Exit criteria**: `baseline` branch exists with only the keep-list files;

### Phase A2: End-to-end regression scaffold `[ ]`

**Goal**: A *failing* test that runs the compiled `smelt` CLI twice against a

**Work**:

  - `typeof(net_revenue) = 'DOUBLE'` in DuckDB

**Exit criteria**: Test compiles and fails with messages matching FINDINGS.md

## Stage B — Fix Phases (run sequentially)

Each phase has a green-bar criterion (its own tests + the Stage A1 e2e test
making forward progress). Do not move on until green.

### Phase B1: Idempotent build (bugs #1 + #6) `[ ]`

**Likely root cause**: `DROP VIEW IF EXISTS` runs unconditionally before
`CREATE OR REPLACE TABLE`; DuckDB rejects type-mismatched drops even with
`IF EXISTS`. Confirm in A0.

**Work**:
- In `smelt-backend/src/lib.rs::execute_model`, unconditionally `DROP TABLE
  IF EXISTS` and `DROP VIEW IF EXISTS` before any `CREATE`.
- Same treatment for `smelt seed`.
- Unit test: model created as `view`, switched to `table`, re-run succeeds.
- Re-test `~/smelt_shop/` with the freshly-built wheel.

**Exit criteria**: Stage A1 idempotency assertion passes; `smelt build` runs
twice in `~/smelt_shop/` without `rm smelt_shop.duckdb`.

### Phase B2: Seeds as ref targets (bug #2) `[ ]`

**Work**:
- Implement the missing branch in `resolve_ref` / `all_seeds` so a top-level
  `seeds/<name>.csv` is a valid `smelt.ref('<name>')` target without a
  `sources.yml` declaration.
- Make sure seeds appear as nodes in `smelt explain`.
- Update `docs-site/docs/guide/seeds.md` to match the actual behaviour.

**Exit criteria**: Stage A1's seed-ref portion passes; the user's
`category_hierarchy` reference resolves without the `sources.yml` workaround.

### Phase B3: Aggregate type narrowing (bug #3) `[ ]`

**Goal**: The `_smelt_typed` wrapper never narrows an aggregate result.
Most consequential bug — silently corrupts financial data.

**Work**:
- Regression tests in `smelt-db/tests/`:
  - `SUM(x)` where `x: DOUBLE` → `DOUBLE`
  - `SUM(x)` where `x: DECIMAL(p, s)` → `DECIMAL(38, s)` (DuckDB semantics)
  - `SUM(a * b)` with decimal `a, b` → preserves widened intermediate
  - `COUNT(*)` and `COUNT(DISTINCT x)` → `BIGINT`
  - `AVG(x)` where `x: INTEGER` → `DOUBLE`
- Audit SUM/COUNT/AVG/MIN/MAX in `smelt-db/src/type_inference.rs`.
- Audit the `_smelt_typed` wrapper emission in
  `smelt-backend/src/compiler.rs`.
- Extend the property test (`prop_type_inference`) to cover aggregates with
  the DuckDB oracle.
- Wire into Stage A1 so `typeof(net_revenue) = 'DOUBLE'` passes.

**Exit criteria**: All new aggregate tests green; property test green;
e2e monetary-sum assertion green.

### Phase B4: Dry-run visibility (bug #5) `[ ]`

**Work**:
- `smelt run --dry-run --verbose` should either print planned SQL or surface
  the same diagnostics as a real run; either way, exit non-zero on errors.
- CLI integration test: workspace with one bad model, dry-run exits non-zero
  with a useful stderr message.

### Phase B5: Datagen ergonomics (bug #4) `[ ]`

**Work**:
- Default `min` for geometric to a sensible value (1?) — discuss with user
  before merging.
- Add `min` to `smelt-datagen --help` per-generator output.
- CLI test asserts `--help` mentions `min` for `geometric`.

### Phase B6: Docs — CUBE/COALESCE pattern (bug #7) `[ ]`

**Work**:
- Replace `COALESCE(col, 'ALL')` recommendation with
  `CASE WHEN GROUPING(col) = 1 THEN 'ALL' ELSE col END` in
  `docs-site/docs/guide/sql-models.md`.
- Audit internal example workspaces for the same foot-gun and fix.

## Stage C — Validation Loop (repeat until clean)

This is the iterative core. Each iteration: build a wheel, hand it to a
sub-agent in a clean worktree, let the sub-agent re-implement the spec from
scratch, then diff the new FINDINGS report against the bugs we believe are
fixed.

### Phase C0: Build candidate wheel `[ ]`

**Work**:
- From the smelt-sql repo, build a local wheel:
  `cd python && uv build` (or `maturin build --release`).
- Note the wheel path and a short version tag, e.g.
  `smelt_sql-0.3.1.dev$(date +%s)-...whl`.
- This is the artifact the sub-agent will install.

### Phase C{n}-reset: Reset smelt_shop to baseline `[ ]`

**Goal**: Before every sub-agent iteration, ensure the sub-agent's worktree
will be created from the pristine `baseline` branch — no models, seeds,
findings, or `.duckdb` artefacts from prior iterations.

**Work** (orchestrator runs these in `~/smelt_shop`):
- Remove any leftover worktrees from prior iterations:
  `git worktree list` → for each `iter-*` worktree, `git worktree remove
  --force <path>` and `git branch -D iter-<n-1>` if present.
- Confirm `baseline` is unchanged: `git diff baseline-v1..baseline` is empty.
  If not, the loop has corrupted the baseline — stop and escalate.
- Create the per-iteration worktree:
  `git worktree add /tmp/smelt_shop_iter_<n> baseline -b iter-<n>`.
- The sub-agent will operate in `/tmp/smelt_shop_iter_<n>`. Pass that
  absolute path into the prompt below.

**Exit criteria**: A clean worktree exists at the iteration path containing
only the baseline keep-list files; no `.smelt/` or `.duckdb` carry-over.

### Phase C{n}: Sub-agent spec re-implementation `[ ]`

**Goal**: A fresh sub-agent, with no memory of this plan, implements the
spec from scratch in the clean worktree using the candidate wheel and
produces a new findings report.

**Spawn** with `Agent(subagent_type="general-purpose")`. We do **not** use
the `Agent` tool's built-in `isolation: "worktree"` here, because that
isolates the *smelt-sql* repo, not `~/smelt_shop`. The git-worktree-of-
`~/smelt_shop` from Phase C{n}-reset is what isolates the sub-agent's
working area.

**Sub-agent prompt template** (self-contained — the sub-agent has no memory
of this plan):

```
You are implementing the spec at <ITER_WORKTREE>/spec.md from scratch.

WORKING DIRECTORY: <ITER_WORKTREE>
Stay inside this directory. It is a fresh git worktree containing only the
spec, the bare uv setup, and CLAUDE.md — there is no prior solution to
build on. Do NOT cd elsewhere; do NOT touch the smelt-sql source tree.

SETUP:
1. The candidate smelt-sql wheel is at <ABSOLUTE_PATH_TO_WHEEL>. Install it
   into this worktree's venv. The recommended path is to add a local file
   dependency in pyproject.toml:
     [tool.uv.sources]
     smelt-sql = { path = "<ABSOLUTE_PATH_TO_WHEEL>" }
   then run `uv sync`. Confirm `uv run smelt --version` matches the wheel.
2. Use uv, python, smelt-sql. Smelt docs are at smeltsql.com.
3. Read spec.md and implement it end-to-end. You will need to write your own
   data loader, datagen config, models, seeds, sources, and validation
   script. Treat this as a greenfield implementation — there is intentionally
   no prior solution in the worktree.

DELIVERABLES:
- A working pipeline: `smelt build` runs cleanly twice in a row without
  deleting the .duckdb file, and your validation script passes 21/21
  acceptance checks from the spec.
- A NEW FINDINGS report at FINDINGS_<ITERATION>.md in the worktree root,
  written from scratch. For each issue found:
  * Reproduce the failure with exact commands.
  * Note the workaround you applied (if any).
  * Severity: critical / major / minor.
- Do NOT silently work around problems — every workaround must appear in
  the report. If you used a manual CAST to defeat a type-narrowing bug,
  that goes in the report.

CONSTRAINTS:
- Stay inside the worktree directory. Do not modify the smelt-sql source.
- Do not edit spec.md.
- Do not consult prior FINDINGS reports — this run is independent. The
  orchestrator will diff your report against historical reports.
- Report length: <= 2 pages.

When finished, print the absolute path to FINDINGS_<ITERATION>.md and stop.
```

**After the sub-agent returns**, the orchestrator must:
- Read `FINDINGS_<n>.md` directly from the worktree path (do not trust the
  agent's stdout summary).
- Diff against the bug table at the top of this plan.
- For each bug: mark fixed, still-broken, or new. Update the table here with
  iteration markers (e.g. `#1: fixed in C2`, `#3: still-broken after C2`).
- Copy `FINDINGS_<n>.md` into
  `docs/plans/20260417-smelt-shop-0.3-followup-findings/<n>.md` so the
  history of attempts is preserved in the smelt-sql repo even after the
  worktree is removed.
- If the sub-agent could not finish the spec, capture the blocker and treat
  it as a new bug.

### Phase C{n}-fix: Address new/remaining findings `[ ]`

**Work**:
- For each "still-broken" or "new" bug from the latest sub-agent report,
  add a sub-phase here (`B7`, `B8`, ...) following the same red-green
  template as B1–B6: regression test against the compiled binary first,
  then fix, then green.
- Rebuild the wheel (Phase C0 again).
- Run Phase C{n+1}-reset, then Phase C{n+1}.
- Tear down the prior worktree only **after** copying FINDINGS_<n>.md into
  the smelt-sql repo (see C{n} step above).

### Loop exit criteria `[ ]`

The loop exits when **all** of the following hold for one full sub-agent
iteration:
- The sub-agent completed the spec without any workarounds (the report's
  "workarounds" section is empty).
- `smelt build` succeeds twice in a row in the sub-agent's worktree.
- `validate.py` reports 21/21.
- No "new" or "still-broken" entries in the latest FINDINGS report.

**Iteration cap**: 5. If we hit 5 iterations without exiting, stop and
escalate to the user — something structural is wrong with the approach,
not just individual bugs.

## Stage D — Release `[ ]`

Once Stage C exits cleanly:
- Bump version, generate changelog from this plan + git history.
- Build wheel + sdist; publish to TestPyPI first.
- One final clean-room sub-agent iteration against the *published* TestPyPI
  wheel (not the local build) — same prompt, same exit criteria. This
  catches packaging bugs that local builds hide.
- Publish to PyPI proper.
- Update the smelt skill in the user's `~/smelt_shop/CLAUDE.md` with notes
  on what the new release fixes.

## Orchestrator notes

- **Per-iteration isolation**: each Phase C iteration runs in a fresh
  `git worktree add` of the `baseline` branch of `~/smelt_shop`. The
  worktree path (`/tmp/smelt_shop_iter_<n>`) is substituted literally into
  the sub-agent prompt. **Do not** rely on the `Agent` tool's
  `isolation: "worktree"` parameter — that isolates the smelt-sql repo, not
  `~/smelt_shop`.
- **Baseline integrity**: the `baseline` branch must be byte-identical
  across iterations. Before each reset, verify
  `git diff baseline-v1..baseline` is empty. If a sub-agent ever ends up
  modifying `baseline`, stop the loop.
- **Wheel path passing**: the orchestrator computes the absolute path of
  the freshly-built wheel and substitutes it into the sub-agent prompt
  literally — sub-agents have no shared filesystem state across runs.
- **Report archival**: copy each `FINDINGS_<n>.md` from the worktree into
  `docs/plans/20260417-smelt-shop-0.3-followup-findings/<n>.md` *before*
  removing the worktree. This is the only durable record once the worktree
  is gone.
- **Report parsing**: the orchestrator reads the sub-agent's
  `FINDINGS_<n>.md` directly (not the sub-agent's stdout summary), since
  agent summaries are not authoritative.
- **Don't repeat the prior plan's mistake**: a green internal test suite is
  necessary but not sufficient. The loop is the gate.
- **When in doubt about types** (Phase B3), defer to DuckDB:
  `SELECT typeof(SUM(x::DOUBLE)) FROM ...` is the oracle.

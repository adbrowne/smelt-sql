## Goal

Make the spec's **one-path-one-entity** rule real, and pay down the structural debt that made it (and its sibling asymmetric-discovery bugs) possible:

- **BUG-002 (correctness, major)** — a workspace where two files resolve to the same `smelt.<path>` (the canonical repro: `models/dup.sql` model + `models/dup.csv` seed) currently loads silently, emits one entity, and drops the other with no diagnostic; `smelt explain --json` exits 0. The spec mandates a hard workspace-load error. Enforce it across **all kinds** (model/function/seed/source) via a single Salsa authority, surfaced identically in CLI and LSP.
- **BUG-063 (architectural, major)** — "discover the entities of a smelt project from disk" is reimplemented in `smelt-core`, `smelt-db`, **and** `smelt-cli` (`cli/seed.rs::discover_seeds` is a third seed-discovery path). This divergence is the direct cause of the BUG-005/006/011/015/019/024 asymmetric-discovery family. Consolidate onto the new address-map authority; delete the CLI-side path.
- **BUG-064 (layering, minor)** — `smelt-db` declares `smelt-planner` as a **production** dependency (planner→db is dev-only), inverting the documented stack. Find the leaked `smelt_planner::` item and sink it down to `smelt-core`/`smelt-types`, dropping the edge.

## Design decisions (resolved — do not re-litigate; from the spec + the layer analysis in `docs/bug-hunt/2026-05-30-findings.md` BUG-002)

- **Enforcement lives in Salsa, not in eager `load_workspace`.** The collision is cross-kind (model is eager, seed/source are Salsa-discovered) and `smelt-core` does not (and must not) depend on `smelt-db`, so the eager loader structurally cannot see the lazy set. Putting the check in Salsa is the deliberate choice: it makes CLI↔LSP parity hold *by construction* (both consume the same query) instead of by syncing two discovery passes. This supersedes the old "must not depend on Salsa for the collision check" framing.
- **Identity is one authority; schema hangs off it.** The collision is a purely *structural* fact about the **set of addresses**. The collision query must depend only on an **address-only** projection of each entity, never on schema (seed columns, source column types). This firewall is cheap via Salsa backdating: even if the rich `project_seeds`/`project_sources` queries re-run on a CSV content edit, the address projection's output is unchanged → backdated → the collision query does not re-run.
- **The identity resolution *is* the collision computation.** The `.yml`/`.csv` sidecar disambiguation (`architecture.md` §Resolution) is the same "walk all files, resolve each to an address" pass that detects a doubly-claimed address. So there is **one** authority (`project_address_map`), not two passes — `project_address_collisions` is a thin diagnostic projection of the map.
- **Pure logic in `smelt-core`, thin Salsa wrapper in `smelt-db`** (Salsa purity rule). The resolve-to-address-map logic is a pure function over the already-discovered descriptors; the Salsa query gathers inputs and calls it.
- **Do NOT build per-seed schema-keyed queries in this plan.** Seeds are not reactive today (`project_seeds` is restart-scoped per its own doc comment at `crates/smelt-db/src/queries/project.rs:140-144`). Adding fine-grained per-seed schema invalidation is premature optimisation of a path that isn't even incremental. Add the address projection only; leave schema as the existing batch. The identity/schema split is realised as a *seam ready for future work*, not fully built.
- **`DuplicateAddress`, Error severity, owned by `scoping.md`'s diagnostic table** (resolution-family, alongside `CteShadowsCallerCte`). The colliding entities do not load. Project-scoped (same address in two projects is independent — project-isolation rule).
- **BUG-063 sequencing.** The CLI-discovery deletion (P3) depends on the address-map query existing (P2). Scope the consolidation to **seeds first** (the worst offender, the `discover_seeds` third path); audit sources/functions for the same pattern but do not expand scope if they are already single-sourced.
- **BUG-064 is investigate-then-fix.** Most likely a plain data type leaked into a `smelt-db` query signature; sink it to `smelt-core`/`smelt-types` (both crates already depend on these) and drop the `[dependencies] smelt-planner` line. If `smelt-db` genuinely needs planner *logic* (not just a type), that query is misplaced and the phase blocks for a design call.

## Per-phase routine
1. **Pre-flight.** `cargo test --quiet 2>&1 | tail -40`. If red, check **what** is red: if the failure is this phase's own acceptance target (the fixture/test this phase exists to make green), that is expected — **proceed**. If the red is unrelated breakage, treat it as a block (record + continue, per §"Block conditions"); do not build on a broken baseline.
2. **Spec increment** (only the phases that list one — here, only P5's close-out retraction): edit the named spec section first; keep it timeless (no phase/ledger vocabulary in the spec body).
3. **Red-green `/smelt:implement`.** Write the phase's failing test(s) first, then the implementation, spec as oracle. Implementer pass, then reviewer pass (material findings only).
4. **Verify.** `cargo fmt --all`; `cargo clippy --all-targets` (zero warnings); `cargo test` green; plus the phase's gates: `cargo test -p smelt-cli --test example_diagnostics` **and** `cargo test -p smelt-lsp --test example_workspaces` (the dual gate — the LSP gate is what catches CLI/Salsa divergence, the whole point of this cluster). For `example_builds`: run **scoped** — `SMELT_EXAMPLE_BUILDS_ONLY="<ws…>" cargo test -p smelt-cli --test example_builds`.
5. **Record + commit.** Update the status-table row to `done` + date; commit and push tests + impl + (spec at P5) + table together. Emit `<<PHASE_COMPLETE>>` (or `<<ALL_DONE>>` on the last green phase).

- The phase needs a design decision **not** answered by this plan (the decisions above are settled) or the spec — e.g. the `DuplicateAddress` anchor range needs a product call, or BUG-064's leak turns out to be planner *logic* rather than a type.
- Pre-flight is red on **unrelated** breakage (not this phase's own target).
- The tree can't be returned to green after the phase.

# Plan: DISTINCT / DISTINCT ON Property Test Generators

**Date**: 2026-03-22
**TODO item**: Generate DISTINCT expressions in property test generators

## Context

The property test generators (`crates/smelt-db/tests/prop_helpers/generators.rs`) currently emit `SELECT ... FROM data` queries without ever using `DISTINCT` or `DISTINCT ON`. The parser already fully supports both `SELECT DISTINCT` and `SELECT DISTINCT ON (expr, ...)` (PostgreSQL syntax), but these paths get zero coverage from the property tests.

DISTINCT does not affect type inference -- it filters duplicate rows but preserves column types. This makes it a good candidate for a lightweight generator addition: we can add it to query assembly and verify that smelt's type inference still matches DuckDB's actual output types, confirming DISTINCT doesn't accidentally break or change type resolution.

## Implementation Steps

### 1. Add a `DistinctMode` enum to generators

```rust
#[derive(Debug, Clone)]
pub enum DistinctMode {
    /// No DISTINCT keyword
    None,
    /// SELECT DISTINCT ...
    Distinct,
    /// SELECT DISTINCT ON (col1, col2) ... (PostgreSQL syntax)
    DistinctOn(Vec<String>),  // column names for the ON clause
}
```

### 2. Add a `distinct_mode_strategy` proptest strategy

Generate `DistinctMode` values with weighted distribution:
- ~70% `None` (most queries stay as-is, keeps existing coverage dominant)
- ~20% `Distinct`
- ~10% `DistinctOn` with 1-3 randomly selected column names from the CTE pool

The `DistinctOn` variant needs access to column names, so the strategy should be generated after `column_pool_strategy` via `prop_flat_map`.

### 3. Modify `assemble_cte_query` to accept `DistinctMode`

Current signature:
```rust
pub fn assemble_cte_query(columns: &[TypedSource], exprs: &[TypedExpr]) -> String
```

New signature:
```rust
pub fn assemble_cte_query(columns: &[TypedSource], exprs: &[TypedExpr], distinct: &DistinctMode) -> String
```

In the format string, insert the DISTINCT clause between `SELECT` and the select list:

```rust
let distinct_clause = match distinct {
    DistinctMode::None => String::new(),
    DistinctMode::Distinct => " DISTINCT".to_string(),
    DistinctMode::DistinctOn(cols) => format!(" DISTINCT ON ({})", cols.join(", ")),
};

format!(
    "WITH data AS (SELECT {}) SELECT{} {} FROM data",
    cte_cols.join(", "),
    distinct_clause,
    select_list.join(", ")
)
```

### 4. Constrain DISTINCT ON to non-aggregate queries

`DISTINCT ON` requires an `ORDER BY` clause for deterministic results and conflicts with aggregate queries. To keep things simple:
- When `has_aggregate` is true, downgrade `DistinctOn` to plain `Distinct` (aggregates + DISTINCT is valid SQL)
- When `DistinctOn` is used, append `ORDER BY` with the DISTINCT ON columns first (DuckDB requires this)

### 5. Update `test_scenario_strategy` to include `DistinctMode`

The strategy currently returns `(Vec<TypedSource>, Vec<ExprKind>, Vec<usize>)`. Extend to also return a `DistinctMode`:

```rust
pub fn test_scenario_strategy(
) -> impl Strategy<Value = (Vec<TypedSource>, Vec<ExprKind>, Vec<usize>, DistinctMode)> {
    column_pool_strategy().prop_flat_map(|cols| {
        let col_names: Vec<String> = cols.iter().map(|c| c.name.clone()).collect();
        let num_exprs = 1..=4usize;
        let distinct = distinct_mode_strategy(&col_names);
        (
            Just(cols),
            prop::collection::vec(expr_kind_strategy(), num_exprs.clone()),
            prop::collection::vec(0..100usize, 1..=4),
            distinct,
        )
            .prop_filter("need at least one expr", |(_, kinds, _, _)| !kinds.is_empty())
    })
}
```

## Risks and Mitigations

- **DISTINCT ON + ORDER BY**: DuckDB requires that DISTINCT ON columns appear at the start of the ORDER BY clause. The implementation must append an appropriate ORDER BY when generating DISTINCT ON queries. If this proves too complex for the initial pass, DISTINCT ON can be deferred and only plain DISTINCT added.
- **Aggregate + DISTINCT interaction**: `SELECT DISTINCT SUM(x) FROM data` is valid SQL but somewhat unusual. The implementation should allow it since it doesn't affect types.
- **Window + DISTINCT ON**: Window functions with DISTINCT ON is unusual. The strategy should avoid generating this combination to reduce flaky failures.

# Plan: Add Time as a Base Type for Property Tests

**Date:** 2026-03-22
**TODO item:** "Time type -- Add as a base type for MAKE_TIME and time functions in property test generators."

## Context

The property test generators (`crates/smelt-db/tests/prop_helpers/generators.rs`) define a `BaseType` enum that determines what column types are available for random SQL expression generation. Currently supported base types are: Boolean, Integer, BigInt, Double, Varchar, Date, Timestamp, and Decimal.

The `Time` type (`DataType::Time`) already exists in the smelt type system (`crates/smelt-types/src/lib.rs`), is handled in the Arrow mapping (`arrow_mapping.rs` maps `Time32`/`Time64` to `DataType::Time`), and has type inference support for `MAKE_TIME` (returns `DataType::Time`). However, the property test generators never produce Time-typed columns, so Time-related expressions are never tested against DuckDB.

Adding Time as a base type enables:
1. Testing that `CAST('12:00:00' AS TIME)` round-trips correctly through smelt inference
2. Testing `MAKE_TIME(hour, minute, second)` as a generated function
3. Testing temporal function behavior on Time inputs (e.g., `DATE_PART('hour', time_col)`)
4. Testing cast paths: Time -> VARCHAR, Time -> TIMESTAMP (if supported)
5. Validating the existing `DataType::Time` Arrow mapping against real DuckDB output

## Key Files to Modify

1. **`crates/smelt-db/tests/prop_helpers/generators.rs`** -- Primary changes
2. **`crates/smelt-db/tests/prop_helpers/type_comparison.rs`** -- Possibly add Time-related compatibility rules
3. **`crates/smelt-db/tests/prop_helpers/divergences.rs`** -- Register any discovered divergences

## Implementation Steps

### Step 1: Add `BaseType::Time` variant

In `generators.rs`, add `Time` to the `BaseType` enum and update all match arms:

- **`BaseType::all()`**: Add `BaseType::Time` to the returned slice.
- **`BaseType::to_smelt_type()`**: Map `BaseType::Time` to `DataType::Time`.
- **`BaseType::cast_sql()`**: Return `"CAST('12:30:00' AS TIME)"` (a valid DuckDB TIME literal).
- **`BaseType::col_prefix()`**: Return `"time_col"`.

### Step 2: Update `is_compatible()` for Time inputs

Time is a temporal type, so update `FuncInput::Temporal` matching:

```rust
FuncInput::Temporal => matches!(base, BaseType::Date | BaseType::Timestamp | BaseType::Time),
```

Note: Some temporal functions like `DATE_TRUNC` may not accept Time inputs in DuckDB. If this causes test failures, we have two options:
- Add a `FuncInput::DateTimeTemporal` variant that excludes Time
- Or keep `Temporal` as-is and add Time-incompatible functions to a divergence/exclusion list

Recommendation: Start by including Time in Temporal. If `DATE_TRUNC(time_col)` fails in DuckDB, split `FuncInput::Temporal` into `TemporalDateTimestamp` (for DATE_TRUNC) and `TemporalAny` (for DATE_PART which does accept Time).

### Step 3: Add `MAKE_TIME` as a generated function

Add a new `FuncDesc` to `core_functions()`:

```rust
FuncDesc {
    name: "MAKE_TIME",
    input: FuncInput::NoArg,  // all arguments are literals
    extra_args: &[],
    prepend_literal: None,
    output_type: DataType::Time,
}
```

`MAKE_TIME` takes three integer arguments: `MAKE_TIME(hour, minute, second)`. Since the generator framework currently supports single-column-argument functions with optional extras, we need one of:
- **Option A (simple):** Generate `MAKE_TIME(12, 30, 0)` as a literal-only function (use `FuncInput::NoArg` and hardcode the SQL). This tests the return type inference without needing column arguments.
- **Option B (richer):** Add a new `FuncInput` variant (e.g., `ThreeIntegers`) or use `extra_args` with two `IntLiteral` entries and an integer column as the first arg.

Recommendation: Start with Option A for simplicity. This still validates that smelt infers `MAKE_TIME -> Time`.

### Step 4: Add Time-related cast targets

In the `ExprKind::Cast` arm of `generate_typed_expr()`, add Time cast handling:

```rust
} else if matches!(col.data_type, DataType::Time) {
    &[
        ("VARCHAR", DataType::Varchar { max_length: None }),

```

Also add Time as a cast target from VARCHAR:
```rust

```

### Step 5: Update `smelt_type_to_base()`

Add mapping from `DataType::Time` back to `BaseType::Time`:

```rust
DataType::Time => Some(BaseType::Time),
```

### Step 6: Update `function_return_type()` if needed

Check if any existing function return type logic needs a Time case. `DATE_PART` on a Time column should still return BigInt, which is already handled. `DATE_TRUNC` on Time may not be valid in DuckDB -- verify and handle accordingly.

### Step 7: Run tests and handle failures

```bash
cargo test -p smelt-db --test type_property_tests
```

Expected issues to address:
- **`DATE_TRUNC` on Time:** DuckDB may reject `DATE_TRUNC('month', time_col)`. If so, split `FuncInput::Temporal` or exclude Time from DATE_TRUNC's compatibility.
- **Arrow mapping:** Already handles `Time32`/`Time64` -> `DataType::Time` (line 33 of `arrow_mapping.rs`), so no changes needed there.
- **Type comparison:** Time should compare exactly (no known Text/Varchar-style aliases for Time), so `type_comparison.rs` likely needs no changes.

### Step 8: Register any divergences

If DuckDB returns a different type than smelt infers for any Time expression, add entries to `divergences.rs`.

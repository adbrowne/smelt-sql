## Goal

Make the spec's **per-target overlay** rule real on the production build path. The merge machinery already exists and is unit-tested; only target-threading + input-registration + dispatch is missing.

- **BUG-014 (architectural, verified)** — Spec §"Per-target overlay" mandates that when a build `target` is set, the loader reads `<basename>.<target>.<ext>` (e.g. `cohorts.prod.yaml`), merges it over the base (List roots REPLACE; Record roots deep-merge; Map roots per-key replace), reads at most one overlay per loader call (§Semantics rule 4), registers the overlay file as a Salsa input (§Constraints), and surfaces a schema-violating overlay as "the same diagnostic family as a base-file mismatch". **None of this runs in production today.** The overlay merge is implemented and unit-tested as `loader_resolved_value_with_overlay` (`crates/smelt-db/src/queries/loader.rs:220`, a `#[salsa::tracked]` query; merge logic `crates/smelt-db/src/loader.rs:1137`; merge tests at loader.rs:1634/1694/1743; Salsa-wiring tests at tests.rs:5212+) — but that query has **zero production callers**. The production generator path `collect_loader_values` (`crates/smelt-db/src/queries/project.rs:1391`) calls the BASE-ONLY `loader_resolved_value` (project.rs:1477); it flows from `evaluate_generator` (project.rs:1294) ← `emitted_models` (project.rs:1525), neither of which carries a target. smelt-db has **no active-build-target input** (the `Workspace` singleton at lib.rs:271 has only files/projects/loader_files; lib.rs:294-295 and lib.rs:436 carry explicit "Phase 6 will add per-target overlay inputs…" stub comments). The CLI `--target` is parsed (main.rs:88/176/246/273/426 → `RunArgs.target` → run.rs:46 validation → run.rs:210/385-402 engine/graph use) but the generator/loader expansion runs through a **separate Salsa DB** (run.rs:84 `init_db` → run.rs:88 `discover_emitted_model_files` → smelt-cli/src/lib.rs:196 → `emitted_models` → `evaluate_generator` → `collect_loader_values`) that never receives `args.target`. That is the dead-end. Repro fixture is present: `examples/meta_config_overlay_probe/` (`cohorts.yaml` min_revenue:100 + `cohorts.prod.yaml` min_revenue:999 + `models/cohorts.gen.sql` + README) — `smelt build --target prod` currently emits base `revenue >= 100` (should be `>= 999`), and a schema-violating overlay builds exit-0 with no diagnostic.

**Decision (locked)**: option (a) — wire overlay resolution into production. The merge machinery exists; only target-threading + input-registration + dispatch is missing.

## Design decisions (resolved — do not re-litigate; from the spec + the BUG-014 brief)

- **Wire the existing query; do not re-author merge logic.** `loader_resolved_value_with_overlay` (loader.rs:220) and its merge (loader.rs:1137) are correct and unit-tested. This plan threads a target, registers overlay inputs, and dispatches to that query. No new merge semantics are introduced.
- **The effective build target defaults to the `smelt.yml` `target:` field; `--target` only overrides on the CLI build/run path.** This is the **Workspace-Loading-Parity** mitigation: the LSP has no `--target` concept, so if the target threaded through `load_workspace` were CLI-only, CLI and LSP discovery would diverge and the dual gate (`example_diagnostics` + `example_workspaces`) would catch it as asymmetric discovery. Instead, both CLI and LSP read the *same* config-derived default (smelt-core already parses `target:` at `crates/smelt-core/src/config.rs:202`), so they agree **by construction**; the CLI build/run path supplies an *override* only when `--target` is passed. Both dual-gate tests must stay green through every phase.
- **The active target is a Salsa input, not a query argument threaded through every signature.** A `target: Option<Arc<str>>` field on the singleton `Workspace` input (or a dedicated `BuildTargetInput`) keeps the existing `emitted_models(db, workspace)` / `evaluate_generator` / `collect_loader_values` signatures from churning, and makes overlay resolution **reactive**: changing the target re-runs overlay resolution (the P1 invalidation test asserts this). Prefer the `Workspace` field if it adds the fewest call sites; fall back to a dedicated input only if the singleton field forces broad churn (a block condition).
- **Overlay path is computed, not declared.** `collect_loader_values` derives `<basename>.<target>.<ext>` from the base loader file path + the effective target, and dispatches to `loader_resolved_value_with_overlay` **only when that overlay input exists**; it falls back to the base-only `loader_resolved_value` when the target is unset or the overlay file is absent. This preserves §Semantics rule 4 ("at most one overlay file is read per loader call") and keeps base-only workspaces byte-identical.
- **Overlay files are Salsa inputs registered at the same seam as base files** (§Constraints). The registration seam is `smelt-core::workspace::load_workspace` (`crates/smelt-core/src/workspace.rs:78`) → `register_loader_files_from_disk` (`crates/smelt-db/src/workspace_ingest.rs:79`), which already registers `cohorts.prod.yaml` as a standalone base input (workspace_ingest.rs:110). P2 *pairs* it as the overlay for `cohorts.yaml` rather than leaving it an orphan base input. The lib.rs:294-295 / lib.rs:436 "Phase 6" stub comments are retired here.
- **Diagnostics: overlay mismatch is the same family as a base mismatch** (§"Per-target overlay" final clause). A schema-violating overlay must surface `ConfigLoaderRequiredFieldMissing` / `ConfigLoaderUnknownField` **anchored at the overlay file's row** and fail the build — exactly as a base-file mismatch does. P4 forwards the overlay validation diagnostics through the existing emission/build diagnostic path; it does not invent a new code.
- **Pure logic in `smelt-core`/loader, thin Salsa wrapper in `smelt-db`** (Salsa purity rule). Target-default derivation from config and overlay-path computation are pure functions over already-parsed inputs; the Salsa query gathers inputs and calls them.
- **Project isolation** (project-isolation rule): the effective target and its overlay set are resolved per project, so the same `<target>` in two projects of one workspace stays independent.

## Block conditions (`<<PHASE_BLOCKED>>` — record and continue, no hard-stop)
When a phase hits a condition below, **do not halt**. Instead: (1) set the row to `blocked` with a one-line reason; (2) append a dated entry to §"Blocked phases" (phase id, reason/decision, candidate options); (3) restore the tree to a clean committed state; (4) commit + push; (5) emit `<<PHASE_BLOCKED>>`. The next iteration skips the blocked row.

Conditions:
- Threading the effective target through `load_workspace` forces an LSP-side divergence that **cannot** stay parity-green (the dual gate goes red and the config-default mitigation does not reconcile CLI and LSP discovery). Block for a design call on how the LSP supplies its target.
- Adding the `target` field to the singleton `Workspace` input churns too many call sites to land cleanly (the dedicated-`BuildTargetInput` fallback is itself disruptive). Block for a design call on the input shape.
- The phase needs a design decision **not** answered by this plan (the decisions above are settled) or the spec.
- Pre-flight is red on **unrelated** breakage (not this phase's own target).
- The tree can't be returned to green after the phase.

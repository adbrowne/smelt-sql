## Goal

Remove the `smelt-db → smelt-planner` **production** dependency by hosting the shared logical model + rule interface in a new `smelt-logical` crate below both consumers.

- **BUG-064 (layering, minor — no functional bug)** — `smelt-db` (the Salsa *analysis* layer) declares `smelt-planner` as a production dependency, inverting the documented downward-only stack. The cause is **not** a single leaked type (the earlier quick-fix premise): `smelt-db` calls the planner in four capacities — frontmatter property parsing (`parse_function_properties`, `FunctionProperties`, `Provenance`, `JoinSpec`), the **rule engine** (`detect_builtin_rules`, `RuleContext`, `RuleSeverity`, `RuleDiagnosticCode`, `collect_path_refs`, `SourceTimeseriesMap`), the **logical plan** model (`Plan`, `LogicalNode`, and `build_logical_plan_pure` which today lives *in* smelt-db), and **lowering** (`as_struct_to_sql`, `backend_supports_struct_literal`). These exist because **planner rules are intended to surface as incremental LSP diagnostics**, so the Salsa analysis layer must be able to evaluate them — the dependency is load-bearing, not accidental.

**The reframe that makes extraction the right fix:** `smelt-planner` contains **no physical/backend/execution code** (the physical half lives downstream in `smelt-runtime`/`smelt-cli`). So this is not an analysis-below-physical inversion; it is that **the shared *logical* model is hosted one crate too high** — inside the planner, when both the analyzer (`smelt-db`) and the rule-applier (`smelt-planner`) need it. Extracting it into `smelt-logical` makes the crate graph match the project's logical/physical-separation thesis.

## Design decisions (resolved — do not re-litigate; from the layer analysis in `docs/bug-hunt/2026-05-30-findings.md` BUG-064 + the 2026-06-06 extraction investigation)

- **New crate `smelt-logical`, NOT fold into `smelt-core`.** (a) *Cohesion with the thesis* — the `Plan`/`LogicalNode` model + rule interface *is* the "logical specification" layer the project sells; folding it into the `smelt-core` grab-bag (config + seeds + discovery + workspace) buries it. (b) *Blast radius* — `smelt-core` is foundational and already churny (`config.rs`, `metadata.rs`); hosting the logical model there recompiles the whole downstream world on every logical-model edit, whereas a dedicated crate localizes churn to db+planner. Folding into `smelt-core` is the **rejected fallback** (still removes the edge, but churnier and less expressive).
- **Placement: `smelt-logical` above `smelt-core`/`smelt-parser`/`smelt-types`, below `smelt-db` + `smelt-planner`.** Cycle-free: `smelt-logical → {core, parser, types}`; `smelt-db`/`smelt-planner → smelt-logical`. `smelt-core` does not and must not depend on `smelt-logical`.
- **The consumed surface is a clean lower slice — verified zero entanglement** with rule-*application* or any physical code. Moving `rules/rule_diagnostics.rs` transitively drags the rule-data classifiers (`rules/{cumulative,incremental}.rs`, `analysis/*`, `graph.rs`, `types.rs`) — that whole **rule-data cluster** moves as one unit. It is *volume, not surgery*. The canonical owners of the shared config/frontmatter types (`DeclarationKind`, `TimeseriesConfig`, `IncrementalConfig`, `Granularity`, `parse_frontmatter`) are **already in `smelt-core`**; `smelt-logical` re-exports them from core exactly as `smelt-planner` does today.
- **Rule *application* STAYS in `smelt-planner`.** `rules/mod.rs::Planner`, `logical_plan_rules.rs`, `cube_split.rs`, `plan_printer.rs`, and `#[cfg(feature="python")] python_bridge.rs` are not consumed by `smelt-db` and remain in the planner (which gains a `smelt-logical` dependency). The python feature flag does **not** follow the move.
- **`smelt-planner` re-exports the moved items** (its existing `pub use` lines in `lib.rs` become re-exports from `smelt_logical`), so its public API and every current caller — including `smelt-db` still importing via `smelt_planner::…` — keep compiling. This **decouples the move from the repoint**: the cluster can land (P2) while `smelt-db` still points at `smelt_planner::…`, and the import flip (P4) is a separate, mechanical commit. **Not an atomic big-bang.**
- **`build_logical_plan_pure` + `FnCallInput` move *down* from `smelt-db`** (`lib.rs:~2182,~2346`) into `smelt-logical` alongside the `Plan` model — it is pure plan construction that today wrongly lives in the analysis layer. The `#[salsa::tracked] logical_plan` query stays in `smelt-db` as the thin wrapper that builds inputs and calls it (honors the Salsa-purity invariant).
- **`parse_function_properties` lives with `FunctionProperties` in `smelt-logical`, not `smelt-parser`.** It is YAML-frontmatter *shaping* on top of `smelt_core::frontmatter::parse_frontmatter`; `smelt-parser` is a Rowan SQL parser with no serde/YAML and is the wrong home.
- **Behavior-preserving refactor.** No diagnostic, type, or build output changes. Every phase keeps the full suite + dual gate green; the only observable end-state difference is `cargo tree -p smelt-db` no longer listing `smelt-planner`.

## Block conditions (`<<PHASE_BLOCKED>>` — record and continue, no hard-stop)
When a phase hits a condition below, **do not halt**. Instead: (1) set the row to `blocked` with a one-line reason; (2) append a dated entry to §"Blocked phases" (phase id, reason/decision, candidate options); (3) restore the tree to a clean committed state; (4) commit + push; (5) emit `<<PHASE_BLOCKED>>`. The next iteration skips the blocked row.

Conditions:
- The transitive drag pulls a **rule-application** or **physical/runtime** type into `smelt-logical` (the investigation says it won't — `RuleContext`/`Plan` reference no execution/backend type — but if one surfaces, the boundary needs a design call: split the offending type rather than drag the application layer down).
- A genuine dependency **cycle** appears (e.g. something in the moved cluster turns out to need `smelt-db`/`smelt-planner`).
- Pre-flight is red on **unrelated** breakage (not this phase's own target).
- The tree can't be returned to green after the phase.

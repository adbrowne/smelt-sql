| Dec | One-line contract (the spec is authoritative) |
|-----|-----------------------------------------------|
| **D-53 (1)** | Pool contents are scale-invariant **only if no shape field uses `foreign_key`**; this is a behavioral truth enforced at generation time by the `fk_counts` passed to `LinkedPool::new` — no new config-time check is needed beyond documenting the rule. |

### Phase P1: `floor()` scale factor, FK bound for all scale factors, zero-row guard

**Goal.** Three related correctness fixes in `run_config()`:

1. **`floor()` not `round()`**: `main.rs` line 217 computes `((num_rows as f64) * scale_factor).round()`. The spec says `floor`. Change to `.floor() as usize` everywhere the effective row count is derived (both the `fk_counts` build loop and the dataset generation loop use the same formula; patch both at once — they're a few lines apart).

2. **FK bound for scale > 1**: `fk_counts` is built before datasets are generated, and its values are already scaled row counts, so the `ForeignKey` generator arm in `apply_spec` (`generic.rs` line 349) already uses the scaled count as its bound — this is correct. The spec says FK bounds equal the effective (scaled) count for _any_ scale factor. The existing `unwrap_or(1)` silent fallback should be converted to a proper error return (`anyhow::bail!` or `Err`) so a missing FK target is loud, not silent. (Note: missing FK targets should have been caught by the forward-reference check, so this is defence-in-depth.)

3. **Zero-row guard**: After computing `scaled_rows = floor(num_rows × scale_factor)`, check whether it is `0`. If so, return a configuration error immediately — do not insert a `0` into `fk_counts` (which would cause a `% 0` panic in the FK generator) and do not attempt to write a zero-row dataset. For FK referencing: after the `fk_counts` build, the per-dataset generation loop should also check that any FK target in its columns has a non-zero count in `fk_counts` before starting generation (covering the case where the target dataset itself produced a zero effective row count).

**Critical files.**
- `crates/smelt-datagen/src/main.rs` — `run_config()`: the `fk_counts` build loop (lines 195–219) and the generation loop (lines 221–280).
- `crates/smelt-datagen/src/generic.rs` — `apply_spec()` `ForeignKey` arm (lines 348–351): harden the `unwrap_or(1)` fallback.

**TDD tests to write first** (add to `crates/smelt-datagen/tests/` as a new file `scale_factor.rs`, or extend `invalid_config.rs`):
- `fk_bound_at_scale_less_than_one` — config: `devices` has `num_rows: 100`; `events` has a `foreign_key { dataset: devices }` column; run with `scale_factor: 0.5`. All generated FK values must be in `[1, 50]` (floor(100 × 0.5) = 50), not `[1, 100]`.
- `fk_bound_at_scale_greater_than_one` — same config, `scale_factor: 2.0`. All FK values must be in `[1, 200]`.
- `scale_factor_uses_floor_not_round` — `num_rows: 1`, `scale_factor: 0.9` → effective count = `floor(0.9)` = 0 → **configuration error** (not 1 row, which `round()` would produce).
- `zero_effective_row_count_is_error` — `num_rows: 1`, `scale_factor: 0.4` → `floor(0.4) = 0` → error naming the dataset.
- `zero_fk_target_is_error` — `devices` has `num_rows: 1`, `scale_factor: 0.4` → devices effective count = 0 → referencing it via `foreign_key` is an error naming both the target dataset and the referencing column.

**Review checklist:** `floor()` used in both loops; zero count → error not panic; FK bound verified at `< 1`, `= 1`, `> 1`; `unwrap_or(1)` in `apply_spec` hardened; no regression on the existing `invalid_config` tests.

**Commit.** `fix(datagen): floor scale, guard zero effective row count, FK bound at any scale (D-53)`

## Spec mismatch (human triage)

None identified. However, note the following for the implementer:

- The spec says "effective row count = `floor(num_rows × scale_factor)`" but `main.rs` currently uses `.round()`. The spec wins; change to `.floor()`. The distinction matters only when the fractional part is `≥ 0.5` (e.g. `num_rows: 1`, `scale_factor: 0.9` → `round` gives 1, `floor` gives 0 → zero-row error under `floor`). The spec deliberately chose `floor` so that scale factors below 1 can produce zero-row datasets that are caught and reported as errors rather than silently generating a "rounding up" row count.

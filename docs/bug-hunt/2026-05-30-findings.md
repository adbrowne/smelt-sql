### BUG-002 — `smelt.<path>` address-uniqueness (one-path-one-entity) is not enforced at workspace load
- **Phase**: A1   **Feature(s)**: architecture   **Found via**: fixture
- **Severity**: major
- **Symptom**: A workspace with `paths: ["models"]` containing both `models/dup.sql` (bare SELECT → model `smelt.dup`) and `models/dup.csv` (seed → `smelt.dup`) — same directory, same stem, two kinds — must be a hard workspace-load error. Observed: `smelt explain --project-dir <ws> --json` exits 0, silently emits a single `dup` model, and drops the `.csv` with no diagnostic.
- **Root cause**: No collision/uniqueness check exists in `crates/smelt-core/src/discovery.rs` or `crates/smelt-core/src/workspace.rs`. Model discovery (eager, `.sql`) and seed discovery (`discover_seeds`, scans `paths:` roots) never reconcile their address sets; nothing detects two files resolving to the same `smelt.<path>`.
- **Spec rule**: architecture.md §Resolution lines 103 & 105 ("Names must be unique within a directory across all kinds — a `data/users.csv` and `data/users.sql` is a workspace-load error"; "Two files that resolve to the same `smelt.<path>` … are a hard workspace-load error"); Constraint & Invariant #9.
- **Resolution**: decided 2026-06-05 — **full cross-kind enforcement inside Salsa** via a single project-wide *address-map* query (option (a), Salsa variant). Rejected option (b) (partial, eager `load_workspace`-only): the filed repro is model-vs-seed, i.e. precisely the cross-kind case (b) defers, so (b) would not fix the reported symptom. We deliberately drop the "must not depend on Salsa for the collision check" constraint — the collision check becomes a Salsa-derived diagnostic, which is what makes CLI ↔ LSP parity hold by construction (both consume the same query) instead of by keeping two discovery paths in sync.
- **Decision rationale (eager/lazy → identity/schema)**: once the check lives in Salsa, the old `smelt-core` (sync) vs `smelt-db` (Salsa) layering no longer constrains it. The split that *remains worth keeping* is **identity vs schema**, expressed as Salsa query granularity, not as a crate boundary: a collision is a purely *structural* fact (the set of `smelt.<path>` addresses), so the collision query must depend only on an **address-only** projection and never transitively on schema-bearing data — otherwise editing a CSV's contents re-runs the collision check for nothing. Salsa backdating gives this firewall cheaply. Note the identity resolution *is* the collision computation (the `.yml`/`.csv` sidecar disambiguation in `architecture.md:101-102` is the same "walk all files, resolve each to an address" pass that detects a doubly-claimed address), so they should be one authority, not two passes.
- **Implementation plan (next pass)** — spec-first, then code, then tests (TDD red-green):
  - **Spec changes (do first; loop never edits specs autonomously):**
    1. `architecture.md` §"Workspace loading parity rule (CLI ↔ LSP)" (~line 309): reframe the eager/lazy boundary. State that *address/identity resolution and collision enforcement* live in a single Salsa query (the address-map) keyed on `ProjectInput`, consumed identically by CLI and LSP; the surviving split is intra-Salsa **identity (address-only, the collision authority) vs schema (per-entity, computed on demand)**, expressed as query decomposition + backdating, not as a `smelt-core`/`smelt-db` boundary. Remove the implication that the cross-kind uniqueness check belongs in eager `load_workspace`.
    2. `architecture.md` §Resolution (lines 104, 106): leave the *rule* as-is (it already states the invariant); append a one-line pointer that enforcement is the `project_address_collisions` query and the diagnostic code below.
    3. Diagnostic surface: mint a code (proposed `DuplicateAddress`) and add it to the owning spec's diagnostic table (architecture.md / scoping.md, wherever workspace-scoped codes are tabled). This is *new diagnostic surface* — the reason this stays needs-review rather than an in-loop autofix (precedent: BUG-003, BUG-007).
  - **Code changes (ordered):**
    1. Add a pure, Salsa-free resolver in `smelt-core` that takes the project's discovered model + function + seed + source descriptors and returns `Map<address, EntityRef>` plus the set of duplicate addresses (Salsa Purity rule — logic is pure, the query is a thin wrapper). The four address sources already exist: models/functions via `load_workspace`/`discovery.rs`, seeds via `discover_seed_infos_with_sidecars` (`crates/smelt-core/src/seeds/mod.rs`), sources via `discover_source_infos` (`crates/smelt-core/src/sources.rs`). Reuse `address_segments.join(".")` as the canonical key (mirror the BUG-005 fix in `logical_graph.rs`).
    2. Add `project_address_map(db, project) -> Arc<Map<Address, EntityRef>>` and `project_address_collisions(db, project) -> Arc<Vec<Diagnostic>>` in `crates/smelt-db/src/queries/project.rs`, keyed on `ProjectInput`. The collision query reads only the **address** projection of seeds/sources — add `project_seed_addresses`/`project_source_addresses` (or project them off the existing `project_seeds`/`project_sources`; backdating firewalls schema-only churn either way). Do **not** make the collision query read `SeedInfo.columns`/`SourceInfo` schema fields.

### BUG-065 — Struct `.*` spread inside a CTE body does not propagate struct fields to the outer SELECT
- **Phase**: D2   **Feature(s)**: function_schema_inference, functions, types   **Found via**: fixture
- **Severity**: major
- **Symptom**: A model body of the form `WITH parsed AS (SELECT smelt.functions.f(raw_col).*  FROM src)  SELECT field1, field2 FROM parsed` infers `field1: Unknown` and `field2: Unknown` instead of the struct's declared concrete types. Struct spread at the top-level SELECT works correctly; the gap is only when the spread is inside a CTE body.
- **Root cause**: `build_type_context` (schema.rs) processes CTE schemas by calling `infer_cte_columns` → `infer_select_output_schema` (dispatch.rs). `infer_select_output_schema` loops over SELECT items and calls `infer_expression_type` on each; `infer_expression_type` has no branch for `SMELT_PATH_CALL_STAR`, so the spread item produces a single `(col{N}, Unknown)` entry instead of expanding the struct fields. Additionally, `build_type_context` seeds CTE schemas BEFORE seeding function signatures into the `TypeContext`, so even after adding a `SMELT_PATH_CALL_STAR` handler, `ctx.lookup_function_signature` returns `None` and the expansion cannot confirm the closed-struct return type.
- **Spec rule**: `function_schema_inference.md` §"Propagation through CTEs, subqueries, and joins" (rule 4): "A `TableExpr`-function output schema is a first-class schema: it propagates through the caller's body structurally and transparently… There is no schema-resolution penalty for wrapping a function call in a CTE or subquery." The same transparency rule applies to struct spreads — the spec does not carve out a CTE exception for `.*` items.
- **Resolution**: code-fix
- **Regression test**: `crates/smelt-cli/tests/type_command_function_returns.rs::struct_spread_inside_cte_body_propagates_field_types` + `examples/fn_struct_spread_cte/`
- **Status**: fixed — Two changes: (1) Added `try_expand_struct_spread_item` to `infer_select_output_schema` (dispatch.rs) — for `SMELT_PATH_CALL_STAR` items, resolves the inner call via `infer_smelt_path_call_type`, confirms closed-struct return, and expands fields. (2) Added `all_function_signatures()` to the `RefSchemaProvider` trait (default `vec![]`; `SalsaRefSchemaProvider` overrides with a workspace scan) and seeded function signatures into `build_type_context` BEFORE CTE processing so `try_expand_struct_spread_item` can find the function's declared return type.

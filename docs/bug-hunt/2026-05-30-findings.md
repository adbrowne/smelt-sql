## Findings

### BUG-001 — Run-pipeline parity rule names a standing CI gate that does not exist
- **Phase**: A1   **Feature(s)**: architecture   **Found via**: drift
- **Severity**: major
- **Symptom**: `docs/specs/architecture.md:318` and `CLAUDE.md` both state the standing gate is `cargo test -p smelt-runtime --test execute_parity`, "which runs the same fixture project through both `smelt-cli` and `smelt-ui` entry points and asserts identical model outputs, manifest contents, and selection sets." No `execute_parity.rs` target exists. `crates/smelt-runtime/tests/compile_parity.rs` tests only the compile API (from outside the crate); `select_parity.rs` tests only `select_executable_models` on in-memory graphs. Neither drives both the CLI (`commands/run.rs`) and UI (`run_manager.rs`) entry points end-to-end.
- **Root cause**: `crates/smelt-runtime/tests/compile_parity.rs:13-14` — "The end-to-end CLI-vs-UI run-output parity test lands in Phase 4 (`execute_parity.rs`)." That phase's test never landed, but the spec + CLAUDE.md + `.claude/commands/smelt/validate.md` were written as if it had. The CLI↔UI run-output parity invariant (Run Pipeline Parity Rule) is therefore **unenforced** by any test.
- **Spec rule**: architecture.md §"Run pipeline parity rule (CLI ↔ UI)" — "The standing CI gate is `cargo test -p smelt-runtime --test execute_parity` …". Validate rule #3: a spec rule with no test is itself drift.
- **Resolution**: needs-review (invariant)
- **Options**: (a) **Add `execute_parity.rs`** — the spec-mandated test: run one DuckDB-backed fixture (test models, generators, `smelt.fn.*` calls, incremental, cumulative) through both `smelt-cli`'s `execute_project` path and `smelt-ui`'s `run_manager.rs`, assert identical model outputs + manifest + selection set. Spec-faithful; non-trivial; touches the parity invariant. (b) Weaken `architecture.md` + `CLAUDE.md` to describe actual coverage (compile + selection tested in isolation) and move full CLI↔UI run parity to **Known Divergences** with a tracking plan link. — *recommendation*: **(a)** — the invariant is load-bearing, three documents already assume the gate exists, and `compile_parity.rs` always intended it ("Phase 4"). Flag scope to the human before authoring.
- **Regression test**: _none yet (would be the new `execute_parity.rs`)_
- **Status**: needs-review

### BUG-002 — `smelt.<path>` address-uniqueness (one-path-one-entity) is not enforced at workspace load
- **Phase**: A1   **Feature(s)**: architecture   **Found via**: fixture
- **Severity**: major
- **Symptom**: A workspace with `paths: ["models"]` containing both `models/dup.sql` (bare SELECT → model `smelt.dup`) and `models/dup.csv` (seed → `smelt.dup`) — same directory, same stem, two kinds — must be a hard workspace-load error. Observed: `smelt explain --project-dir <ws> --json` exits 0, silently emits a single `dup` model, and drops the `.csv` with no diagnostic.
- **Root cause**: No collision/uniqueness check exists in `crates/smelt-core/src/discovery.rs` or `crates/smelt-core/src/workspace.rs`. Model discovery (eager, `.sql`) and seed discovery (`discover_seeds`, scans `paths:` roots) never reconcile their address sets; nothing detects two files resolving to the same `smelt.<path>`.
- **Spec rule**: architecture.md §Resolution lines 103 & 105 ("Names must be unique within a directory across all kinds — a `data/users.csv` and `data/users.sql` is a workspace-load error"; "Two files that resolve to the same `smelt.<path>` … are a hard workspace-load error"); Constraint & Invariant #9.
- **Resolution**: needs-review (invariant)
- **Options**: (a) Add a workspace-load collision check that gathers all entity addresses across kinds and errors on duplicates. **Full** enforcement (model vs seed vs source) must span the eager (`load_workspace`) and lazy (Salsa `project_seeds`/`project_sources`) discovery paths — crossing the eager/lazy boundary the architecture spec deliberately separates, and it must surface identically in CLI and LSP (workspace-loading parity). (b) Implement **partial** enforcement now for the contained eager set (model-vs-model, model-vs-function) in `load_workspace`, and track full cross-kind collision (incl. seeds/sources) separately. — *recommendation*: discuss (a) vs (b); decide where the cross-kind check lives without violating the eager/lazy split. Add a `examples/*_broken_*` fixture + a diagnostic-assertion test once the shape is agreed.
- **Regression test**: _none yet (would be an `examples/architecture_broken_path_collision/` fixture + a workspace-load-error assertion)_
- **Status**: needs-review

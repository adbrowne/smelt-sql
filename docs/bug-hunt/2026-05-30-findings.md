### BUG-005 — Sub-directory seeds unresolvable in the CLI run/explain path (asymmetric discovery)
- **Phase**: A3   **Feature(s)**: cli (architecture, seeds)   **Found via**: fixture (adversarial drive of `smelt explain`/`build` over `examples/ephemeral_demo`)
- **Severity**: major
- **Symptom**: `examples/ephemeral_demo` declares an ephemeral seed at `models/lookup/regions.csv` (sidecar `regions.yml`) and a model `region_report` selecting from `smelt.lookup.regions`. Both LSP gates assert the workspace is clean (`example_diagnostics::ephemeral_demo_no_diagnostics`, `example_workspaces::ephemeral_demo`), yet `smelt build`, `smelt run`, and `smelt explain [--json]` all fail: `Dependency resolution failed: Model 'region_report' references undefined model/source 'lookup.regions'` (exit 1). A shipped example demonstrating ephemeral seeds could not be built or explained from the CLI.
- **Root cause**: `crates/smelt-cli/src/logical_graph.rs:78` — `let seed_set: HashSet<String> = seeds.iter().map(|s| s.name.clone()).collect();` keyed the seed validation set by the seed's leaf `name` (`"regions"`). But model nodes and dependency strings are keyed by the **canonical dot-path** (`address_segments.join(".")`, e.g. `"lookup.regions"`; see `logical_graph.rs:137-144`, `:193-206`). `validate()` (`:247`) then checks `is_seed("lookup.regions")` against a set holding only `"regions"` → miss → "undefined". The CLI's dep-validation resolver thus diverged from the Salsa/LSP `resolve_ref_path`, which resolves sub-directory seeds by full address — the asymmetric-discovery bug class `CLAUDE.md` warns about. The existing `ephemeral_seed.rs` test missed it because it builds the resolver manually rather than driving the CLI discovery + graph path.
- **Spec rule**: architecture.md §Resolution ("`smelt.<path>` is the universal addressing scheme"; entities addressable by full path); cli.md Constraint #11 ("Argument resolution uses the same resolver as model SQL … there is no parallel leaf-only resolver in the CLI surface") and Constraint #10 (all CLI output canonical `smelt.<path>`).
- **Resolution**: code-fix
- **Regression test**: `crates/smelt-cli/src/logical_graph.rs::tests::test_subdirectory_seed_as_ref_target_validates` (unit, red-green confirmed — fails with the exact "undefined model/source 'lookup.regions'" error before the fix) + `crates/smelt-cli/tests/subdir_seed_resolution.rs::ephemeral_demo_subdir_seed_resolves_in_cli_path` (integration over the real `examples/ephemeral_demo` through `build_logical_graph`, closing the example-level asymmetric-discovery gap the gates missed).
- **Fix**: key `seed_set` by `address_segments.join(".")` (falling back to `name` when empty, mirroring the model `canonical_key` logic). Backward-compatible: top-level seeds have `address_segments == [name]`, so their key is unchanged. `iter_seeds()` now surfaces seeds by canonical path (Constraint #10).
- **Status**: fixed

### BUG-006 — In-model meta-language is LSP-clean but does not survive the CLI run/build pipeline
- **Phase**: A5   **Feature(s)**: meta_language (architecture, cli)   **Found via**: fixture (adversarial end-to-end drive of `smelt run`/`build` over shipped `examples/meta_*`)
- **Severity**: major
- **Symptom**: Multiple shipped, LSP-clean meta-language example workspaces fail when driven through the CLI run/build path, in two distinct ways:
  - `examples/meta_lists` → `smelt run` emits an un-elided empty spread to DuckDB: `Parser Error: syntax error at or near ".."` on `...[],`. The spec (§"Lists and spread", Surface + Semantics rule 7) requires `...[]` to elide itself and adjacent commas before SQL reaches the engine.
  - `examples/meta_hofs`, `examples/meta_polish` → `Dependency validation failed: Model '…' references undefined model/source 'config.var'` (from `smelt.config.var(...)`).
  - `examples/meta_workspace` → `references undefined model/source 'with_tag'` (from `smelt.models.with_tag(...)`).
  - A reflection function `coalesce_numeric(t) = smelt.columns_of(t) |> filter(fn c => c.is_numeric) |> map(fn c => COALESCE(c.name,0))` spread into a hand-authored model is inlined but emitted **verbatim** (the `...`, `|>`, `columns_of` are never meta-evaluated) → DuckDB `syntax error at or near ".."`.
  All of these workspaces pass `cargo test -p smelt-cli --test example_diagnostics` (LSP/Salsa path is clean); only the CLI run/build/explain path is affected. This is the BUG-005 asymmetric-discovery class, now systemic across the meta-language surface.
- **Root cause** (two classes, both confirmed by code inspection):
  - **Class 1 — CLI dependency validator mis-extracts meta accessors as model/source refs.** `crates/smelt-cli/src/logical_graph.rs:113-134`: the dependency filter skips only `Some("sources") | Some("functions")` namespaces (line 117) and strips a legacy `models` prefix (line 123-124). It does **not** exclude the meta-accessor namespaces `config.*` (so `smelt.config.var` → dep `"config.var"`), bare `columns_of` (→ dep `"columns_of"`), or `models.with_tag`/`models.all` (the `models`-prefix strip turns `smelt.models.with_tag` into dep `"with_tag"`). `extract_refs` (`crates/smelt-core/src/refs.rs:57-111`) emits **all** `smelt.<path>` call forms — meta accessors included — and the CLI consumes them unfiltered. The Salsa/LSP path explicitly excludes these meta accessors before dependency resolution (`crates/smelt-db/src/queries/function_diagnostics.rs:1083-1101`), which is why the example_diagnostics gate stays green.
  - **Class 2 — in-model meta-evaluation is never invoked in the run pipeline.** `crates/smelt-cli/src/commands/run.rs` delegates to `smelt_runtime::execute_project`, which expands **only** generator-emitted models (the W1–W4 Salsa pipeline in `crates/smelt-db/src/queries/project.rs::evaluate_generator`/`emitted_models`). Hand-authored models containing inline meta syntax (spread/HOF/`columns_of`/ternary) are passed to the compiler verbatim — there is no meta-expansion step for them. `examples/per_cohort_union` builds only because it routes everything through a `generates: models` generator (which IS expanded), not through in-model spread/HOF.
- **Spec rule**: §"Lists and spread" Surface ("Empty-list spread elides itself and its adjacent commas") + Semantics rule 7; §"Reflection"/§"Compile-time variables" (accessors are meta-only, never model refs); §"Two worlds, one program" ("After meta-evaluation, the Data-World CST handed to codegen contains no `ARRAY_LITERAL` and no spread node"). Architecture §Run Pipeline Parity (the gap is in the shared `execute_project`, so it affects CLI and UI identically).
- **Resolution**: needs-review (invariant / architectural — the holding fix touches `smelt-runtime`'s run pipeline)
- **Options**:
  - (a) **Wire in-model meta-expansion into `smelt_runtime::execute_project`** so hand-authored models with spread/HOF/`columns_of`/ternary are meta-evaluated before codegen (the Class-2 fix), AND add the meta-accessor namespaces to the CLI dependency filter at `logical_graph.rs:117` — or, better, exclude meta accessors at the shared `extract_refs` boundary so CLI and Salsa agree (the Class-1 fix). Add an end-to-end gate (`smelt build` over `meta_lists`/`meta_hofs` asserting correct DuckDB output) — currently no test drives these examples through the CLI. Spec-faithful but non-trivial and pipeline-touching.
  - (b) **Scope the shipped `meta_*` examples as LSP-only demonstration fixtures** (matching `meta_columns`, whose source has no backing data and was never meant to run), and add a §Known Divergence to `meta_language.md` stating in-model meta-expansion in the run pipeline is not yet wired (only `generates: models` generators expand end-to-end). Lower effort; documents reality; defers the codegen work.
  - *Recommendation*: **(a)** for Class 1 at minimum (the CLI/Salsa resolver divergence is a clear correctness bug and the exact asymmetric-discovery class CLAUDE.md warns about), gated behind a human decision on Class 2's scope. Class 1's isolated fix was **not** applied autonomously because (i) on its own it does not make any example buildable (Class 2 still blocks with a DuckDB syntax error, so a "won't hold" end-to-end regression test is impossible), and (ii) excluding the `models.with_tag` form collides with the legacy `smelt.models.<leaf>` model-namespace strip and needs a resolver-design call.
- **Regression test**: _none yet_ — deferred to the human pass. The natural shapes: a `logical_graph.rs` unit test asserting `smelt.config.var(...)`/`smelt.columns_of(...)` are not emitted as model deps (Class 1, would hold), and an end-to-end `smelt build` test over `meta_lists` asserting `...[]` elision in the materialised output (Class 2, only passes after the pipeline fix).
- **Status**: needs-review

### BUG-007 — Function-body CTE colliding with a caller CTE silently drops the argument (no collision diagnostic)
- **Phase**: B1   **Feature(s)**: expansion (functions, codegen)   **Found via**: fixture (adversarial CLI `run -v` drive + DuckDB execution)
- **Severity**: major (silently-wrong data; requires a user-chosen CTE-name collision)
- **Symptom**: A `smelt.define` whose body declares a CTE, when called with a caller-scope CTE of the **same name**, emits SQL in which the argument is silently shadowed by the body's CTE — producing wrong results with **no diagnostic**. Minimal repro (driven through `target/debug/smelt run --project-dir <ws> -v`, then queried on DuckDB):
  - Function `dbl(source: TableExpr<{amount: Numeric}>) -> TableExpr AS ( WITH helper AS (SELECT 1 AS amount) SELECT amount * 2 AS doubled FROM source )`.
  - Model `WITH helper AS (SELECT CAST(10 AS DECIMAL(18,2)) AS amount) SELECT doubled FROM smelt.functions.dbl(helper)`.
  - Emitted SQL: `… FROM ((WITH helper AS (SELECT 1 AS amount) SELECT amount * 2 AS doubled FROM helper)) AS __smelt_t84`. The argument `source` was substituted to the caller's CTE name `helper`, but the body's own `WITH helper` shadows it; the inner `FROM helper` resolves to the body CTE (`amount=1`), **not** the passed argument (`amount=10`).
  - **Result: `doubled = 2` (int32) instead of the correct `20.00` (decimal).** The caller's data is silently dropped. `smelt build`/`run` exit 0; no warning, no error.
- **Root cause**: No codegen-time caller-vs-callee CTE-collision check exists. The transparent-function splice (`crates/smelt-planner/src/logical_plan_rules.rs`, `ExpandTransparentFunctionCalls`) wraps the callee body as a `FROM (…) AS __smelt_tNN` subquery and substitutes argument identifiers, but never compares the body's introduced CTE names against the caller-scope CTE names at the splice point — so a collision is neither renamed nor diagnosed. `rg` for caller-vs-callee CTE collision detection across `crates/` finds nothing; the only CTE diagnostic is `CteCycle` (within-body mutual recursion only — `crates/smelt-db/src/function_body_check.rs` / `tests/cte_splice.rs::cte_cycle_detected`). The argument-as-CTE shadowing is invisible to type-checking because the body type-checks against the *declared* `source` param schema, and at codegen the substituted identifier silently binds to the nearer (body) CTE under SQL scope rules.
- **Spec rule**: `expansion.md` §Surface line 21 ("the compiler emits a diagnostic rather than alpha-renaming") + §Semantics "Hygiene v1" rule #3 ("CTE-name collisions emit a diagnostic … anchored at the body CTE's declaration"). The spec frames collisions as a *hygiene* gap ("not a soundness gap — collisions surface as a diagnostic rather than as silently-wrong code"); because the diagnostic is absent, it is **currently a soundness gap**.
- **Resolution**: needs-review (invariant / architectural — the holding fix lands a new diagnostic in the codegen/run pipeline, touching the Run-Pipeline-Parity seam; and adds diagnostic surface, which prior precedent (BUG-003) treats as needs-review rather than an in-loop auto-fix)
- **Options**:
  - (a) **Implement codegen-time CTE-collision detection.** At the transparent-function splice point, collect the caller-scope CTE names in scope and the callee body's introduced CTE names; on overlap, emit a collision diagnostic anchored at the body CTE's declaration (mint a dedicated code such as `CteShadowsCallerCte`, or reuse the `CteCycle` family per the spec's hedge). Add the code to `scoping.md`'s diagnostic table + a `examples/*_broken_*` fixture + a `broken_function_diagnostics`-style assertion (red-green). Spec-faithful; non-trivial; pipeline-touching; new diagnostic surface. *(v2's planned alpha-rename would instead rename the body CTE — out of v1 scope.)*
  - (b) **Demote Hygiene v1 rule #3 to a Known Divergence** in `expansion.md`, documenting that codegen-time CTE-collision detection is not yet wired and a name collision between a caller CTE and a function-body CTE produces silently-shadowed SQL. Records reality; defers the safety net. **Not acceptable on its own** given the soundness impact — should be paired with at least a `wontfix`→`fix` follow-up plan.
  - *Recommendation*: **(a)** — this is a silent data-correctness bug, the spec already mandates the diagnostic, and the repro is minimal. Flagged needs-review (not auto-fixed in-loop) because the holding fix adds a new diagnostic code to a spec table (loop never edits specs autonomously) and lands in the shared codegen/run pipeline (architectural). A failing regression test was intentionally **not** committed: the only assertions available (a diagnostic that doesn't fire / wrong DuckDB output) would either leave the tree red or require the fix to exist first.
- **Regression test**: _none yet (deferred to the human pass)_ — natural shapes: `examples/expansion_broken_cte_caller_collision/` (function body CTE name == caller CTE name) + a `broken_function_diagnostics` case asserting the collision diagnostic; and an end-to-end `smelt run` assertion that the materialised `doubled` equals the correct `20` (only passes after the fix).
- **Status**: needs-review

### BUG-009 — TableExpr function with a `source.*` body emits over-qualified `schema.table.*` when called with a `smelt.<path>` argument (schema-layer/codegen disagreement)
- **Phase**: B2   **Feature(s)**: function_schema_inference (expansion, types)   **Found via**: fixture (adversarial drive of `smelt type` + `smelt run` over a new probe workspace)
- **Severity**: major (idiomatic `FROM smelt.functions.f(smelt.model)` emits invalid SQL; silent at `smelt type`, fails only at `smelt run`)
- **Symptom**: A `TableExpr`-returning function whose body uses a qualified wildcard `source.*`, when called with a `smelt.<path>` **model/source ref** argument, materialises invalid SQL on DuckDB. Minimal repro (probe workspace, since removed — repro inline):
  - Function: `smelt.define add_margin(source: TableExpr<{revenue: Numeric, cost: Numeric}>) -> TableExpr AS ( SELECT source.*, revenue - cost AS margin FROM source )`.
  - Model `base`: `SELECT CAST(100 AS DECIMAL(18,2)) AS revenue, CAST(30 AS DECIMAL(18,2)) AS cost`.
  - Model `via_cte`: `WITH m AS ( SELECT margin FROM smelt.functions.add_margin(smelt.base) ) SELECT margin FROM m`.
  - `smelt type` resolves the schema correctly: `via_cte: () -> {margin: DECIMAL(38,10)}` (and `via_from -> {revenue, cost, margin}`, `via_subquery -> {margin}`, `via_join -> {revenue, margin}`) — **no `Unknown`**.
  - `smelt run` fails: `Execution failed for 'main.via_cte': Parser Error: syntax error at or near "*"`. Emitted SQL:
    ```sql
    WITH m AS ( SELECT margin FROM ((
      SELECT main.base.*, revenue - cost AS margin FROM main.base
    )) AS __smelt_t118 )
    SELECT margin FROM m
    ```
    The body's `source.*` was rewritten to `main.base.*` (a `schema.table.*` three-part wildcard) which DuckDB's parser rejects.
- **Root cause** (hypothesis, traced): the transparent-function splice (`crates/smelt-planner/src/logical_plan_rules.rs`, `ExpandTransparentFunctionCalls`) substitutes the `source` parameter with the argument's **physical qualified name** (`main.base`) everywhere it appears, including the qualified wildcard `source.*` → `main.base.*`, instead of either (i) aliasing the argument table to the parameter name at the splice (`FROM main.base AS source`, leaving `source.*` intact) or (ii) emitting a single-part `base.*`. `examples/functions_demo/functions/add_margin.sql` is the *same* function but its only runtime caller (`margin_via_cte`) passes a **bare CTE name** `x` as the argument, so `source.*`→`x.*` stays single-part and valid — which is why the bug never surfaced: no existing test executes a `source.*`-bodied TableExpr function over a *model/source ref* on DuckDB. (Schema-layer resolution via `infer_tableexpr_return_schema` is correct in both cases — hence `smelt type` is clean and the gates stay green.)
- **Spec rule**: function_schema_inference.md Constraint & Invariant #2 ("Schema-layer/codegen agreement — the columns a call contributes to a model's resolved `ModelSchema` must equal the columns the emitted SQL for that call produces. Struct-spread and `TableExpr` expansion may not diverge between the two layers."); Semantics rule 3 (`source.*` expands against the `TableExpr` parameter's schema). Also architecture.md §Run Pipeline Parity (the defect is in the shared `execute_project` codegen, so CLI and UI are affected identically — BUG-005/006 asymmetric-discovery class).
- **Resolution**: needs-review (invariant / architectural — the holding fix lands in the shared codegen/run pipeline in `smelt-planner`; same class as BUG-006/BUG-007, which prior iterations also logged needs-review rather than auto-fixing)
- **Options**:
  - (a) **Fix the splice to preserve `source.*` validity.** At the transparent-function splice, alias the substituted argument to the parameter name (`FROM <arg-physical-name> AS source`) so the body's `source.*` remains a valid single-part qualified wildcard; or rewrite the wildcard to use only the trailing identifier of the substituted name (`main.base.*` → `base.*`). Add an end-to-end `smelt run` gate over a TableExpr function called with a `smelt.<path>` argument (the missing coverage). Spec-faithful; non-trivial; pipeline-touching; must not regress `functions_demo/margin_via_cte` (CTE-arg) or the as_struct/`.*` paths.
  - (b) Document an `expansion.md` / `function_schema_inference.md` Known Divergence that a `source.*` body over a `smelt.<path>` argument is not yet supported in codegen, and steer authors to expand columns explicitly. Lower effort; records reality; **not acceptable on its own** because it breaks the canonical idiom the spec's Design section endorses ("authors routinely wrap a function call in a CTE … `WITH sessionized AS (SELECT … FROM smelt.functions.sessionize(...))`").
  - *Recommendation*: **(a)** — it is a clear codegen correctness bug breaking idiomatic usage, the schema layer already proves the intended shape, and the spec mandates schema/codegen agreement. Flagged `needs-review` (not auto-fixed in-loop) because the holding fix lands in the shared `smelt-planner` splice (architectural) and must be cross-verified against `functions_demo` and the as_struct path — which the current session's intermittent tool-result channel made too risky to do reliably. No tentative fix was applied; the probe fixture was removed so the tree stays pristine/green (the repro above is self-contained).
- **Regression test**: _none yet (deferred to the human pass)_ — natural shapes: a new `examples/` fixture (e.g. `fn_schema_tableexpr_star/`) with a `source.*`-bodied TableExpr function called via `FROM smelt.functions.f(smelt.<model>)` plus a CTE/subquery/JOIN wrapper, driven through `smelt run` asserting the materialised columns + values (`margin = 70`); only passes after the splice fix. A unit test on the splice asserting the emitted wildcard is single-part would also hold.
- **Status**: needs-review
